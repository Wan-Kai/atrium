# SPEC-0001：MVP 1 纯对话

- **状态**：已确认
- **创建**：2026-09-30
- **更新**：2026-10-04
- **相关**：[路线图](../roadmap.md) 阶段 1 第 1 步、[ADR-0002](../adr/0002-connect-pi-via-rpc-subprocess.md)、[ADR-0005](../adr/0005-split-host-and-ui-pwa-first.md)、[ADR-0006](../adr/0006-organize-sessions-by-workspace.md)、[领域模型](../architecture/domain-model.md)、[设计语言](../architecture/design-language.md)

## 背景与目标

Atrium 的第一个可用版本。它要回答一个问题：**在 Atrium 里用 pi 加 Codex 模型，能不能完成日常的真实编码任务？** 如果不能，整条路线都要调整，所以越早知道越好。

同时，它会把 ADR-0005 定下的架构从头到尾打通一遍：Electron → UI → WebSocket → 宿主 → pi RPC。后面的 MVP 都在这个骨架上叠加。

完成后：你可以在 Atrium 里打开一个项目、和 pi 对话写代码，并且能看清它做了什么。

## 非目标

- Atrium 自己的 extension：审批、上下文检查器都放到 MVP 2。但用户自己安装的 pi extension 弹出的对话框必须能显示和回答（需求 10），否则会话会卡住
- 审批：沿用 pi 的默认行为，工具调用直接执行
- 新建和清理 worktree（MVP 1 只识别已有的 worktree）
- 浏览器操作的专门界面（通过 pi 的 `mcp.json` 配置 MCP server 即可使用）
- 插件系统、会话树、分叉
- 打包、签名、自动更新；手机端和 PWA；多窗口
- 文件系统相关：审查面板、文件路径操作（用编辑器打开、在 Finder 中显示等）
- 系统通知
- 订阅额度（5 小时、每周用量）：不在对话面板里显示

## 需求

1. 当我打开 Atrium，我希望在侧栏看到各个项目和其下的工作区（本地目录或 worktree），一眼看出哪些在运行、哪些在等我处理、哪些 worktree 还没合并；在对话区顶部用标签页切换同一工作区里的会话（见下文"侧栏""对话区"）。
2. 当我新建会话并输入需求，我希望看到流式输出的回复和推理过程。
3. 当我粘贴或拖入一张截图，我希望它随消息一起发给模型。
4. 当 agent 调用工具，我希望看到它做了什么：执行的命令和输出、读了哪个文件、改动的 diff、新写入的文件。
5. 当 agent 走偏了，我希望随时中断它。
6. 当 agent 还在运行时，我希望继续输入的消息默认排队；需要时点一下，就能让它在 agent 下一步之前送达（插话）。
7. 当我想换模型或调整推理强度，我希望在输入框旁边直接切换。
8. 当我关掉 Atrium 再打开，我希望恢复之前的会话继续聊。
9. 我希望在输入框下方的状态栏随时看到上下文用量、缓存命中率、token 用量、输出速度，并能选择显示哪些指标。
10. 当我自己安装的 pi extension 弹出对话框提问时，我希望在 Atrium 里看到并回答它。
11. 我希望对话默认只突出回复，过程折叠起来；需要时能切换显示模式，查看推理过程或每一步的细节。
12. 当一个会话在跑时，我希望切去看别的会话、甚至开新会话，它在后台继续跑。
13. 第一次打开 Atrium 时，我希望被引导装好 pi、登录模型、添加项目。
14. 我希望能复制一条消息或一条回复。

## 方案设计

### 进程与启动

```
Electron 主进程
  ├── 启动宿主（Node 子进程），生成随机 token，宿主监听 127.0.0.1 的随机端口
  └── 窗口加载宿主提供的 UI，并通过 preload 把地址和 token 交给 UI

宿主
  └── 每个活动的会话 → 一个 pi 子进程：pi --mode rpc [--session <文件>]，工作目录为工作区目录（对话为它自己的目录）
```

- 多个会话可以同时运行，切走不中断。MVP 1 不回收空闲进程（与 Paseo 一致）：会话打开后 pi 进程常驻，直到归档、交给终端、宿主退出或进程崩溃；宿主重启后会话处于"未启动"，打开时再以 `--session` 启动。会话多了再加回收。
- pi 进程意外退出时，宿主通知 UI，用户可以一键重新打开这个会话。

### 各包职责

| 包 | MVP 1 要做的 |
|---|---|
| `protocol` | 用 zod 定义下文的命令和事件 |
| `client` | WebSocket 连接（带 token、断线重连）、收发协议消息、维护会话状态：消息列表、流式拼接、运行状态、用量 |
| `host` | WebSocket 服务和鉴权；项目和会话列表；pi 适配器：启动和监督进程，把 pi 事件翻译成 Atrium 事件 |
| `ui` | 界面，见下文 |
| `apps/desktop` | 启动宿主、创建窗口、preload 传 token |

### 界面

```
┌──────────────┬──────────────────────────────────────────┐
│ 侧栏          │ 对话区：标题栏 / 消息流 / 排队 / 输入框       │
│ 收件箱        │                                          │
│ 项目 → 会话    │ 状态栏（输入框正下方，居中）                 │
└──────────────┴──────────────────────────────────────────┘
```

- **视觉**：以 DeepSeek Harness 的产品界面为基准，逐个组件实测后对齐（系统字体、半透明侧栏与主区贴合、14px 常规字重为主、0.5px 细线、圆角 8 / 12 / 16 / 22）。
- **图标**：Phosphor Icons。14～18px 用 regular（屏幕线宽约 1px），20px 以上用 light；状态图标是纯线性图标，只给图标上色，不加底色。
- **动效**：以 Apple 为基准，用弹簧（时长 + 回弹）而不是固定时长的缓动；按下立即反馈、展开收起有高度过渡、位置变化用位移过渡；遵从系统的"减弱动态效果"。
- **外观**：跟随系统 / 浅色 / 深色三档，记住选择，系统外观变化时自动跟随；深色贴近 DeepSeek Harness，浅色按同样的层级关系推导。
- 完整页面原型：`prototypes/app-prototype.html`。设计规范（变量、组件、动效参数）见 [设计语言](../architecture/design-language.md)。
- 本 spec 引用的原型（`prototypes/` 下的侧栏、对话区、图标对比、完整页面）按"用完即弃"的约定保存在 `prototype/ui` 分支，不进 `main`。

### 侧栏

参考 Paseo 的工作区模型，侧栏按"项目 → 工作区"组织，会话放在工作区里，以对话区顶部的标签页呈现（见"对话区"）；另有不绑定工作区的"对话"。尺寸和样式按 DeepSeek Harness 对齐（宽 270、行高 34、14px）。原型讨论过程中先后比较过"会话平铺 + 彩色 git 图标 + worktree 折叠区"等方案（`prototypes/sidebar-prototype.html`），最终改为工作区模型：会话属于哪个 worktree 从靠颜色对应变成结构上的包含，合并状态直接挂在工作区上。

**概念关系**

```
项目（一个 git 仓库或目录）
 ├── 本地工作区（项目目录本身，每个项目一个）
 └── worktree 工作区（每个 worktree 一个，含不是 Atrium 创建的"外部" worktree）
      │  工作区与目录一一对应
      └── 会话（目录下的 pi 会话文件）
           ├── 打开着的 → 对话区顶部的标签页
           └── 全部 → "历史"菜单
对话（不绑定项目和工作区的会话，⌘N 新建）
 └── 每个对话一个空目录 ~/.atrium/chats/<id>/，宿主按目录认出它们
```

- 工作区和目录一一对应：pi 按工作目录保存会话，宿主按会话的工作目录把它归到对应的工作区，没有歧义。以后确实需要多个工作区共用一个目录（按任务分组）时再放开。
- MVP 1 的工作区：每个项目自动有一个本地工作区；`git worktree list` 识别出的每个 worktree 是一个工作区。新建 worktree 工作区、归档并清理 worktree 放到阶段 1 第 3 步。
- 对话用于和项目无关的提问。pi 必须有工作目录，所以每个对话给一个独立的空目录，agent 写的文件互不干扰；"移到某个项目"以后再做。
- Atrium 只保存索引：项目列表（目录、显示名）；工作区（所属项目、本地或 worktree、目录、分支、自定义名称、创建时的起点提交、是否外部、是否归档）；每个工作区和"对话"打开着哪些标签页、当前是哪一个；会话的归档状态、出错是否已看过。不保存对话内容。

**收件箱**

- 只放"等你处理"和"出错"的会话，跨所有项目和对话汇总，按状态优先级、再按时间排序。第一行是会话标题和最近活动时间，第二行是"项目 · 工作区"，对话写"对话"。
- 最多显示 5 条，其余收成"还有 N 条"，点击展开；展开后末尾是"收起"。
- 点击：切到会话所在的工作区（或"对话"），没打开的会话补开一个标签页并激活。收件箱行和工作区行同时高亮：一个表示正在看的会话，一个表示所在的工作区。工作区所在的项目是收起的，不自动展开，项目行带上选中底色。
- 离开收件箱：待审批、待回答、待授权要等问题解决（看一眼不算）；出错的会话打开过即算已看过，移出收件箱，但标签页和工作区行上的出错图标保留，直到下一次运行开始。
- 不单独设"运行中"分区。

**搜索**

- 点"项目"标题右侧的搜索按钮，搜索框在原位展开；搜索框和它上面的内容（新建对话、收件箱、"项目"标题）都不动，项目列表和"对话"换成搜索结果。
- 结果分两组：工作区（名称 + 所属项目 + 合并状态）、会话（与收件箱同样的两行格式，包含对话）。点击工作区切过去；点击会话打开它。
- 匹配工作区名和会话标题；全文搜索以后再做。清空或关闭搜索框，恢复项目列表。

**项目与工作区**

- 项目可折叠。项目行：文件夹图标、名称；悬停出现"+"（新建工作区）；收起时，右侧显示待合并的 worktree 数和其中会话的最高优先级状态。展开时不显示待合并数，下面每个工作区都能看到。
- 工作区在项目下缩进显示，不放图标，名称和项目名对齐。本地工作区排第一；其余 worktree 按创建时间倒序，位置稳定，不因为 agent 跑完一轮而跳动；已合并、已移除的变淡、排在最后。
- 工作区行：名称、合并状态、行尾是其中会话的最高优先级状态（空闲时不显示）。"本地""外部"不单独标注，只在悬停提示里说明。合并状态是纯文字标签、不加底框：未提交、待合并前面有橙色小圆点，`↑N` 用橙色加粗，`✓ 已合并` 用绿色，已移除用最淡的灰色。
- 点击工作区：切过去，恢复它上次激活的标签页；没有打开的会话时显示这个工作区的空状态。
- 悬停 worktree 工作区出现"查看改动 / 合并"（未合并时）或"清理"（已合并时），阶段 1 第 3 步实现；MVP 1 只读显示合并状态。
- "···"菜单：重命名；在访达中显示；归档工作区并清理 worktree（阶段 1 第 3 步）。

**对话**

- 侧栏底部的"对话"分区列出最近 5 个对话（标题、时间、非空闲时的状态），更多的点"全部 N 个对话"，在"历史"里看。
- 选中对话时，对话区顶部的标签页是打开着的对话，标签栏的"+"新建对话；新对话的空状态提示"不绑定项目和工作区"。
- 标签栏的"+"在当前所在的地方新建：在工作区里就是这个工作区的会话，在"对话"里就是新对话。

**命名**

- 项目名：默认取目录名，可以重命名。添加的目录与已有项目同名时，自动在后面加序号，如 `app (1)`，并提示可以重命名；手动重命名成已有的名字时，提示重名、不保存。
- 工作区名：默认是分支名，跟着分支变化。本地工作区取项目目录当前检出的分支（不一定是 `main`）；worktree 取它检出的分支；处于 detached HEAD 时用目录名，悬停显示短 commit 号；项目不是 git 仓库时，本地工作区用目录名。
- 工作区可以重命名：自定义名称只存在 Atrium 的索引里，不改 git 分支名；改过名的工作区悬停时显示分支名；名称清空即恢复为分支名。
- 会话标题，按以下顺序取第一个有值的：
  1. pi 的会话名：手动重命名和模型生成的标题都写在这里（`set_session_name`），终端 pi 也能看到。
  2. 兜底标题：第一条用户消息的第一行，去掉 Markdown 符号和首尾空白，过长由界面省略；只有图片时显示"图片"。兜底标题只用于显示，不写回 pi。
- 自动生成标题：会话（含对话）的第一轮运行结束（`agent_settled`）时，如果会话还没有名字，宿主用一次性调用让模型起一个短标题（与用户消息同语言，中文不超过 16 个字，不带标点和引号），写回 pi 的会话名，替换掉兜底标题；标签页、收件箱、"历史"同步更新。
  - 输入：第一条用户消息和第一条回复的开头，截断到约 2000 字符。
  - 调用：`pi --mode json -p --no-session`，默认用当前会话的模型，设置里可以指定一个更便宜的模型。
  - 已经有名字的会话不再生成，因此不会覆盖手动重命名；生成过程中用户手动改了名，丢弃生成结果。
  - 失败时保留兜底标题，在下一轮运行结束时再试一次。
  - 没在 Atrium 里跑过的历史会话（比如终端 pi 里开的）不批量补生成，仍显示兜底标题。
- 在终端 pi 里开的会话同样显示，不区分来源。

**worktree 合并状态**：和会话状态是两个维度。会话状态回答"agent 需不需要我"，合并状态回答"这批改动收尾了没有"。

| 状态 | 判断 | 显示 |
|---|---|---|
| 有未提交的改动 | worktree 内 `git status` 不干净 | `• 未提交` |
| 有未合并的提交 | 未判定为已合并，且分支比主干多 N 个提交 | `↑N`（悬停说明"未合并"） |
| 无改动 | 干净，且分支还停在起点（见下文） | 不显示标签，不变淡 |
| 已合并 | 干净，分支离开过起点，且已进入主干（见下文） | `✓ 已合并`，变淡，提供"清理"入口（阶段 1 第 3 步） |
| 已移除 | worktree 目录不存在（`git worktree list` 标为 prunable） | `已移除`，变淡 |
| 无法判断 | 没有主干分支、git 低于 2.38、git 出错、外部 worktree 看不出起点 | 最淡的 `状态未知`，悬停说明原因；未提交仍照常显示（2026-10-08 定） |

- 主干默认取 `origin/HEAD` 指向的分支，每个项目可以单独修改。比较对象用远程分支（如 `origin/main`），宿主在后台定期 `git fetch`（窗口获得焦点时、每隔几分钟），因为合并常在 GitHub 上完成，本地 `main` 可能还没更新。只 fetch 本身是仓库顶层的项目：放在别的仓库里的普通目录不会去 fetch 外面那个仓库。
- 判断已合并，按顺序：
  1. 分支已在主干历史中（`git merge-base --is-ancestor`）→ 已合并。覆盖普通 merge 和快进。
  2. 否则用 `git merge-tree --write-tree <主干> <分支>` 模拟合并（不改工作区和 index，但会在仓库里创建 git 对象），结果与主干的 tree 相同 → 已合并。覆盖 squash、rebase、cherry-pick；主干之后改了别处不影响判断；主干回滚了该改动则判为未合并。模拟合并有冲突，一律视为未合并。需要 git 2.38 以上。
- 区分"无改动"和"已合并"：刚建好的 worktree 分支天然在主干历史里，只看第 1 步会误判为已合并。Atrium 新建 worktree 时记下起点提交；分支最新提交仍等于起点 → 无改动，离开过起点后又进入主干 → 已合并。外部 worktree 没有记录起点，看分支的 reflog 里有没有过它自己的提交。
- 计算时机：不持续监听文件。对相关的 worktree 重算：其中的会话一次运行结束时、窗口获得焦点时、后台 `git fetch` 之后（只重算 `↑N` 和已合并，不跑 `git status`）。已合并的判断结果按"分支提交 + 主干提交"缓存；同时最多跑 4 个 git 命令。
- 成本：`git status` 最贵（大仓库可能几百毫秒），其余都是毫秒级。
- 不提示"搁置多久"。

**会话状态**：一个会话同时满足多个状态时，按下表从上到下取第一个；工作区行、项目行（收起时）显示其中会话的最高优先级状态。图标是纯线性图标、只给图标上色，不加底色；不同状态用不同的形状或动画区分，不只靠颜色；悬停显示具体原因。

### 对话区

已定稿（原型 `prototypes/app-prototype.html`，在 `prototype/ui` 分支）。

调研了 Claude Code 桌面端、Codex 桌面端、Paseo、Cursor、Zed，共同方向是：**突出结果，折叠过程；运行中的输入可以排队或插话**。MVP 1 只做纯对话能力，审查面板、文件路径操作放到以后。

经原型讨论（`prototypes/conversation-prototype.html` 方案 A）确定采用"过程折叠条"：跑完后过程收成一行摘要，点击展开；没有采用时间线、轮次卡片两种结构。

**标签栏**（对话区顶部）

- 显示当前工作区"打开着的"会话，每个标签是一个会话：标题、非空闲时的状态图标、关闭按钮。关闭标签只是收起，会话保留在"历史"里。
- "+"在当前工作区新建会话（在"对话"里则新建对话）；"历史 ⌄"列出这个工作区的全部会话（状态、时间、是否已打开），点击即在标签页中打开。
- 右侧是显示模式和"···"：重命名、归档、复制会话文件路径、在终端中继续（交接给终端：Atrium 先停止并释放这个会话，再复制 `pi --session <文件>`，见"关键流程"）。
- 标签多了先压缩到最小宽度（约 96px），再放不下就横向滚动，两端渐隐提示还有更多。
- 快捷键：⌘T 在当前工作区新建会话，⌘W 关闭标签，⌘1–9 切到第几个，⌘⇧[ / ⌘⇧] 切到上一个 / 下一个。
- 会话可以在后台运行：切换标签、切换工作区、关闭标签都不会中断它，状态显示在侧栏、收件箱和"历史"里。每个会话本来就是独立的 pi 进程，多个会话可以同时运行；要停下，打开它点"停止"。
- 工作区没有打开的会话时，对话区显示空状态，直接在输入框里输入就会新建会话。空状态（以及新会话、新对话的空状态）的布局和 logo 待设计，先用占位。
- 以后的"对话 / 轨迹"是单个会话内部的视图切换，和会话标签页不冲突，放在对话区里另找位置（MVP 2）。

**显示模式**（参考 Claude Code）：摘要（默认）/ 思考 / 详细，用 Ctrl+O 切换，全局记住选择。入口是标签栏右侧的"👁 摘要模式 ⌄"。

| 内容 | 运行时 | 跑完后（摘要模式） |
|---|---|---|
| 推理过程 | 实时显示 | 折叠成"思考了 N 秒"；思考模式下展开 |
| 只读操作（读文件、搜索、列目录） | 连续的几个合并成一行，如"探索：读了 5 个文件，搜索了 2 次" | 收进过程摘要 |
| 命令（bash） | 一行"运行 · 命令"，右侧显示运行中 / 通过 / 退出码；详情块里实时滚动输出 | 收进过程摘要；有失败的命令时，标题行末尾加红色标记"N 条命令失败"，不单独展开（agent 常常会自己修好，展开显示太吵） |
| 文件改动（edit / write） | 一行"编辑 · 文件路径 +N −M"，详情块里显示 diff（`edit` 用 `details.diff`），带行号和增删竖条 | 收进过程摘要，展开可看 diff |
| 系统事件（上下文压缩、自动重试） | 一行灰色提示，压缩时带压缩前的 token 数 | 保留 |
| 对话框（待回答、待授权） | 消息流底部的卡片，直接在卡片上作答 | 显示你的回答 |

详细模式下所有步骤都展开。

**一轮里的文字**：agent 在一轮里常常说好几段话（"我先看看现有实现…"），中间穿插工具调用。只有最后一段作为回复显示在过程下方；前面几段作为文字步骤收进过程里，展开能看到。一轮里没有任何步骤时不显示过程行；只有推理时显示"思考了 N 秒"。

**过程的呈现**（参考 DeepSeek Harness）：

- 标题行：运行时显示带扫光效果的"进行中"；跑完后显示"已完成，用时 N · 读了 … · 跑了 …"，被中断时显示"已停止，用时 N"。展开时标题行下方有一条细分隔线。
- 步骤是单行列表："图标 + 动词 · 对象"，文件路径带虚线下划线，编辑步骤在末尾显示 +N −M。点击某一步，在下方的深色详情块里显示内容（左上标"输出 / 改动"，右上标工具名）。不做成卡片。

**运行中输入：默认排队，可插话**

- 按回车：agent 空闲时直接发送；运行中进入排队。⌘+回车：直接插话。
- 排队中的消息收在输入框上方的胶囊条里（见"输入框"），可以编辑、删除、点"插话"。
- 插话调用 pi 的 `steer`：在 agent 当前这批工具调用执行完、下一次请求模型之前送达，不是立刻打断。界面上标注"下一步前送达"；要立刻停下用"停止"。
- 排队由宿主管理，不使用 pi 的 `follow_up` 队列：本次运行结束（`agent_settled`），或上一条输入被 extension 直接处理（`handled`）后，宿主依次把下一条作为 `prompt` 发出。这样编辑、删除、调整顺序都由 Atrium 控制。
- 停止后，排队暂停、不自动发出，由你决定继续发送还是清掉。
- 空闲时按 ⌘+回车，等同于普通发送。
- 排队只放在宿主内存里，宿主重启后丢失。

**消息下方的信息**（常驻显示，参考 DeepSeek Harness）：

- 用户消息下方：时间、复制。用户消息超过约 12 行时折叠，末尾"展开"。MVP 1 不做编辑和重发（涉及分叉，和会话树一起做）。
- 回复下方：复制回复、本轮用量（这一轮的输入 + 输出 token）、时间。不做复制整轮、点赞、点踩、分享。

**对话记录的其他设计**（调研 Paseo、Zed、Cursor、Claude 桌面端后确定）

- 提问导航条（Paseo）：消息流右边缘一列细横条，每条对应一次提问，当前所在的加长；悬停放大并预览提问内容，点击跳转。窗口太窄时隐藏。
- 平滑流式输出（Paseo）：增量到达是一阵一阵的，按积压量调节显示速度（约 150ms 内追平），不按到达直接绘制；复制、选择、滚动都以完整文本为准。
- 每轮改动汇总（Claude 桌面端、Zed）：回复下方的信息行加"改了 N 个文件 +A −D"，点开列出文件，点文件展开对应的 diff。由这一轮 edit / write 工具的结果统计，不依赖文件系统面板。语义是"已观测到的工具修改"：`edit` 有增删行，`write` 只列文件（没有旧内容，不编数字），通过 bash 等方式的改动统计不到；多次编辑同一文件是累计编辑量，不是净改动。
- 运行中实时计时：过程标题行显示"进行中 · 12s"。
- 回复的"···"：复制为 Markdown；整个会话"导出为 Markdown"。
- 可选（MVP 1 有余力再做）：⌘F 会话内搜索（高亮命中、上下跳转）；选中回复中的文字后浮出"引用"，插入输入框作为引用块。
- 以后：从某一轮分叉（pi 的 `fork`，和会话树一起做）；检查点与回滚文件（每轮开始前快照，MVP 2 与审批一起）；agent 提出的任务建议卡片（点一下在新 worktree 开会话，需要 extension）；侧聊（不写回主会话的临时提问）。

**运行出错与停止**

- **失败自动重试 3 次，还不行再告诉用户**：
  - 模型调用失败（限流、过载、网络、5xx 等可重试的错误）：交给 pi 自带的重试，宿主启动 pi 时确保自动重试开启、次数为 3（pi 默认 `retry.maxRetries = 3`，指数退避）。重试期间显示一行灰色"正在重试（第 N / 3 次）"。上下文超长由 pi 先压缩再重试一次。
  - pi 进程崩溃：宿主自动重启进程并重新打开会话，最多连续 3 次。崩溃时如果正在运行：上一条输入还没写进会话，就重新提交它；已经写进会话，就补发一条"继续"（界面上标为系统自动发出），让 agent 接着做。
  - 认证失败、目录不存在等重试无用的错误不重试，直接提示。
  - 3 次都失败后，在消息流里显示红色错误卡片：一句话说明，可展开看原始报错，带"重试"按钮；会话进入"出错"，进收件箱。点"重试"按上面同样的规则再来一轮。
- 停止后，写了一半的回复保留，末尾标"已停止"，过程标题行显示"已停止，用时 N"。

**滚动与长会话**

- 停在底部时跟随新内容；向上翻时停止跟随，右下角出现"↓ 回到底部"，有新内容时带一个小圆点。
- 打开会话时先取最近 20 轮（`fetch_transcript` 的 `tail`），往上翻到顶时按游标加载更早的（`before`）；以后需要再做虚拟列表。
- 恢复的历史会话：每轮用时由消息时间戳推算，是近似值；TTFT、输出速度这类只有当场计时才有的数据，宿主存活期间保留，宿主重启后显示"—"。

**回复渲染**：要完整，同时尽量轻。调研了 Paseo（移动端 `react-native-markdown-display`，基于 markdown-it，加 mermaid）、pi 自身（终端里用 marked + highlight.js）、LobeChat / Open WebUI（GFM、代码高亮、KaTeX、Mermaid 齐全），以及专门处理流式输出的库（Streamdown、Incremark、markstream）。

- 采用 Vercel 的 [Streamdown](https://github.com/vercel/streamdown)（Apache-2.0）：react-markdown 的替代品，专为 AI 流式输出设计。
  - 流式：自动补全没写完的语法（未闭合的代码块、加粗），输出途中不闪烁错乱的格式；按块缓存，已经写完的块不重新渲染。
  - 功能拆成按需安装的插件：`@streamdown/code`（Shiki 高亮）、`@streamdown/math`（KaTeX）、`@streamdown/mermaid`、`@streamdown/cjk`。
  - 内置链接和图片的安全限制（rehype-harden）；和 ADR-0005 选定的 Tailwind / shadcn 一致。
- 渲染范围：
  - GFM 全套：标题、列表（含嵌套、任务列表）、引用、表格（横向可滚动）、删除线、脚注、分隔线。
  - 代码块：语言标签、复制按钮、Shiki 高亮，主题跟随浅色 / 深色；`diff` 代码块按增删着色。语言包按需加载。
  - 中文：启用 `@streamdown/cjk`，修正加粗、删除线紧挨中文标点时不生效的问题（例如 `**注意：**后面的文字`）。
  - 数学公式：支持 `$$…$$` 块公式和 `\(…\)` 行内公式；不启用单个 `$`，避免和 shell 变量、价格冲突。KaTeX 第一次遇到公式时才加载。
  - Mermaid：第一次遇到时才加载，渲染成图，可切换看源码，主题跟随浅色 / 深色。
  - 链接：用系统浏览器打开。图片：本地图片和 `https` 远程图片直接显示；`http` 图片不加载，显示为指向它的链接（2026-10-07 定：原先"远程图片点击后才加载"改为直接显示，接受图片地址可能把信息带出去的风险，见 security.md"渲染内容"）。
  - 原始 HTML：不执行，按文本显示。


**输入框**：提示文字为"发消息或描述任务，@ 引用文件，/ 使用命令"；左下角是"+"菜单；右下角是模型选择、发送 / 停止。内边距 14px，底栏与文字区间隔 10px。附件显示成文件卡片或小胶囊。MVP 1 不显示审批相关的标签（工具调用照常直接执行）；MVP 2 加审批模式选择器时再定位置。

- 模型选择按钮：胶囊形，服务商官方图标 + 模型名 + 档位字。档位由 pi 按模型给出（pi 共有 off / minimal / low / medium / high / xhigh / max，各模型支持的不同），界面按实际档位数画格子，常见的四档显示为低 / 中 / 高 / 极高。推理强度由整个按钮的"点阵密度"表达：按钮里铺一层圆角方点（间距 6px），档位越高从左往右铺得越满、越亮，切换时平滑过渡。
  - 拉满（极高）时有专属效果：点阵变成蓝 → 青 → 桃的彩色，带随机明暗（种子与"开始设置"按钮相同，每人不同）和轻微闪烁；每 3.6 秒有一道"\"方向的光从左扫过（约 0.9 秒，先加速后减速）；按钮外圈泛出淡蓝光，档位字变成渐变色。减弱动态效果时只保留静态彩色点阵。
  - 点开在上方弹出面板：上半部分是模型列表，按已登录的服务商分组（组名带官方图标），每行只写模型名和基础数据（上下文、最大输出、是否支持图片），不写介绍；当前模型带对勾，选中即关闭。下半部分是推理强度：一个横向的框（高 38px，每档约 56px 宽，档位多时框跟着变长），框的背景就是点阵，覆盖到第几格就是第几档；框内用细竖线分出档位数，左侧写当前档位名，右侧写"3 / 4"。框在面板里水平居中，下方说明文字也居中。按住框左右拖动，覆盖边缘跟手移动，拉过两端有橡皮筋阻尼；松手后按弹簧动画（response 0.38s、阻尼 0.72，略带回弹）吸附到最近一档；直接点某一格会弹到那一格；←→ 每次一档，到头再按会轻轻顶一下。档位名切换时新字沿拖动方向滑入。拉满时框内变成彩色点阵、带扫光和外圈淡蓝光。下面一句说明当前档位适合什么。调整不关闭面板，按钮上的点阵同步变化。
  - 模型来自 pi 的 `get_available_models`，档位来自 `get_available_thinking_levels`，模型不支持的档位不显示。

- 回车发送，Shift+回车换行。输入法正在组字时（`isComposing`）按回车只是选词，不发送。
- 运行中按钮固定为"停止"；输入框里有字时按回车加入排队；按 Esc 也能停止。
- 每个会话各自保存草稿，切换标签再回来，内容还在。
- 模型：新会话默认用上一次用的模型；会话中途换模型，从下一次请求开始生效。
- `/` 命令：在输入框开头输入 `/` 弹出 pi 的命令列表（`get_commands`：提示词模板、skill、extension 命令），选中后插入输入框。

**第 1 步：安装 pi**

- 找不到 pi：主按钮"安装 pi"，宿主在后台运行 pi 官方安装脚本（`curl -fsSL https://pi.dev/install.sh | sh`），输出实时显示在页面上的终端窗口里（终端高度随输出增长，最多约 7 行，底边有进度线），可以取消；装好后自动进入下一步。官方脚本在没有终端时会跳过所有交互提问，可以直接由宿主运行。
- 缺 Node.js（pi 需要 22.19 以上，安装脚本会先检查）：有 Homebrew 时提供"用 Homebrew 安装 Node.js"（`brew install node`），装好后接着安装 pi；没有 Homebrew 时给出 nodejs.org 的下载链接。
- 版本低于要求：主按钮"更新 pi"，运行 `pi update --self`，同样显示日志。pi 报告"无法自更新这种安装方式"时，退回到手动更新。
- 失败时显示"没有装好"、完整日志和"重试"，并自动展开手动方式。手动方式始终可以展开：安装命令（npm / 安装脚本两种，可复制）、"我装好了，重新检测"、手动选择 pi 的位置。
- 从访达启动的 Electron 拿不到 shell 里的 `PATH`，宿主启动时先从登录 shell 读取 `PATH`，再查找 pi、node、npm、brew。做法（M1.2 实现，2026-10-05 定为取完整环境）：取登录 shell 的**完整环境**，不只是 `PATH`，这样 `.zshrc` 里设的 API Key、代理（`HTTPS_PROXY`）、`NODE_OPTIONS` 在 Atrium 里同样生效，和终端里的 pi 一致；实测取完整环境和只取 `PATH` 一样快，时间都花在 shell 启动上。先用交互式登录 shell（`-i -l -c`，很多人在 `.zshrc` 里设变量），失败或超时（10 秒）再用登录 shell（`-l -c`）；`/usr/bin/env -0` 的输出夹在随机标记之间，rc 文件打印的横幅、回显不影响，值里的换行不会被拆开；shell 自己的 `SHLVL`、`_`、`PWD`、`OLDPWD` 不要。shell 只带宿主的少数变量启动（`HOME`、`USER`、`SHELL`、`TMPDIR`、语言、`SSH_AUTH_SOCK`、`ZDOTDIR`、`PATH`），结果里去掉 `ATRIUM_`、`ELECTRON_` 开头的变量，token 不会进入 pi 的环境。支持 zsh、bash、sh、dash、ksh，其他 shell（fish 等）沿用宿主的环境（同样去掉这两类变量）。读取在宿主开始监听之后于后台进行，不拖慢启动（本机交互式 zsh 要 1～2.6 秒）；只在宿主启动时读一次，之后每个会话的 pi 都用这份环境。环境里可能有密钥，日志只记来源、`PATH` 和变量个数。

### 关键流程

对象和关系见 [领域模型](../architecture/domain-model.md)；以下关于 pi 的行为已对照 pi 1.0.1（提交 `4c6fb7c`）的源码核实。

- **工作区与会话列表**：宿主用 `git worktree list` 列出项目的工作区（本地工作区 + 各 worktree）。pi 的 RPC 没有列出历史会话的命令，宿主直接读 `~/.pi/agent/sessions/--<路径>--/*.jsonl`（Paseo 也是这样做的），按文件头里的 `cwd` 归到对应的容器，从中取会话 id、时间、会话名和第一条用户消息（按"侧栏 · 命名"得出标题）。窗口获得焦点、会话的一次运行结束时重扫，按文件大小和修改时间缓存，只重读变化的文件；不常驻监听会话目录（2026-10-08 定）。会话以 pi 的会话 id 为主键，文件路径只做定位；同一个 id 扫到多个文件时报告冲突。Atrium 自己只保存索引（见"侧栏 · 概念关系"）。
- **新建会话**：pi 创建会话时立即分配 id，但在第一条用户消息之前不写出文件。这期间的会话是"草稿"，只有宿主记得；写出文件后发 `session_bound`。草稿会话记在索引里，宿主重启后照样恢复成空标签（不启动进程，第一次发消息时再启动）；新对话的目录也一直保留，Atrium 不自动清理，用户自己删。
- **恢复会话**：以 `--session <文件>` 启动 pi（一个会话固定一个进程，不用 `switch_session`），用 `get_entries` 取回全部条目，按 `id / parentId` 和 `leafId` 沿当前分支重建对话记录。**不用 `get_messages`**：它返回的是送给模型的上下文，压缩之后旧消息已被摘要替换。之后用 `get_entries(since)` 增量更新，同时单独跟踪 `leafId`（条目没有增加时叶子也可能变）。切换模型、压缩等写入的条目不发事件，所以在 `agent_settled`、`compaction_end` 和宿主自己的命令之后都再取一次。条目 id 只在单个文件内唯一，跨会话用"会话 id + 条目 id"。pi 恢复时使用文件头里的 `cwd`；该目录不存在时报"恢复失败：目录不存在"，不换目录。
- **流式输出**：`message_update` 里的 `text_delta` 和 `thinking_delta` 追加到对应的内容块；`message_end` 到达时，用完整消息替换拼接结果。
- **提交输入**：`prompt` 的回应有三种：`started`（启动了运行）、`queued`（运行中被 pi 排进去）、`handled`（被 extension 命令或输入处理器消费，没有运行）。`handled` 视为这条输入已完成。
- **运行结束**：以 `agent_settled` 为准，而不是 `agent_end`，因为 pi 在 `agent_end` 之后还可能自动重试或压缩。`agent_settled` 只表示"不会再自动继续"，成功、失败、被停止要看实际事件单独判断。
- **运行中继续输入**：宿主维护排队；上一条输入 `handled`，或运行 `agent_settled` 后，依次发出下一条。插话调用 `steer`（见上文"对话区"），pi 的 `queue_update` 每次带完整的内部队列，用来确认插话是否送达。正在压缩时 pi 的 `prompt` 会报错，所以压缩期间暂停出队，`compaction_end` 后再发。出队和停止由同一个会话控制器串行处理。
- **中断**：宿主先暂停出队，再对 pi `clear_queue`、`abort`。否则已经插话、还没送达的消息会让运行继续下去（Paseo 踩过这个坑）。宿主自己的排队保留并暂停，不自动发出。`abort` 2 秒内没确认停下时，会话保持"停止中"，拒绝新的提交和切换模型等操作，直到确认或进程退出，避免宿主和 pi 的状态对不上。
- **进程崩溃**：运行状态回到空闲，排队暂停，已插话但未确认送达的消息退回排队，未回答的对话框作废，记录一条失败，通知界面。重新打开会话时不自动重放结果未知的上一条输入。
- **图片**：粘贴或拖入的图片由客户端压缩后单独上传（见"接口与数据 · 附件"），宿主发消息时转成 base64 放进 pi `prompt` 的 `images` 字段。只有当前模型的 `input` 包含 `image` 时才允许添加图片，否则提示当前模型不支持。文件引用和粘贴内容在发送时展开进 `text`；历史消息里不保证还原成小胶囊。
- **工具卡片**：
  - `bash`：显示命令和输出，输出随 `tool_execution_update` 实时刷新
  - `read`：显示文件路径和行范围
  - `edit`：用结果里的 `details.diff` 显示 diff
  - `write`：显示文件路径和写入的内容（没有旧内容，不显示增删行）
  - 其他工具（包括 MCP 工具）：显示工具名、参数和结果文本
  - 同一批里的工具调用可能并行，每个调用各自显示状态
- **上下文分段**：总量用 `get_session_stats` 的 `contextUsage.tokens`，它可能为空，也可能是 pi 的估算值，为空时显示"—"。系统提示词和工具定义从会话记录还原：pi 在第一次请求时把提示词的各个分段（`sections`）和工具声明（`toolsAdded`）写成一条系统消息，之后的变化也写成系统消息（按名字修改分段、`toolsAdded` / `toolsRemoved`）；压缩条目里存有完整的检查点（`systemMessage`）。宿主沿当前分支回放这些条目，得到当前的提示词和工具集，再按字符数估算 token；对话消息 = 总量 − 系统提示词 − 工具定义。分段数字标"~"。新会话在第一次请求前、以及没有系统消息的旧会话，只显示总量。
- **对话框**：pi 发出 `extension_ui_request` 时，对话框类（`select` / `confirm` / `input` / `editor`）显示为卡片，回答后发 `extension_ui_response`；带超时的显示倒计时。对话框可能出现在一次运行之外，由宿主按会话保存（pi 不把它写进会话文件），所以"问题 → 回答"只在宿主存活期间保留。有未回答对话框的会话不回收进程；多个客户端同时回答，只接受第一个。单向通知类（`notify` 等）保留原文、暂时不显示。
- **在终端中继续**：pi 没有跨进程的写锁，两个进程同时写一个会话会悄悄分叉。所以这是一次交接：Atrium 停止接受该会话的写命令并回收进程，再给出 `pi --session <文件>`；用户回到 Atrium 时重新加载。会话文件被外部改动后怎么提示，等文件区设计时再定；宿主先预留检测（比较文件大小和修改时间）和 `session_changed_externally` 事件。
- **同步与断线重连**（参照 Paseo）：
  - 项目、工作区、会话摘要三个列表各带 `generation`（宿主每次启动生成）和递增的 `seq`。客户端带游标请求，宿主返回快照或增量，之后推送 `upsert / remove`。
  - 会话的对话记录带 `epoch`（进程代次）和 `seq`。客户端只订阅打开着或可见的会话，宿主只给订阅者推增量；按游标分页拉取（最近 / 更早 / 补缺口），`epoch` 变了或有缺口就整段替换。
  - 重连时先对齐三个列表，再对打开着的会话拉最近一页和会话快照（流式中的消息、工具状态、排队、未回答的对话框、指标、关注状态）。
  - 刚发的消息先在本地显示，带 `clientMessageId`；宿主确认后用同一个 id 对上，不重复。
  - 断线不自动重发结果未知的命令。

## 接口与数据

命令和事件的字段随里程碑补全，准绳是 `packages/protocol` 的 zod 定义。

所有会话命令都带 `sessionId` 和客户端生成的 `requestId`；连接上没有隐式的"当前会话"。所有会话事件都带 `sessionId`、`epoch`（进程代次）和 `seq`（会话内单调递增）；列表类事件带 `generation` 和 `seq`。命令落到哪个类，见 [领域模型 · 协议与类的对应](../architecture/domain-model.md#8-协议与类的对应)。

### 协议细节（2026-10-07 定）

zod 定义在 `packages/protocol`，是唯一的准绳；下面的表格是概览。

**信封**（`protocol/src/envelope.ts`）

- 客户端发的每条消息是一个可辨识联合 `ClientMessage`，按 `type` 区分：握手的 `hello`，以及各条命令。宿主发的是 `HostMessage`：`welcome`、`response` 和各种事件。
- 每条命令都带 `requestId`（客户端生成，同一连接内唯一）和 `traceparent`；会话命令再带 `sessionId`。参数和这三个字段平铺在同一层，不另套 `params`。

**应答**

- 每条命令恰好一条应答：`{ type: "response", requestId, ok: true, result? }` 或 `{ type: "response", requestId, ok: false, error: { code, params? } }`。宿主不产出给用户看的文字，界面按 `code` 和 `params` 显示。
- 错误码是 protocol 里的枚举，随里程碑增加。M1.3 用到：`invalid_message`（不是 JSON、不符合 schema）、`unknown_command`、`session_not_found`、`pi_unavailable`（`params.status` 说明原因：`missing` / `outdated` / `unusable` 是检查结果，`exited` 是 pi 已退出，`unresponsive` 是 pi 没有回应）、`session_busy`（pi 正在运行或压缩，不收新消息）、`transcript_changed`（`fetch_transcript`、`fetch_step` 带的 `epoch` 已经过时，M1.4）、`session_cwd_missing`（打开的会话记录的工作目录不存在，M1.4）、`pi_rejected`（pi 拒绝了这条命令，`params.detail` 是 pi 的原文，只供"展开看原始报错"）、`internal_error`（宿主自己的 bug）。pi 的拒绝不算宿主的 bug，不报 `internal_error`。
- `prompt` 不设期限：pi 要做完发送前的准备（可能包括自动压缩）才回应答，可能远超 30 秒；超时会让界面以为没发出，而 pi 照样执行。
- 未知或无效的消息也有应答：能读出 `requestId` 就带上，读不出时为 `null`。限流仍然直接断开（4429）；现在用日志"message ignored"计数的限流测试改成断言应答。
- 原来事件表里的 `error` 不再需要：命令的错误走应答；运行中的失败由 `run_settled` 带出，系统事件走 `notice`。

**握手与心跳**

- `welcome` 带 `protocolVersion`、`hostVersion`、`hostInstanceId`（宿主每次启动随机生成，就是列表同步的 `generation`）和 `heartbeatMs`（15000）。客户端重连后比较 `hostInstanceId`，判断宿主是否重启过。
- 客户端每 `heartbeatMs` 发一条 `ping` 命令，`heartbeatMs` 内没收到应答就当连接已死、断开重连（浏览器察觉不到休眠唤醒后断掉的 TCP）。宿主每 `heartbeatMs` 发一次 WebSocket 协议层的 ping，到下一次时还没收到 pong 就终止连接（浏览器会自动回 pong）。

**事件**

- 会话事件带 `sessionId`、`epoch`、`seq`，以及所属运行的 `traceId`（不在运行中为 `null`）。快照带 `exited`，pi 已退出的会话重连后也显示为已退出。
- 客户端每次连上都比较 `hostInstanceId`：变了说明宿主重启过，之前订阅的会话在新宿主里不存在（宿主重启后的恢复在 M1.4、M1.7）。M1.3 把这些会话的视图标为"已失效"，保留已显示的消息，清掉运行和流式状态，不再订阅；对话界面在已失效或已退出的会话里发消息时，新建一个对话。
- 列表事件带 `collection`（`projects`、`workspaces`、`sessions`）、`generation`、`seq`。

**追踪**：宿主为每条命令开一个 `command <type>` span，父 span 是命令自带的 `traceparent`，再用 span link 指向连接的 trace；不挂在连接那条长 trace 下面，否则一个连接上的所有操作会堆进同一条 trace。

**订阅**：哪个客户端订阅了哪些会话，记在宿主 `sync/` 下的 SubscriptionRegistry（[领域模型 §6、§7](../architecture/domain-model.md#6-宿主的组件)）；连接断开时清掉它的订阅。

**发送端背压**：宿主发消息前看这个连接的 `bufferedAmount`，超过 16 MiB 就以 4507 关闭这个连接，不再往里写。客户端重连后按游标重新对齐（[领域模型 §7](../architecture/domain-model.md#7-客户端与一致性)），所以不需要在宿主为它合并或丢弃增量；一个读得慢的客户端只影响它自己。

**附件**（实现在 M1.6）

- 客户端先压缩：长边缩到不超过 2048 像素（主流模型本来就会把更大的图缩小再看），编码成 WebP；单张压缩后仍超过 1 MiB 时降低质量重试，还不行就提示图片太大。
- 粘贴或拖入时就用 `upload_attachment(mimeType, data)` 单独上传（`data` 是 base64），应答带 `attachmentId`；`prompt` 和 `steer` 只带 `attachmentIds`。每条 WebSocket 消息仍不超过 1 MiB，一次发好几张图也不受影响，发送时也不用再等上传。
- 宿主把上传的图片暂存在内存里，按客户端计：最多 32 MiB、20 张，超出时应答 `attachment_limit`。被 `prompt` / `steer` 用掉、连接断开、或 30 分钟没被用到时释放；消息进了宿主的排队时，图片随排队项保存，不再算在客户端头上。宿主发给 pi 时按 pi 的 RPC 格式放进 `prompt` 的 `images`。

**界面问题上报**：`report_client_issue(kind, message, details?)` 把界面里的未捕获错误和性能问题（长任务、掉帧）写进宿主日志，带客户端 id 和当时的 trace id。`message` 和 `details` 截断到 4 KB，照常脱敏；界面不在里面放对话内容。界面在入口捕获未处理的错误和 Promise 拒绝，并观察超过 50 毫秒的长任务；同一类问题每 10 秒最多报一次，不会触发连接的限流。

**M1.3 先做的部分**

- 命令：`ping`、`create_chat`（最小形态：在 `~/.atrium/chats/` 下建目录，按领域模型"已决定 9"立刻启动 pi；写进索引留到 M1.5）、`subscribe_sessions`、`prompt`（只有文字）、`report_client_issue`。
- 运行中输入框不能发送：宿主的排队和"停止"在 M1.6，这之前运行中发消息只会被 pi 拒绝（`session_busy`）。
- 事件：`session_snapshot`（这次宿主运行中见过的消息；用 `get_entries` 重建历史在 M1.4）、`run_started`、`message_started`、`text_delta`、`reasoning_delta`、`message_finished`、`run_settled`、`session_exited`。
- 只显示文字和推理；工具调用的事件和显示在 M1.4。

### 对话记录（M1.4，2026-10-08 定）

对话区显示的是 TranscriptProjection（[领域模型 §2](../architecture/domain-model.md#2-会话历史条目分支与对话记录)）：宿主沿当前分支把 pi 的条目组织成"轮"和"提示条"，实时事件和分页拉取用同一套实体，M1.3 的消息级事件（`message_started`、`text_delta`、`reasoning_delta`、`message_finished`）由下面的轮级事件取代。

**实体**（`packages/protocol`）

- **轮** `Turn`：一条用户消息到下一条用户消息之间的全部内容。字段：`id`、`user`（文字、图片张数、`clientMessageId`、时间）、`steps`、`outcome`（`running` / `done` / `stopped` / `failed`）、`error`（失败时 pi 的原文）、`startedAt`、`durationMs`（运行中为空；宿主当场看到的轮按宿主计时，只在历史里出现的轮由消息时间戳推算）、`usage`（这一轮所有助手消息的输入、输出 token 之和，没有助手消息时为空）、`changes`（这一轮"已观测到的工具修改"：文件路径和增删行，`write` 没有行数）。
- **步骤** `Step`，按出现顺序：
  - `thinking`：推理文字；`durationMs` 只有当场计时才有，否则为空，界面显示"思考过程"而不是"思考了 N 秒"。
  - `text`：一段文字。只有一轮最后那段文字作为回复显示在过程下方，前面的收进过程（"一轮里的文字"）；哪段是最后一段由界面判断。
  - `tool`：`callId`、`tool`（工具名）、`args`、`status`（`running` / `done` / `failed` / `unfinished`：这一轮结束了还没有结果，比如被中断）、`output`（结果文字；运行中是到此刻为止的输出）、`details`、`partial`（见下面"大内容"）。`details` 按工具区分：`bash`（命令）、`read`（路径、起止行）、`edit`（路径、pi 给的 diff、增删行数）、`write`（路径和写入内容，内容来自调用参数，pi 的结果里没有；`write` 的 `args` 不再带 `content`，内容只发一份）、其他工具没有。
  - `steer`：插话。pi 的文件不记录一条用户消息是插话还是新的一轮（2026-10-08 按 pi 1.0.2 源码核实）。宿主当场看到的用户消息，记下它开启了新的一轮还是插话，运行结束后按顺序对应到新的用户消息条目，重建时以记录为准（M1.5 起存进 `~/.atrium`，宿主重启后仍在）。没有记录的（宿主之外跑的会话、宿主重启前的历史）用推断：紧跟在工具结果之后、下一次模型回复之前的用户消息是插话，属于当前这一轮。这条推断在"一次运行停在工具结果上"（工具要求结束本轮、pi 中途崩溃）时会把下一轮并进来，这种情况少见，接受。
  - `retry`：自动重试（第 N 次、pi 的报错原文），显示成一行灰色"正在重试"。重试发生在一轮中间，所以是步骤，不是提示条。失败的那次回复已经输出的部分（通常没有）照常是前面的步骤，重试步骤跟在后面，所以不会被当成回复；实时事件没有"删除步骤"，这样实时和重建才能一致。第 N 次按 pi 的计法：连续失败一次加一，有一次回复成功就归零；报错原文为空时和 pi 一样写 "Unknown error"。上下文溢出时 pi 屏蔽失败的回复、先压缩再重试，不发自动重试事件，所以也不算重试步骤：被屏蔽的出错回复后面紧跟压缩条目时，只显示压缩提示条。
- **提示条** `Notice`：`compacted`（压缩前 token 数、压缩摘要）。压缩发生在一轮中间时（上下文溢出），提示条放在这一轮之后，不把一轮拆开。

**id**：工具步骤带 pi 的调用 id；步骤的 `id` 是它在轮里的序号（从 `"0"` 起的十进制字符串）：一条助手消息的第 i 块是这条消息开始时已有步骤数 + i，实时和重建按同样的规则排出同样的序号。轮的 `id` 在实时时由宿主生成；运行结束后宿主重新读条目，按顺序把新的用户消息条目对应到实时的轮，沿用实时的 id。只在历史里出现的轮用"会话 id + 条目 id"。

**实时事件**（都带 `sessionId + epoch + seq + traceId`）：

- `turn_started(turn)`：pi 回显开启一轮的用户消息时，带整条轮（`outcome: running`，还没有步骤）。
- `step_added(turnId, step)`：推理、文字块开始时（文字为空）；工具调用在调用块写完时，带完整参数；插话、重试出现时。
- `step_delta(turnId, stepId, delta)`：推理、文字的增量。
- `step_updated(turnId, step)`：带整个步骤。助手消息结束时，与已发的不同的步骤各发一次；工具有了实时输出、结果时；一轮结束时还在运行的工具改为 `unfinished`。
- `turn_finished(turnId, outcome, error, durationMs, usage, changes)`：运行结束（`agent_settled`）时，在 `run_settled` 之前。pi 在运行中退出时，这一轮的结果是 `failed`（`error` 为空）；之后打开这个会话，文件里看不出崩溃，同一轮显示为 `stopped`。
- `notice_added(notice, before)`：见下面"快照与分页"的重建。`before` 是插在哪一条之前（轮或提示条的 id），为空表示放在最后。压缩发生在运行中，或在新消息开始前（pi 在 `prompt` 里先压缩），提示条在运行结束后才出现。
- `run_started`、`run_settled`、`session_exited` 不变。

**快照与分页**

- `session_snapshot` 带最近 20 轮（连同其间的提示条）、`hasOlder`、运行状态和 `exited`。打开会话订阅后一条消息就能画出首屏。快照和分页还受大小限制（4 MB）：装不下 20 轮时少带几轮（至少一轮），其余的留给翻页。
- `fetch_transcript(sessionId, before, limit)`：取某一条（轮或提示条）之前的 `limit` 条，返回条目和 `hasOlder`，带当前 `epoch`；`epoch` 已经变了就应答 `transcript_changed`，客户端改为重新订阅取快照。
- 运行结束、压缩结束、宿主自己发出改变状态的命令之后，宿主用 `get_entries(since)` 补齐条目并重建（运行中不重建，等这次运行结束）。重建结果和已推给客户端的完全一致就什么都不推；只是多了提示条（不论在哪里），就逐条推 `notice_added`，带插入位置；其余情况（例如当前分支变了、实时漏了什么），`epoch` 加一并给订阅者推新的快照。

**大内容**（2026-10-08 定）：内容不截断、不丢。工具步骤里的长文字（输出、`write` 的内容、`edit` 的 diff、参数里的长字符串）各自超过 16 KB 时，事件、快照和分页里只带一段预览（`bash` 的输出取结尾，其他取开头），步骤标 `partial: true`；界面展开这一步时用 `fetch_step(sessionId, epoch, turnId, stepId)` 取回完整的步骤。宿主内存里和重建比较用的都是完整内容。`epoch` 变了同样应答 `transcript_changed`。

**当场计时的数据**：轮的用时、推理用时由宿主在实时事件里测得，连同轮的实时 id、`clientMessageId` 和它开启新一轮还是插话，按轮另外存放，重建时合并回去，所以正常运行后重建结果和实时推过的一致；宿主重启后为空（"滚动与长会话"）。首 token 时间、输出速度只在状态栏显示，和状态栏一起在 M1.6 做（2026-10-08 定）。

**打开历史会话**（M1.4 的临时入口，M1.5 由侧栏和"历史"取代，见下一节）：没有打开会话时，对话区列出 pi 会话目录里最近的会话（第一条提问、时间）。`list_recent_sessions(limit)` 返回会话 id、文件里的第一条提问、修改时间；`open_session(sessionId)` 用 `pi --session <文件>` 在会话记录的工作目录里启动 pi 并返回，客户端随后订阅；工作目录不存在时应答 `session_cwd_missing`（`params.cwd`），界面显示"恢复失败：目录不存在"。扫描会话目录是 pi 包的 SessionFiles，只读，按 LF 分行，和读 pi 的 RPC 输出用同一个分帧（pi-internals §3）。

### 项目、工作区与会话（M1.5，2026-10-08 定）

侧栏、标签栏和"历史"显示的是宿主推来的一份完整列表（[领域模型 · 已决定 11](../architecture/domain-model.md#已决定)）。M1.5 只发快照：客户端订阅后先收到一份，之后索引、扫描结果或会话的运行状态一有变化，宿主合并一下再推一份完整的。M1.7 再加增量和游标。M1.4 的临时入口 `list_recent_sessions` 和"最近会话"列表随之删掉。

**实体**（`packages/protocol`）

- **项目** `Project`：`id`（`prj_…`）、`path`（解析过符号链接的真实路径）、`name`。
- **工作区** `Workspace`：`id`（`wks_…`）、`projectId`、`kind`（`local` / `worktree`）、`dir`、`alias`（自定义名称，没有为空）、`branch`（检出的分支；detached HEAD 或不是 git 仓库时为空）、`head`（detached 时的短 commit 号）、`external`（不是 Atrium 建的 worktree）、`createdAt`（worktree 的创建时间，本地工作区为空）、`merge`（合并状态，本地工作区和非 git 项目为空）。名称由界面按 `alias ?? branch ?? 目录名` 得出。
- **合并状态** `MergeState`：`dirty`、`ahead`、`verdict`（`noChange` / `pending` / `merged` / `removed` / `unknown`）、`reason`（`unknown` 的原因：`git_too_old`、`no_main_branch`、`git_failed`、`base_unknown`）。主干只认项目的覆盖值或 `origin/HEAD`，没有就是 `unknown`（`no_main_branch`），不猜本地分支（2026-10-08 定）。
- **会话摘要** `SessionSummary`：`sessionId`、`containerId`（工作区 id，或对话的 `chats`）、`name`（pi 的会话名）、`prompt`（第一条用户消息的第一行，去掉 Markdown 符号和首尾空白，最多 200 个字符；没有文字为空）、`file`（会话文件路径，还没写出时为空）、`state`（`draft` / `persisted` / `missing`）、`updatedAt`、`archived`、`running`。标题由界面按 `name ?? prompt` 得出，都为空时草稿显示"新会话"，否则显示"图片"。
- **布局** `Layout`（只给这个客户端自己的）：`container`（当前所在的工作区或 `chats`，没有为空）、`tabs`（每个容器打开着的会话和当前标签）。
- **偏好** `Preferences`：`appearance`（`system` / `light` / `dark`）、`displayMode`（摘要 / 思考 / 详细，从 M1.4 的 localStorage 挪到宿主，所有客户端一致）。

**事件**：`index_snapshot(generation, seq, projects, workspaces, sessions, layout, preferences, resets)`。`generation` 是宿主实例 id，`seq` 每推一次加一。`resets` 列出这次宿主启动时因损坏被重置的索引文件（领域模型 §1"索引的存储"），界面提示一次。

**命令**

- `subscribe_index()`：订阅列表，宿主马上推一份快照，之后有变化就推。连接断开即退订。
- 订阅一个已写出文件、但 pi 还没启动的会话时，宿主先记下订阅，pi 启动（由 `open_session` 或第一次 `prompt` 触发）后再发快照，不拒绝；客户端拿到列表后，对当前标签先 `open_session` 再订阅（2026-10-08 审查后补）。
- `add_project(path)`：登记项目，返回 `projectId`。不是目录应答 `path_not_found`；已经是某个项目或其工作区时应答 `project_exists`（`params.projectId`）；名称和已有项目重复时自动加序号，如 `app (1)`。选的是某个仓库的 worktree（不是主工作树）时，登记的是主工作树所在的仓库，这个 worktree 作为它的一个工作区出现（2026-10-08 定）。同时添加的几个目录依次处理。
- `remove_project(projectId)` / `rename_project(projectId, name)`：移除只删索引，同时停掉其中会话的 pi、从各客户端的布局里去掉；改成已有项目的名字应答 `name_taken`。
- `rename_workspace(workspaceId, name | null)`：`null` 恢复为分支名。
- `window_focused()`：窗口获得焦点，宿主重扫工作区、合并状态和会话文件。
- `create_session(workspaceId)` / `create_chat()`：新建草稿会话并立刻启动 pi（领域模型"已决定 9"，2026-10-08 定工作区里的新会话也一样），打开成这个客户端的标签并激活，返回 `sessionId`。
- `open_session(sessionId)`：打开成标签并激活，切到它所在的容器；pi 没在运行就用 `--session <文件>` 启动。宿主重启后恢复的草稿不启动，第一次 `prompt` 时才用 `--session-id <id>` 启动（"已决定 7"）。
- `close_tab(sessionId)`：只改这个客户端的布局。关掉的是还没发过消息的草稿时，丢弃它：停掉 pi、删掉索引里的记录，对话的空目录一并删掉（只删空的）（2026-10-08 定）。
- 同一个客户端改标签和位置的命令（`open_session`、`close_tab`、`select_container`，以及新建后打开标签）按收到的顺序生效：`open_session` 要等第一次扫描，扫描期间关掉的标签不会在扫描结束后又被打开（2026-10-08 修）。
- `select_container(containerId | null)`：切换工作区或"对话"。
- `archive_session(sessionId)`：只改索引；停掉它的 pi，从各客户端的布局里去掉。
- `rename_session(sessionId, name)`：用 pi 的 `set_session_name` 写回；pi 没在运行就先启动。草稿不能改名，应答 `session_is_draft`，界面上"重命名"置灰（2026-10-08 定）。
- `set_preferences(appearance?, displayMode?)`。

新增错误码：`project_not_found`、`workspace_not_found`、`project_exists`、`name_taken`、`path_not_found`、`session_is_draft`。

**扫描**：工作区用 `git worktree list --porcelain`，同时最多跑 4 个 git 命令。会话只扫已登记的容器对应的 pi 会话目录（按 pi 的规则由工作目录得出目录名），再按文件头的 `cwd` 核对；按文件大小和修改时间缓存，文件只增长时只读新增的部分（会话名取最新一条 `session_info`）。同一个 id 出现在多个文件时取最新的，日志记一条冲突。

**收件箱**挪到 M1.7，和关注状态一起做（2026-10-08 定）：它收的"待回答、待授权、出错未看"要到 M1.6、M1.7 才有，为空时本来就整块不显示。

## 备选方案

| 方案 | 为什么不用 |
|---|---|
| SDK 嵌入 pi | 见 ADR-0002，放弃进程隔离 |
| Atrium 自己保存对话记录 | 和 pi 的会话文件重复，两份数据会不一致；对话历史归 pi（见 [架构总览](../architecture/overview.md)） |

## 风险与待定问题

- [ ] **没有审批的风险**：agent 可能误删文件或执行危险命令。缓解：MVP 1 只在 git 仓库里使用，出问题用 git 回滚。
- [x] **pi 适配器用 pi 自带的 `RpcClient`，还是自己实现 JSONL 客户端**：自己实现（2026-10-04 定，对照 pi 1.0.1 的 `rpc-client.ts`）。`RpcClient` 没有发送 `extension_ui_response` 的方法（`send()` 是私有的），做不了需求 10；它还写死了 `node <cli.js>` 的启动方式、每条命令 30 秒超时（`compact` 会超）、无限增长的 stderr，并要依赖整个 `pi-coding-agent` 包。自己实现约 300 行：直接启动 `pi --mode rpc`，按命令设超时，stderr 只留最近一段、其余写日志，退出时先关 stdin、再 SIGTERM，最后连同所有后代的进程组一起 SIGKILL（2026-10-04 实测后细化，见 pi-internals §3"退出"）；分帧照搬 pi 的 `jsonl.ts`（MIT，只按 LF 切行）；类型用 `import type` 从固定版本的 pi 包取，只在开发时安装。Paseo 也是自己实现。
- [x] **包管理器**：pnpm workspaces。
- [x] **UI 组件库和状态管理**：组件用 shadcn；`client` 用 Zustand 的 `zustand/vanilla`（2026-10-04 定）：约 1KB、不依赖 React 和 DOM，UI 用 `useStore(store, selector)` 订阅。按领域拆 store：列表（项目、工作区、会话摘要）、每个会话一个（订阅时创建、退订时释放）、布局；流式增量只复制当前那条消息，其他轮次引用不变；选择器返回对象时用 `useShallow`；不引入 Immer。备选里自己写 store 要重做选择器和 devtools，MobX / Valtio 的可变代理不利于按序号整段替换，Jotai 围绕 React 设计，Signals 接 React 不顺。
- [ ] **pi 版本兼容**：会话文件格式和 RPC 都可能变化。宿主启动时检查 pi 版本，低于最低版本就提示升级。
