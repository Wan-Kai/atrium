# SPEC-0001：MVP 1 纯对话

- **状态**：已确认
- **创建**：2026-09-30
- **更新**：2026-10-04
- **相关**：[路线图](../roadmap.md) 阶段 1 第 1 步、[ADR-0002](../adr/0002-connect-pi-via-rpc-subprocess.md)、[ADR-0005](../adr/0005-split-host-and-ui-pwa-first.md)、[ADR-0006](../adr/0006-organize-sessions-by-workspace.md)、[领域模型](../architecture/domain-model.md)、[设计语言](../architecture/design-language.md)

## 背景与目标

Atrium 的第一个可用版本。它要回答一个问题：**在 Atrium 里用 pi 加 Codex 模型，能不能完成日常的真实编码任务？** 如果不能，整条路线都要调整，所以越早知道越好。

同时，它会把 ADR-0005 定下的架构从头到尾打通一遍：Electron → UI → WebSocket → 宿主 → pi RPC。后面的 MVP 都在这个骨架上叠加。

完成后：你可以在 Atrium 里打开一个项目、和 pi 对话写代码，并且能看清它做了什么。

## 非目标

- Atrium 自己的 extension：审批、上下文检查器都放到 MVP 2。但用户自己安装的 pi extension 弹出的对话框必须能显示和回答（需求 10），否则会话会卡住
- 审批：沿用 pi 的默认行为，工具调用直接执行
- 新建和清理 worktree（MVP 1 只识别已有的 worktree）
- 浏览器操作的专门界面（通过 pi 的 `mcp.json` 配置 MCP server 即可使用）
- 插件系统、会话树、分叉
- 打包、签名、自动更新；手机端和 PWA；多窗口
- 文件系统相关：审查面板、文件路径操作（用编辑器打开、在 Finder 中显示等）
- 系统通知
- 订阅额度（5 小时、每周用量）：不在对话面板里显示

## 需求

1. 当我打开 Atrium，我希望在侧栏看到各个项目和其下的工作区（本地目录或 worktree），一眼看出哪些在运行、哪些在等我处理、哪些 worktree 还没合并；在对话区顶部用标签页切换同一工作区里的会话（见下文"侧栏""对话区"）。
2. 当我新建会话并输入需求，我希望看到流式输出的回复和推理过程。
3. 当我粘贴或拖入一张截图，我希望它随消息一起发给模型。
4. 当 agent 调用工具，我希望看到它做了什么：执行的命令和输出、读了哪个文件、改动的 diff、新写入的文件。
5. 当 agent 走偏了，我希望随时中断它。
6. 当 agent 还在运行时，我希望继续输入的消息默认排队；需要时点一下，就能让它在 agent 下一步之前送达（插话）。
7. 当我想换模型或调整推理强度，我希望在输入框旁边直接切换。
8. 当我关掉 Atrium 再打开，我希望恢复之前的会话继续聊。
9. 我希望在输入框下方的状态栏随时看到上下文用量、缓存命中率、token 用量、输出速度，并能选择显示哪些指标。
10. 当我自己安装的 pi extension 弹出对话框提问时，我希望在 Atrium 里看到并回答它。
11. 我希望对话默认只突出回复，过程折叠起来；需要时能切换显示模式，查看推理过程或每一步的细节。
12. 当一个会话在跑时，我希望切去看别的会话、甚至开新会话，它在后台继续跑。
13. 第一次打开 Atrium 时，我希望被引导装好 pi、登录模型、添加项目。
14. 我希望能复制一条消息或一条回复。

## 方案设计

### 进程与启动

```
Electron 主进程
  ├── 启动宿主（Node 子进程），生成随机 token，宿主监听 127.0.0.1 的随机端口
  └── 窗口加载宿主提供的 UI，并通过 preload 把地址和 token 交给 UI

宿主
  └── 每个活动的会话 → 一个 pi 子进程：pi --mode rpc [--session <文件>]，工作目录为工作区目录（对话为它自己的目录）
```

- 多个会话可以同时运行，切走不中断。MVP 1 不回收空闲进程（与 Paseo 一致）：会话打开后 pi 进程常驻，直到归档、交给终端、宿主退出或进程崩溃；宿主重启后会话处于"未启动"，打开时再以 `--session` 启动。会话多了再加回收。
- pi 进程意外退出时，宿主通知 UI，用户可以一键重新打开这个会话。

### 各包职责

| 包 | MVP 1 要做的 |
|---|---|
| `protocol` | 用 zod 定义下文的命令和事件 |
| `client` | WebSocket 连接（带 token、断线重连）、收发协议消息、维护会话状态：消息列表、流式拼接、运行状态、用量 |
| `host` | WebSocket 服务和鉴权；项目和会话列表；pi 适配器：启动和监督进程，把 pi 事件翻译成 Atrium 事件 |
| `ui` | 界面，见下文 |
| `apps/desktop` | 启动宿主、创建窗口、preload 传 token |

### 界面

```
┌──────────────┬──────────────────────────────────────────┐
│ 侧栏          │ 对话区：标题栏 / 消息流 / 排队 / 输入框       │
│ 收件箱        │                                          │
│ 项目 → 会话    │ 状态栏（输入框正下方，居中）                 │
└──────────────┴──────────────────────────────────────────┘
```

- **视觉**：以 DeepSeek Harness 的产品界面为基准，逐个组件实测后对齐（系统字体、半透明侧栏与主区贴合、14px 常规字重为主、0.5px 细线、圆角 8 / 12 / 16 / 22）。
- **图标**：Hugeicons 免费版的 stroke-rounded，线宽 1.75（2026-10-12 由 Phosphor 换成，更圆润；细则见 design-language "图标"）；状态图标是纯线性图标，只给图标上色，不加底色。
- **动效**：以 Apple 为基准，用弹簧（时长 + 回弹）而不是固定时长的缓动；按下立即反馈、展开收起有高度过渡、位置变化用位移过渡；遵从系统的"减弱动态效果"。
- **外观**：跟随系统 / 浅色 / 深色三档，记住选择，系统外观变化时自动跟随；深色贴近 DeepSeek Harness，浅色按同样的层级关系推导。
- 完整页面原型：`prototypes/app-prototype.html`。设计规范（变量、组件、动效参数）见 [设计语言](../architecture/design-language.md)。
- 本 spec 引用的原型（`prototypes/` 下的侧栏、对话区、图标对比、完整页面）按"用完即弃"的约定保存在 `prototype/ui` 分支，不进 `main`。

### 侧栏

参考 Paseo 的工作区模型，侧栏按"项目 → 工作区"组织，会话放在工作区里，以对话区顶部的标签页呈现（见"对话区"）；另有不绑定工作区的"对话"。尺寸和样式按 DeepSeek Harness 对齐（宽 270、行高 34、14px）。原型讨论过程中先后比较过"会话平铺 + 彩色 git 图标 + worktree 折叠区"等方案（`prototypes/sidebar-prototype.html`），最终改为工作区模型：会话属于哪个 worktree 从靠颜色对应变成结构上的包含，合并状态直接挂在工作区上。

**概念关系**

```
项目（一个 git 仓库或目录）
 ├── 本地工作区（项目目录本身，每个项目一个）
 └── worktree 工作区（每个 worktree 一个，含不是 Atrium 创建的"外部" worktree）
      │  工作区与目录一一对应
      └── 会话（目录下的 pi 会话文件）
           ├── 打开着的 → 对话区顶部的标签页
           └── 全部 → "历史"菜单
对话（不绑定项目和工作区，⌘N 新建；2026-10-12 改，ADR-0007）
 │  每个对话一个空目录 ~/.atrium/chats/<目录名>/，宿主按目录认出它们；没有 git
 └── 会话（和工作区一样：打开着的是标签页，全部在"历史"里）
```

- 工作区和目录一一对应：pi 按工作目录保存会话，宿主按会话的工作目录把它归到对应的工作区，没有歧义。以后确实需要多个工作区共用一个目录（按任务分组）时再放开。
- MVP 1 的工作区：每个项目自动有一个本地工作区；`git worktree list` 识别出的每个 worktree 是一个工作区。新建 worktree 工作区、归档并清理 worktree 放到阶段 1 第 3 步。
- 对话用于和项目无关的提问。pi 必须有工作目录，所以每个对话给一个独立的空目录，agent 写的文件互不干扰；"移到某个项目"以后再做。一个对话就是一个没有 git 的工作空间，和工作区一样可以有多个会话，以后要打开的浏览器页面等内容也放在对话里，所以各个对话互不相干，不挤在一起（2026-10-12 改，原先所有对话是一个容器里的标签页）。
- Atrium 只保存索引：项目列表（目录、显示名）；工作区（所属项目、本地或 worktree、目录、分支、自定义名称、创建时的起点提交、是否外部、是否归档）；对话的自定义名称；每个工作区和对话打开着哪些标签页、当前是哪一个；会话的归档状态、出错是否已看过。不保存对话内容。

**收件箱**

- 只放"等你处理"和"出错"的会话，跨所有项目和对话汇总，按状态优先级、再按时间排序。第一行是会话标题和最近活动时间，第二行是"项目 · 工作区"，对话写"对话 · 对话名"。
- 最多显示 5 条，其余收成"还有 N 条"，点击展开；展开后末尾是"收起"。
- 点击：切到会话所在的工作区或对话，没打开的会话补开一个标签页并激活。收件箱行和工作区（或对话）行同时高亮：一个表示正在看的会话，一个表示所在的工作区。工作区所在的项目是收起的，不自动展开，项目行带上选中底色。
- 离开收件箱：待审批、待回答、待授权要等问题解决（看一眼不算）；出错的会话打开过即算已看过，移出收件箱，但标签页和工作区行上的出错图标保留，直到下一次运行开始。
- 不单独设"运行中"分区。

**搜索**

- 点"项目"标题右侧的搜索按钮，搜索框在原位展开；搜索框和它上面的内容（新建对话、收件箱、"项目"标题）都不动，项目列表和"对话"换成搜索结果。
- 结果分三组：工作区（名称 + 所属项目 + 合并状态）、对话（名称 + 时间）、会话（与收件箱同样的两行格式，包含对话里的会话）。点击工作区或对话切过去；点击会话打开它。
- 匹配工作区名、对话名和会话标题；全文搜索以后再做。清空或关闭搜索框，恢复项目列表。

**项目与工作区**

- 项目可折叠。项目行：文件夹图标、名称；悬停出现"+"（新建工作区）；收起时，右侧显示待合并的 worktree 数和其中会话的最高优先级状态。展开时不显示待合并数，下面每个工作区都能看到。
- 工作区在项目下缩进显示，不放图标，名称和项目名对齐。本地工作区排第一；其余 worktree 按创建时间倒序，位置稳定，不因为 agent 跑完一轮而跳动；已合并、已移除的变淡、排在最后。
- 工作区行：名称、合并状态、行尾是其中会话的最高优先级状态（空闲时不显示）。"本地""外部"不单独标注，只在悬停提示里说明。合并状态是纯文字标签、不加底框：未提交、待合并前面有橙色小圆点，`↑N`（圆头上箭头图标加数字）用橙色加粗，`✓ 已合并`（合并图标加文字）用绿色，已移除用最淡的灰色。
- 点击工作区：切过去，恢复它上次激活的标签页；没有打开的会话时显示这个工作区的空状态。
- 悬停 worktree 工作区出现"查看改动 / 合并"（未合并时）或"清理"（已合并时），阶段 1 第 3 步实现；MVP 1 只读显示合并状态。
- "···"菜单：重命名；在访达中显示；归档工作区并清理 worktree（阶段 1 第 3 步）。

**对话**

每个对话和工作区一样是一个容器（2026-10-12 改，[ADR-0007](../adr/0007-each-chat-is-its-own-container.md)）：

- 侧栏底部的"对话"分区像工作区一样逐行列出对话：名称、最近活动时间（其中会话最近的一次）、会话的最高优先级状态（空闲时不显示），按最近活动排列。显示最近 5 个，其余的点"显示全部 N 个"在原地展开，展开后末尾是"收起"。所有会话都归档了的对话不列出。
- 点击对话：切过去，恢复它上次激活的标签页；没有打开着的标签页时打开它最近的会话（对话不像工作区那样常有空状态，点进去应当看到内容）。对话行在所在的对话被选中时高亮，和工作区行一样。
- 选中对话时，对话区顶部的标签页是这个对话打开着的会话，"历史"列出这个对话的全部会话；标签栏的"+"（⌘T）在这个对话里新建会话，以对话的目录为工作目录。新对话用侧栏的"新建对话"或 ⌘N。
- 标签栏的"+"在当前所在的地方新建：在工作区里就是这个工作区的会话，在对话里就是这个对话的会话，哪里都不在时新建对话。
- "···"菜单：重命名。
- 以后对话里要打开的浏览器页面等内容也作为这个对话的标签页。

**命名**

- 项目名：默认取目录名，可以重命名。添加的目录与已有项目同名时，自动在后面加序号，如 `app (1)`，并提示可以重命名；手动重命名成已有的名字时，提示重名、不保存。
- 工作区名：默认是分支名，跟着分支变化。本地工作区取项目目录当前检出的分支（不一定是 `main`）；worktree 取它检出的分支；处于 detached HEAD 时用目录名，悬停显示短 commit 号；项目不是 git 仓库时，本地工作区用目录名。
- 对话名：默认取第一个会话（最早建的、没归档的）的标题，第一个会话还是草稿时显示"新对话"；可以重命名，自定义名称存在 Atrium 的索引里，清空即恢复默认（2026-10-12 定）。
- 工作区可以重命名：自定义名称只存在 Atrium 的索引里，不改 git 分支名；改过名的工作区悬停时显示分支名；名称清空即恢复为分支名。
- 会话标题，按以下顺序取第一个有值的：
  1. pi 的会话名：手动重命名和模型生成的标题都写在这里（`set_session_name`），终端 pi 也能看到。
  2. 兜底标题：第一条用户消息的第一行，去掉 Markdown 符号和首尾空白，过长由界面省略；只有图片时显示"图片"。兜底标题只用于显示，不写回 pi。
- 自动生成标题：会话（含对话）的第一轮运行结束（`agent_settled`）时，如果会话还没有名字，宿主用一次性调用让模型起一个短标题（与用户消息同语言，中文不超过 16 个字，不带标点和引号），写回 pi 的会话名，替换掉兜底标题；标签页、收件箱、"历史"同步更新。
  - 输入：第一条用户消息和第一条回复的开头，截断到约 2000 字符。
  - 调用：`pi --mode json -p --no-session`，默认用当前会话的模型，设置里可以指定一个更便宜的模型。
  - 已经有名字的会话不再生成，因此不会覆盖手动重命名；生成过程中用户手动改了名，丢弃生成结果。
  - 失败时保留兜底标题，在下一轮运行结束时再试一次。
  - 没在 Atrium 里跑过的历史会话（比如终端 pi 里开的）不批量补生成，仍显示兜底标题。
- 在终端 pi 里开的会话同样显示，不区分来源。

**worktree 合并状态**：和会话状态是两个维度。会话状态回答"agent 需不需要我"，合并状态回答"这批改动收尾了没有"。

| 状态 | 判断 | 显示 |
|---|---|---|
| 有未提交的改动 | worktree 内 `git status` 不干净 | `• 未提交` |
| 有未合并的提交 | 未判定为已合并，且分支比主干多 N 个提交 | `↑N`（悬停说明"未合并"） |
| 无改动 | 干净，且分支还停在起点（见下文） | 不显示标签，不变淡 |
| 已合并 | 干净，分支离开过起点，且已进入主干（见下文） | `✓ 已合并`，变淡，提供"清理"入口（阶段 1 第 3 步） |
| 已移除 | worktree 目录不存在（`git worktree list` 标为 prunable） | `已移除`，变淡 |
| 无法判断 | 没有主干分支、git 低于 2.38、git 出错、外部 worktree 看不出起点 | 最淡的 `状态未知`，悬停说明原因；未提交仍照常显示（2026-10-08 定） |

- 主干默认取 `origin/HEAD` 指向的分支，每个项目可以单独修改。比较对象用远程分支（如 `origin/main`），宿主在后台定期 `git fetch`（窗口获得焦点时、每隔几分钟），因为合并常在 GitHub 上完成，本地 `main` 可能还没更新。只 fetch 本身是仓库顶层的项目：放在别的仓库里的普通目录不会去 fetch 外面那个仓库。
- 判断已合并，按顺序：
  1. 分支已在主干历史中（`git merge-base --is-ancestor`）→ 已合并。覆盖普通 merge 和快进。
  2. 否则用 `git merge-tree --write-tree <主干> <分支>` 模拟合并（不改工作区和 index，但会在仓库里创建 git 对象），结果与主干的 tree 相同 → 已合并。覆盖 squash、rebase、cherry-pick；主干之后改了别处不影响判断；主干回滚了该改动则判为未合并。模拟合并有冲突，一律视为未合并。需要 git 2.38 以上。
- 区分"无改动"和"已合并"：刚建好的 worktree 分支天然在主干历史里，只看第 1 步会误判为已合并。Atrium 新建 worktree 时记下起点提交；分支最新提交仍等于起点 → 无改动，离开过起点后又进入主干 → 已合并。外部 worktree 没有记录起点，看分支的 reflog 里有没有过它自己的提交：`commit`、`cherry-pick`、`revert`、`am` 写下的提交，以及 `merge`、`pull` 做出的合并提交（`am` 和 `pull` 2026-10-09 补上）；只是快进、建分支、切换的不算。
- 计算时机：不持续监听文件。对相关的 worktree 重算：其中的会话一次运行结束时、窗口获得焦点时、后台 `git fetch` 之后（只重算 `↑N` 和已合并，不跑 `git status`）。已合并的判断结果按"分支提交 + 主干提交"缓存；同时最多跑 4 个 git 命令。
- 成本：`git status` 最贵（大仓库可能几百毫秒），其余都是毫秒级。
- 不提示"搁置多久"。

**会话状态**：一个会话同时满足多个状态时，按下表从上到下取第一个；工作区行、项目行（收起时）显示其中会话的最高优先级状态。图标是纯线性图标、只给图标上色，不加底色；不同状态用不同的形状或动画区分，不只靠颜色；悬停显示具体原因。

### 对话区

已定稿（原型 `prototypes/app-prototype.html`，在 `prototype/ui` 分支）。

调研了 Claude Code 桌面端、Codex 桌面端、Paseo、Cursor、Zed，共同方向是：**突出结果，折叠过程；运行中的输入可以排队或插话**。MVP 1 只做纯对话能力，审查面板、文件路径操作放到以后。

经原型讨论（`prototypes/conversation-prototype.html` 方案 A）确定采用"过程折叠条"：跑完后过程收成一行摘要，点击展开；没有采用时间线、轮次卡片两种结构。

2026-10-12 改为"过程轨道"（`prototypes/process-rail-prototype.html`，参考 Phil Pitus 的 [Thinking process](https://x.com/pitus_/status/2109282877506777206)）：展开后的过程是一条竖线串起的步骤，进行中的、走不通的、插话各有自己的节点；跑完后仍收成一行摘要，并且是看得见的折叠动效，不再一跑完就消失。原来否决的"时间线"是每一步都常驻展开的流水账；轨道只在运行中和点开时出现，"突出结果，折叠过程"不变。

**标签栏**（对话区顶部）

- 显示当前工作区"打开着的"会话，每个标签是一个会话：标题、非空闲时的状态图标、关闭按钮。关闭标签只是收起，会话保留在"历史"里。
- "+"在当前工作区或对话里新建会话（哪里都不在时新建对话）；"历史 ⌄"列出这个工作区或对话的全部会话（状态、时间、是否已打开），点击即在标签页中打开。
- 右侧是显示模式和"···"：重命名、归档、复制会话文件路径、在终端中继续（交接给终端：Atrium 先停止并释放这个会话，再复制 `pi --session <文件>`，见"关键流程"）。
- 标签多了先压缩到最小宽度（约 96px），再放不下就横向滚动，两端渐隐提示还有更多。
- 快捷键：⌘T 在当前工作区或对话里新建会话，⌘W 关闭标签，⌘1–9 切到第几个，⌘⇧[ / ⌘⇧] 切到上一个 / 下一个。
- 会话可以在后台运行：切换标签、切换工作区、关闭标签都不会中断它，状态显示在侧栏、收件箱和"历史"里。每个会话本来就是独立的 pi 进程，多个会话可以同时运行；要停下，打开它点"停止"。
- 工作区没有打开的会话时，对话区显示空状态，直接在输入框里输入就会新建会话：输入第一个字时就新建，pi 的启动藏在打字里，已经打的字留在新会话的输入框里（2026-10-11 定）。空状态（以及新会话、新对话的空状态）的布局待设计，先用占位。
- 以后的"对话 / 轨迹"是单个会话内部的视图切换，和会话标签页不冲突，放在对话区里另找位置（MVP 2）。

**显示模式**（参考 Claude Code）：摘要（默认）/ 思考 / 详细，用 Ctrl+O 切换，全局记住选择。入口是标签栏右侧的"👁 摘要模式 ⌄"。

| 内容 | 运行时 | 跑完后（摘要模式） |
|---|---|---|
| 推理过程 | 实时显示（"思考中"） | 折叠成"思考了 N 秒"；思考模式下展开 |
| 只读操作（读文件、搜索、列目录） | 连续的几个合并成一行，如"正在探索代码库 · 读了 3 个文件"，做完是"探索了代码库 · 读了 5 个文件，搜索了 2 次"；下面一排读过的文件胶囊，最多 5 个，多的写"+N 个" | 收进过程摘要 |
| 命令（bash） | 一行"正在运行 命令"，做完是"运行了 命令"，右侧显示通过 / 失败；详情块里实时滚动输出。失败的命令画成从主线岔出去的死路（见"过程的呈现"） | 收进过程摘要；有失败的命令时，标题行末尾加灰色的"N 条命令没走通"，不单独展开（agent 常常会自己修好，标红、展开都太吵；2026-10-12 由红色的"N 条命令失败"改） |
| 文件改动（edit / write） | 一行"正在编辑 文件"，做完是"编辑了 文件 +N −M"或"写入了 文件"，文件以胶囊显示；详情块里显示 diff（`edit` 用 `details.diff`），带行号和增删竖条 | 收进过程摘要，展开可看 diff |
| 插话 | 从旁边汇入主线的一行"你插话 · 内容" | 保留在标题行下方 |
| 系统事件（上下文压缩、自动重试） | 一行灰色提示，压缩时带压缩前的 token 数 | 保留 |
| 对话框（待回答、待授权） | 消息流底部的卡片，直接在卡片上作答 | 显示你的回答 |

详细模式下所有步骤都展开。

**一轮里的文字**：agent 在一轮里常常说好几段话（"我先看看现有实现…"），中间穿插工具调用。只有最后一段作为回复显示在过程下方；前面几段作为文字步骤收进过程里，展开能看到。一轮里没有任何步骤时不显示过程行；只有推理时显示"思考了 N 秒"。

**过程的呈现**（过程轨道，2026-10-12 定，原型 `prototypes/process-rail-prototype.html`；尺寸、颜色、动效见 [design-language · 消息流](../architecture/design-language.md#消息流)）：

- 等待回复（2026-10-11 定，自用时发现发出后到第一个字之间没有任何表示）：从发出消息起，到这一轮有东西可显示（推理、步骤或回复的第一个字）之前，消息下方显示"进行中"行：眨眼的小猫（Atrium 的标志）+ 扫光的"进行中" + 计时（宿主报告运行开始后才有）。运行中已经有这一轮时，消息进排队，不显示。第一个步骤到了，这一行原地成为过程的标题行；没有过程的轮，回复一出来这一行就去掉。小猫站在轨道的位置上，和下面的节点对齐。
- 标题行：运行时轨道位置是眨眼的小猫，后面是扫光的"进行中 · 12s"；跑完后小猫换成折叠箭头（展开时 ⌄，收起时 ›），文字是"已完成，用时 N"，收起时后面接"· 读了 … · 跑了 … · 改了 …"；被中断是"已停止，用时 N"。
- 轨道：左侧一条细竖线把步骤串起来，每一步一个节点，节点上下和竖线之间留一点缝。做完的一步是灰色小圆点，探索行是放大镜；进行中的一步是蓝点外一圈转动的弧，文字扫光、说"正在…"，做完后弧收进圆点、文字换成过去时。一轮中间说的话（文字步骤）只显示话本身。新的一步出现时节点弹出、文字从下方淡入。
- 走不通的一步：失败的工具调用从主线岔到右边一格，一段虚线弯过去，节点是 ×，文字变灰；主线在旁边接着往下。
- 插话：从右边一格汇入主线，节点是蓝色空心圆，文字"你插话"是蓝色。
- 完成行：跑完时轨道末端多一行：完成是蓝色实心勾"完成"，后面灰字"改了 N 个文件 +A −D · N 条命令没走通"（没有的部分不写）；停止是"已停止"，出错是"出错了"。
- 跑完后的折叠（2026-10-12 定）：摘要模式下，一轮当场跑完时，轨道先停在展开状态让人看到"完成"，1 秒后折叠进标题行：高度平滑收拢，各行从下往上依次淡出上移，箭头从 ⌄ 转到 ›，标题行末尾的摘要淡入；下方的回复跟着平滑上移，不跳。点标题行展开时反向播放。打开会话时已经跑完的轮直接是收起的，不播动画；详细模式不折叠；减弱动态效果时直接切换。
- 点击某一步，在它下方的深色详情块里显示内容（左上标"输出 / 改动"，右上标工具名），竖线在详情块旁边接着往下。不做成卡片。

**运行中输入：默认排队，可插话**

- 按回车：agent 空闲时直接发送；运行中进入排队。⌘+回车：直接插话。
- 排队中的消息收在输入框上方的胶囊条里（见"输入框"），可以编辑、删除、点"插话"。
- 插话调用 pi 的 `steer`：在 agent 当前这批工具调用执行完、下一次请求模型之前送达，不是立刻打断。界面上标注"下一步前送达"；要立刻停下用"停止"。
- 排队由宿主管理，不使用 pi 的 `follow_up` 队列：本次运行结束（`agent_settled`），或上一条输入被 extension 直接处理（`handled`）后，宿主依次把下一条作为 `prompt` 发出。这样编辑、删除、调整顺序都由 Atrium 控制。
- 停止后，排队暂停、不自动发出，由你决定继续发送还是清掉。
- 空闲时按 ⌘+回车，等同于普通发送。
- 排队只放在宿主内存里，宿主重启后丢失。

**消息下方的信息**（常驻显示，参考 DeepSeek Harness）：

- 用户消息下方：时间、复制。用户消息超过约 12 行时折叠，末尾"展开"。MVP 1 不做编辑和重发（涉及分叉，和会话树一起做）。
- 回复下方：复制回复、本轮用量（这一轮的输入 + 输出 token）、时间。复制的是回复的 Markdown 原文，只有这一个复制，不另设"···"菜单（2026-10-12 定，原先复制显示的纯文字、"···"里再放"复制为 Markdown"，两个复制重复）。不做复制整轮、点赞、点踩、分享。

**对话记录的其他设计**（调研 Paseo、Zed、Cursor、Claude 桌面端后确定）

- 提问导航条（Paseo）：消息流右边缘一列细横条，每条对应一次提问，当前所在的加长；悬停放大并预览提问内容，点击跳转。窗口太窄时隐藏。
- 平滑流式输出（Paseo）：增量到达是一阵一阵的，按积压量调节显示速度（约 150ms 内追平），不按到达直接绘制；复制、选择、滚动都以完整文本为准。
- 每轮改动汇总（Claude 桌面端、Zed）：回复下方的信息行加"改了 N 个文件 +A −D"，点开列出文件，点文件展开对应的 diff。由这一轮 edit / write 工具的结果统计，不依赖文件系统面板。语义是"已观测到的工具修改"：`edit` 有增删行，`write` 只列文件（没有旧内容，不编数字），通过 bash 等方式的改动统计不到；多次编辑同一文件是累计编辑量，不是净改动。
- 运行中实时计时：过程标题行显示"进行中 · 12s"。
- 整个会话"导出为 Markdown"。
- 可选（MVP 1 有余力再做）：⌘F 会话内搜索（高亮命中、上下跳转）；选中回复中的文字后浮出"引用"，插入输入框作为引用块。
- 以后：从某一轮分叉（pi 的 `fork`，和会话树一起做）；检查点与回滚文件（每轮开始前快照，MVP 2 与审批一起）；agent 提出的任务建议卡片（点一下在新 worktree 开会话，需要 extension）；侧聊（不写回主会话的临时提问）。

**运行出错与停止**

- **失败自动重试 3 次，还不行再告诉用户**：
  - 模型调用失败（限流、过载、网络、5xx 等可重试的错误）：交给 pi 自带的重试，宿主启动 pi 时确保自动重试开启；次数沿用 pi 的设置（默认 `retry.maxRetries = 3`，指数退避，2026-10-09 定：RPC 改不了次数）。重试期间显示一行灰色"正在重试（第 N / M 次）"，M 是 pi 给的上限。上下文超长由 pi 先压缩再重试一次。
  - pi 进程崩溃：宿主自动重启进程并重新打开会话，最多连续 3 次；一次运行正常结束（`agent_settled` 且没有失败）后连续计数归零（2026-10-09 定）。崩溃时如果正在运行：上一条输入还没写进会话，就重新提交它；已经写进会话，就补发一条"继续"（界面上标为系统自动发出），让 agent 接着做。
  - 认证失败、目录不存在等重试无用的错误不重试，直接提示。
  - 3 次都失败后，在消息流里显示红色错误卡片：一句话说明，可展开看原始报错，带"重试"按钮；会话进入"出错"，进收件箱。点"重试"按上面同样的规则再来一轮。
- 停止后，写了一半的回复保留，末尾标"已停止"，过程标题行显示"已停止，用时 N"。

**滚动与长会话**

- 停在底部时跟随新内容；向上翻时停止跟随，右下角出现"↓ 回到底部"，有新内容时带一个小圆点。
- 打开会话时先取最近 20 轮（`fetch_transcript` 的 `tail`），往上翻到顶时按游标加载更早的（`before`）；以后需要再做虚拟列表。
- 恢复的历史会话：每轮用时由消息时间戳推算，是近似值；TTFT、输出速度这类只有当场计时才有的数据，宿主存活期间保留，宿主重启后显示"—"。

**回复渲染**：要完整，同时尽量轻。调研了 Paseo（移动端 `react-native-markdown-display`，基于 markdown-it，加 mermaid）、pi 自身（终端里用 marked + highlight.js）、LobeChat / Open WebUI（GFM、代码高亮、KaTeX、Mermaid 齐全），以及专门处理流式输出的库（Streamdown、Incremark、markstream）。

- 采用 Vercel 的 [Streamdown](https://github.com/vercel/streamdown)（Apache-2.0）：react-markdown 的替代品，专为 AI 流式输出设计。
  - 流式：自动补全没写完的语法（未闭合的代码块、加粗），输出途中不闪烁错乱的格式；按块缓存，已经写完的块不重新渲染。
  - 功能拆成按需安装的插件：`@streamdown/code`（Shiki 高亮）、`@streamdown/math`（KaTeX）、`@streamdown/mermaid`、`@streamdown/cjk`。
  - 内置链接和图片的安全限制（rehype-harden）；和 ADR-0005 选定的 Tailwind / shadcn 一致。
- 渲染范围：
  - GFM 全套：标题、列表（含嵌套、任务列表）、引用、表格（横向可滚动）、删除线、脚注、分隔线。
  - 代码块：语言标签、复制按钮、Shiki 高亮，主题跟随浅色 / 深色；`diff` 代码块按增删着色。语言包按需加载。
  - 中文：启用 `@streamdown/cjk`，修正加粗、删除线紧挨中文标点时不生效的问题（例如 `**注意：**后面的文字`）。
  - 数学公式：支持 `$$…$$` 块公式和 `\(…\)` 行内公式；不启用单个 `$`，避免和 shell 变量、价格冲突。KaTeX 第一次遇到公式时才加载。
  - Mermaid：第一次遇到时才加载，渲染成图，可切换看源码，主题跟随浅色 / 深色。
  - 链接：用系统浏览器打开。图片：本地图片和 `https` 远程图片直接显示；`http` 图片不加载，显示为指向它的链接（2026-10-07 定：原先"远程图片点击后才加载"改为直接显示，接受图片地址可能把信息带出去的风险，见 security.md"渲染内容"）。
  - 原始 HTML：不执行，按文本显示。

**第 1 步：安装 pi**

- 找不到 pi：主按钮"安装 pi"，宿主在后台运行 pi 官方安装脚本（`curl -fsSL https://pi.dev/install.sh | sh`），输出实时显示在页面上的终端窗口里（终端高度随输出增长，最多约 7 行，底边有进度线；开始前显示要运行的命令），可以取消；pi 一变成可用就自动进入下一步，不停在"pi 已就绪"。从后面的步骤返回到第 1 步时，pi 已可用就显示"pi 已就绪"、版本和位置，点"继续"前进（2026-10-11 定）。官方脚本在没有终端时会跳过所有交互提问，可以直接由宿主运行。
- 缺 Node.js（pi 需要 22.19 以上，安装脚本会先检查）：有 Homebrew 时提供"用 Homebrew 安装 Node.js"（`brew install node`），装好后接着安装 pi；没有 Homebrew 时主按钮是"去 nodejs.org 下载"，装好后点"我已经装好了"重新检测。上方用两枚小标签说明缺什么、找到了什么（"Node.js 22.19+ 未找到"或"Node.js x 太旧"，"Homebrew 已安装"或"没有 Homebrew"）。只有这个窗口发起的 Node 安装成功后才接着安装 pi，接着的这次安装同样显示在这一步的终端里（2026-10-11 定）。Homebrew 不在登录 shell 的 `PATH` 上（刚装好 Homebrew、还没把 `brew shellenv` 写进配置）时，宿主把它所在的目录加到工具环境的 `PATH` 末尾，装好的 Node 才找得到、接着安装 pi 时也用得上（2026-10-11 定）。
- 版本低于要求：主按钮"更新 pi"，运行 `pi update`，同样显示日志。pi 报告"无法自更新这种安装方式"时，退回到手动更新。
- 找到的 pi 不能运行（`broken`）：和找不到一样重新安装，标题"pi 运行不了"，pi 自己的报错放在默认收起的"展开看原始报错"里（2026-10-11 定）。
- 失败时显示"没有装好"、完整日志和"重试"，说明按原因区分：下载不了安装脚本（多半是网络问题）、启动不了、被中途结束、退出码 N。宿主拒绝开始时（`install_busy`、`install_unavailable`）在下方说明原因。
- 手动方式始终显示在终端下面，不用展开（2026-10-11 定）：安装命令（安装脚本 / npm 两种，可切换、可复制；更新时是 `pi update`，装 Node 时是 `brew install node`），底栏的"我已经装好了"（更新时"我已经更新了"）用 `check_setup(refresh)` 重新检测，还是没有时提示"还是没找到（还是旧版本），可能要重开终端"。任务跑完了但重新检测后还是找不到能用的 pi（或 Node.js），提示可能要重开终端，并给"重新检测"。手动选择 pi 的位置暂不做（2026-10-11，待确认）。
- 从访达启动的 Electron 拿不到 shell 里的 `PATH`，宿主启动时先从登录 shell 读取 `PATH`，再查找 pi、node、npm、brew。做法（M1.2 实现，2026-10-05 定为取完整环境）：取登录 shell 的**完整环境**，不只是 `PATH`，这样 `.zshrc` 里设的 API Key、代理（`HTTPS_PROXY`）、`NODE_OPTIONS` 在 Atrium 里同样生效，和终端里的 pi 一致；实测取完整环境和只取 `PATH` 一样快，时间都花在 shell 启动上。先用交互式登录 shell（`-i -l -c`，很多人在 `.zshrc` 里设变量），失败或超时（10 秒）再用登录 shell（`-l -c`）；`/usr/bin/env -0` 的输出夹在随机标记之间，rc 文件打印的横幅、回显不影响，值里的换行不会被拆开；shell 自己的 `SHLVL`、`_`、`PWD`、`OLDPWD` 不要。shell 只带宿主的少数变量启动（`HOME`、`USER`、`SHELL`、`TMPDIR`、语言、`SSH_AUTH_SOCK`、`ZDOTDIR`、`PATH`），结果里去掉 `ATRIUM_`、`ELECTRON_` 开头的变量，token 不会进入 pi 的环境。支持 zsh、bash、sh、dash、ksh，其他 shell（fish 等）沿用宿主的环境（同样去掉这两类变量）。读取在宿主开始监听之后于后台进行，不拖慢启动（本机交互式 zsh 要 1～2.6 秒）；宿主启动时读一次，之后每个会话的 pi 都用这份环境；首次启动装好 pi 或 Node 后（`check_setup(refresh)`）再读一次，之后启动的 pi 用新的这份（2026-10-10 定）；日志的脱敏只增不减，旧环境里的密钥仍然脱敏，因为已经在跑的 pi 还拿着它们（2026-10-11 定）。环境里可能有密钥，日志只记来源、`PATH` 和变量个数。代理变量（`HTTPS_PROXY` 等）可以在设置里换掉（见"设置 · pi"的网络代理）；宿主自己发出的请求（查 pi 的最新版本、下载安装脚本）也按这份环境里的代理变量走，和 pi 一致（2026-10-11 定，原先宿主自己的请求不走代理，代理环境下查不到最新版本）。

**第 2 步：登录模型**

- 标题下有"用订阅登录 / 使用 API Key"切换。
- 订阅登录是一张分组列表，每行：官方图标（白底圆角）、名称与说明、右侧"登录"。顺序：ChatGPT（Plus / Pro，可用 Codex 模型；pi 的 `openai`）、Claude（Pro / Max）、GitHub Copilot、Kimi Code、Grok（SuperGrok / X Premium）、OpenRouter、Meta（Muse 订阅），以 pi 支持的为准：pi 没有的不显示，pi 以后新增的、带 OAuth 的服务商排在后面自动出现（名称用 pi 给的 `loginLabel` 或 `name`，图标用通用图标）。不显示 pi 标为 legacy 的 `openai-codex` 和要先配网关的 `radius`（2026-10-10 定）。
- 点"登录"后这一行描蓝边，显示"在浏览器中完成登录"和"取消"，宿主用系统浏览器打开 pi 给的授权地址（只接受 `https`）；完成后显示"✓ 已登录"。至少登录一个，"继续"才可用。登录过程中 pi 要问的其他内容在这一行下面展开：
  - 登录方式：自动选浏览器登录（pi 的 `browser`），不问用户。
  - 浏览器在别的机器上：一个默认收起的"粘贴回调地址"输入框（pi 的 `manual_code`），和本机的回调同时等，哪个先到用哪个。
  - 设备码（`device_code`）：显示码、"复制"和"打开验证页"。
  - pi 的其他提问（如 GitHub Copilot 的企业域名）：按 pi 给的文字显示一个输入框或选择框；文字是 pi 的原文（英文），宿主不翻译。
- API Key：选择服务商、粘贴 Key、保存，附"去哪里获取 API Key"链接；说明 Key 只写在本机的 `~/.pi/agent/auth.json`。服务商列表、保存走 pi 的 API Key 登录（同上，pi 还要问别的，比如账户 id，就接着问）。
- 凭据写在 pi 里，终端里的 pi 也能用。pi 的 RPC 没有登录命令，没有可用模型时 RPC 模式只给一个占位模型（2026-10-10 实测）。**登录调用用户装的 pi**（2026-10-10 验证并定，见 [pi-internals](../research/pi-internals.md) §4"从外部调用 pi 的登录"）：宿主用系统 Node（pi 用的那个）运行 `packages/pi` 里的登录程序，它 `import` 用户装的 pi 包里的 `ModelRuntime`，查各家的登录状态、走 OAuth 和 API Key 登录、退出，凭据由 pi 在锁下写进 `auth.json`；和宿主之间按行传 JSON，Key 走标准输入。OpenAI 要的设备 ID 用 pi 自己的（`~/.pi/agent/settings.json` 的 `deviceId`），和终端里的 pi 是同一台设备。版本和终端里的 pi 一致，Atrium 不另带一份 pi。取消登录时停掉登录程序，回调端口随之释放。
- 登录程序加载不了 pi（例如 Nix 装的、pi 的接口变了）：这一步显示"在终端运行 `pi`，输入 `/login`"（命令可复制）和"我登录好了，重新检测"。这时 Atrium 判断不了终端里是否登录成功，"继续"始终可用（2026-10-11 定）。
- 图标一律用各家官方资源，来源记录在 `prototypes/brand/SOURCES.md`；发布前按各家品牌规范核对用法。

**接口**（2026-10-10 定，M1.10）：

- `check_setup(refresh?)`：应答 `SetupState`：
  - `pi`：`{ state: missing | broken | outdated | ready, path, version, minimum }`，`broken` 带 pi 自己的报错原文；
  - `node`：`{ state: missing | outdated | ready, version }`（要求 22.19 以上）；`homebrew`、`fd`：找到与否；
  - `login`：`{ state: unavailable }`（登录程序加载不了 pi，或 pi 不可用）或 `{ state: ready, providers }`，每个服务商：`providerId`、`name`（pi 给的原文）、`oauth`（`{ label, subscription } | null`）、`apiKey`（能否存 Key）、`signedIn`（`{ method: oauth | api_key, stored } | null`，`stored` 为假表示 Key 来自环境变量）；只列 SPEC 上面定的订阅服务商、pi 新增的带 OAuth 的服务商，以及能存 Key 的服务商；
  - `projects`：已添加的项目数。
  - `refresh` 为真时先重新读取登录 shell 的环境（装好 pi、Node 后 shell 配置文件可能改了 `PATH`），之后启动的 pi 都用新环境。
- `install_pi()` / `install_node()` / `update_pi()`：应答 `{ jobId }`，同一时刻只有一个安装任务，已有任务时应答 `install_busy`；缺少任务要用的工具时应答 `install_unavailable`（还没检测到工具；装 Node 时没有 Homebrew；更新时找不到 pi）。
  - 安装 pi：宿主从写死的地址下载官方脚本（`https`，不跟随到别的域名；30 秒、1 MiB 为限），交给 `/bin/sh -s` 的标准输入运行，不经过 shell 拼接命令；没有终端，脚本跳过所有提问。
  - 安装 Node：运行找到的 `brew install node`。
  - 更新 pi：运行 `pi update`（`--self` 是它的别名）；有会话在运行时先处于 `waiting`，等都结束再开始。更新进行中（`running`）要启动 pi 的会话等它结束；更新成功后宿主停掉空闲会话的 pi（会话收到 `session_exited`，`reason` 为 `requested`），界面下次发送时照常重新打开会话，用新版本启动；运行中的会话、有未回答对话框的会话不动。正在启动的 pi 先等它起来再判断，免得用旧版本起来的漏掉（2026-10-11 定）。
  - 任务成功后，宿主先重新检测工具（同 `check_setup(refresh)`），再报告 `ok`，界面之后用 `check_setup()` 即可拿到新结果。
  - 任务用登录 shell 的环境运行，自成进程组，取消时结束整棵进程树（先 SIGTERM 整个进程组，3 秒不走再强制结束）。任务没有时限。
- `cancel_install(jobId)`：`jobId` 不是进行中的任务时应答 `install_not_found`。
- 事件 `install_updated { jobId, kind, state, running, exitCode, reason }`：`kind` 为 `install_pi | install_node | update_pi`；`state` 为 `waiting | running | ok | failed | cancelled`；`waiting` 时 `running` 是还在运行的会话数，其他时候为 `null`；`failed` 带 `reason`：`exit`（`exitCode` 为退出码，被信号结束时为 `null`）、`download_failed`（下载脚本失败）、`spawn_failed`（启动不了），其他状态 `reason`、`exitCode` 为 `null`。每次变化整份推送给所有连接。
- 连接建立后（`welcome` 之后），宿主把进行中的、或最后一个结束的安装任务和登录推给这个连接（`install_updated`、`login_updated`，输出不补发），断线期间结束的任务和登录界面也能看到结果；界面换了宿主实例时先清掉旧实例的（2026-10-11 定）。
- 事件 `install_output { jobId, text }`：输出原文（标准输出和标准错误合在一起），按块推送给所有连接；颜色和"\r"覆盖由界面处理。输出不进日志，日志只记任务种类、结果和退出码。
- `login(providerId, method, key?)`：应答 `{ loginId }`。同一时刻只有一个登录，新的登录先取消进行中的，等它的登录程序退出（回调端口释放）再开始；登录不可用时不取消进行中的（2026-10-11 定）。`key` 只在 `api_key` 时给，交给 pi 的第一个密码类提问。登录不可用（`check_setup` 的 `login` 为 `unavailable`）时应答 `login_unavailable`。
- `answer_login(loginId, promptId, value)` / `cancel_login(loginId)`：`loginId` 不是进行中的登录时应答 `login_not_found`；回答已经撤回的提问时丢掉。`logout(providerId)`：pi 拒绝或超时时应答 `logout_failed`（`reason`，`detail` 为 pi 的原文）；正在登录同一个服务商时，先取消那个登录、等它退出再退出，免得两个程序先后写 `auth.json`、后写的盖掉先写的（2026-10-11 定）。
- 事件 `credentials_changed {}`：登录成功、退出登录后推给所有连接（退出时在应答之前），界面收到后重新问 `check_setup`，并重新加载已经加载过的模型列表；别的窗口这样才知道凭据变了（"最后一个能用的凭据"的确认、生成标题用的模型列表靠它，2026-10-11 定）。
- 事件 `login_updated`：登录的完整状态，每次变化整份推送给所有连接：`loginId`、`providerId`、`method`、`state`（`running | ok | failed | cancelled`）、`authUrl`（`{ url, instructions } | null`，只放 `https` 的，其他的地址让登录以 `failed` 结束、`reason` 为 `insecure_url`）、`deviceCode`（`{ userCode, verificationUri, expiresInSeconds } | null`，`verificationUri` 同样只放 `https` 的）、`questions`（pi 正在问的：`promptId`、`kind`、`message`、`placeholder`、`options`）、`progress`（pi 最近一条进度或提示文字，提示里的链接不带）、`error`（`{ reason: unavailable | failed | timed_out | insecure_url, detail } | null`，`detail` 为 pi 的原文）。只有发起登录的那个客户端打开授权地址。日志只记服务商、方式和结果，不记 Key、地址、提问和 pi 的原文。pi 的原文（`detail`、`progress`、提问的文字、`authUrl` 的说明，以及 `check_setup` 里 `broken` 的报错）超过协议上限（16 KiB）时宿主截断，整条消息不会因为过长被丢掉（2026-10-11 定）。
- `discover_projects()`：应答 `{ directories }`，pi 历史会话里出现过的工作目录，每个 `{ path, sessions, lastUsedAt }`（会话数、其中最近一次修改的时间，毫秒），去掉已添加的项目和它们的工作区（`add_project` 会应答 `project_exists` 的）、Atrium 对话目录下的和已经不存在的目录，按最近使用排列。宿主在 pi 存会话的位置（和侧栏找会话同一个，见 pi-internals §1）只读每个会话文件的第一行（文件头里的 `cwd`），按工作目录分的文件夹里有符号链接时和 pi 一样跟进去（2026-10-11 定），`path` 是解析符号链接后的真实路径，指向同一目录的合在一起。还没检测到工具时应答空列表。添加用已有的 `add_project`。
- 握手的 `welcome` 带 `installSeed`：本机安装 ID（`~/.atrium/install-id`，第一次启动时生成的 UUID）算出的正整数，欢迎页按钮和模型按钮拉满时的点阵都用它。界面原先存在 `localStorage` 里的种子不再使用。

  - 位置（"在访达中显示"）、当前版本、最新版本、上次检查和"检查更新"按钮。
  - 有新版本时显示"更新 pi"，刚更新过、之后又查到更新的版本也一样（2026-10-11 定）；侧栏的"设置"按钮和"pi"分类上各有一个蓝色小圆点，不弹窗、不打断。
  - 更新过程：有会话在运行时显示"等待 N 个会话运行结束"（可取消）；更新中显示终端输出和进度，可取消；失败显示完整输出和"重试"；完成后显示"已更新到 x.y.z"，可查看日志。更新期间新开的会话等更新完成再启动 pi。
  - "手动更新"折叠项：可复制的 `pi update` 和"我更新好了，重新检测"。
  - 网络代理（2026-10-11 定，参考 Paseo 给服务商设环境变量的做法）：代理地址（如 `http://127.0.0.1:7897`）和"不走代理的地址"（逗号或换行分隔，如 `.anthropic.com`），"保存"和"不用代理"。设了之后，宿主交给 pi（会话、列模型、版本检查）、登录、安装和更新的环境里，`HTTPS_PROXY`、`HTTP_PROXY`（及小写）都是这个地址，`NO_PROXY`（及小写）是 `localhost,127.0.0.1,::1` 加上填的列表，取代登录 shell 里的同名变量；宿主自己查最新版本、下载安装脚本也走它。已经在跑的 pi 不受影响，下次启动时生效，组下面说明这一点。没设时沿用登录 shell 的代理变量。只接受 `http://`、`https://` 的地址，只有主机和端口，不能带用户名和密码（会进 pi 的环境，日志的脱敏也认不出来）；不接受时在输入框下说明原因。
- **关于**：Atrium 版本、与宿主的连接（"已连接"，或正在重连等）、pi 版本、日志文件夹（"在访达中显示"）。

**接口**（2026-10-10 定，M1.10）：

- 偏好和 `set_preferences` 多了 `titleModel`（`{ providerId, modelId } | null`，`null` 为跟随会话的模型，M1.10 之前的偏好文件读作 `null`）和 `setupDone`（见"首次启动 · 什么时候显示"）。
- 偏好和 `set_preferences` 多了 `proxy`（`{ url, noProxy } | null`，`null` 为不设，之前的偏好文件读作 `null`；2026-10-11 定）。宿主不接受的应答 `proxy_invalid`，`params.reason` 说明原因：`malformed`（不是地址，或除主机和端口外还有路径、查询）、`scheme`（不是 `http` / `https`）、`credentials`（带用户名或密码）、`no_proxy`（"不走代理"里有空项，或带空白、逗号）。日志只记代理来自设置、登录 shell 还是没有，不记地址。
- `set_main_branch(projectId, branch | null)`：应答 `{}`；`null` 恢复自动；`branch` 必须是 `origin` 上存在的分支，否则应答 `branch_not_found`（`params.branch`）。改了之后宿主重新扫描这个项目的工作区（合并状态），正在显示的改动重新计算。
- `list_branches(projectId)`：应答 `{ branches, head }`：`branches` 是 `origin` 上的分支名（不带 `origin/`，去掉 `HEAD`，按名字排列），供主干下拉用；`head` 是 `origin/HEAD` 指向的分支，"自动"旁边显示它，没有时为 `null`。不是 git 仓库或没有 git 时两者都为空（2026-10-11 定）。
- 列表里的项目多了 `mainBranch`：用户选的主干，`null` 为自动（2026-10-11 定）。
- `check_setup` 的 `pi` 多了 `latest`（npm 上的最新版本）和 `checkedAt`（查到它的时间，毫秒）：从没查到时都为 `null`，之后某次没查到保留上次的结果。宿主启动后和之后每天查一次；`check_pi_update()` 立刻查（同时只查一次），应答 `{ latest, checkedAt }`。每次查到用事件 `pi_latest { latest, checkedAt }` 推给所有客户端。宿主在 `check_setup` 查完登录状态后才取 `latest`；界面以 `checkedAt` 较新的为准，`check_setup` 还没答复时收到的 `pi_latest` 也留着（2026-10-11 定）。查的是 pi 自己检查新版本用的 `https://pi.dev/api/latest-version`（返回 npm 上的版本和包名，10 秒为限），和终端里的 pi 看到的一致；pi 的环境里设了 `PI_OFFLINE` 时不查（2026-10-11 定）。日志只记查到的版本或没查到的原因。
- 握手的 `welcome` 多了 `logDir`。"在访达中显示"走桌面壳的 `reveal(path)`，只接受存在的绝对路径。

### 关键流程

对象和关系见 [领域模型](../architecture/domain-model.md)；以下关于 pi 的行为已对照 pi 1.0.1（提交 `4c6fb7c`）的源码核实。

- **工作区与会话列表**：宿主用 `git worktree list` 列出项目的工作区（本地工作区 + 各 worktree）。pi 的 RPC 没有列出历史会话的命令，宿主直接读 `~/.pi/agent/sessions/--<路径>--/*.jsonl`（Paseo 也是这样做的），按文件头里的 `cwd` 归到对应的容器，从中取会话 id、时间、会话名和第一条用户消息（按"侧栏 · 命名"得出标题）。窗口获得焦点、会话的一次运行结束时重扫，按文件大小和修改时间缓存，只重读变化的文件；不常驻监听会话目录（2026-10-08 定）。会话以 pi 的会话 id 为主键，文件路径只做定位；同一个 id 扫到多个文件时报告冲突。Atrium 自己只保存索引（见"侧栏 · 概念关系"）。
- **新建会话**：宿主新建时生成会话 id，pi 用 `--session-id` 启动后沿用它（2026-10-11 改，原先用 pi 自己分配的 id），但在第一条用户消息之前不写出文件。这期间的会话是"草稿"，只有宿主记得。pi 报出第一条用户消息时文件已经写出（它先发事件、同一时刻接着写盘，pi-internals §1），宿主这时扫一次会话目录，草稿变成会话，列表经 `index_changes` 更新，运行还没结束标签就显示第一条消息（2026-10-10 定，取代原先打算的 `session_bound` 事件）；没扫到的，运行结束后的那次扫描再补上。草稿会话记在索引里，宿主重启后照样恢复成空标签（不启动进程，第一次发消息时再启动）；新对话的目录也一直保留，Atrium 不自动清理，用户自己删。
- **恢复会话**：以 `--session <文件>` 启动 pi（一个会话固定一个进程，不用 `switch_session`），用 `get_entries` 取回全部条目，按 `id / parentId` 和 `leafId` 沿当前分支重建对话记录。**不用 `get_messages`**：它返回的是送给模型的上下文，压缩之后旧消息已被摘要替换。之后用 `get_entries(since)` 增量更新，同时单独跟踪 `leafId`（条目没有增加时叶子也可能变）。切换模型、压缩等写入的条目不发事件，所以在 `agent_settled`、`compaction_end` 和宿主自己的命令之后都再取一次。条目 id 只在单个文件内唯一，跨会话用"会话 id + 条目 id"。pi 恢复时使用文件头里的 `cwd`；该目录不存在时报"恢复失败：目录不存在"，不换目录。
- **流式输出**：`message_update` 里的 `text_delta` 和 `thinking_delta` 追加到对应的内容块；`message_end` 到达时，用完整消息替换拼接结果。
- **提交输入**：`prompt` 的回应有三种：`started`（启动了运行）、`queued`（运行中被 pi 排进去）、`handled`（被 extension 命令或输入处理器消费，没有运行）。`handled` 视为这条输入已完成。
- **运行结束**：以 `agent_settled` 为准，而不是 `agent_end`，因为 pi 在 `agent_end` 之后还可能自动重试或压缩。`agent_settled` 只表示"不会再自动继续"，成功、失败、被停止要看实际事件单独判断。
- **运行中继续输入**：宿主维护排队；上一条输入 `handled`，或运行 `agent_settled` 后，依次发出下一条。插话调用 `steer`（见上文"对话区"），pi 的 `queue_update` 每次带完整的内部队列，用来确认插话是否送达。正在压缩时 pi 的 `prompt` 会报错，所以压缩期间暂停出队，`compaction_end` 后再发。出队和停止由同一个会话控制器串行处理。
- **中断**：宿主先暂停出队，再对 pi `clear_queue`、`abort`。否则已经插话、还没送达的消息会让运行继续下去（Paseo 踩过这个坑）。宿主自己的排队保留并暂停，不自动发出。`abort` 2 秒内没确认停下时，会话保持"停止中"，拒绝新的提交和切换模型等操作，直到确认或进程退出，避免宿主和 pi 的状态对不上。不设上限，也不提供"强制结束"（2026-10-09 定）。
- **进程崩溃**：运行状态回到空闲，排队暂停，已插话但未确认送达的消息退回排队，未回答的对话框作废，记录一条失败，通知界面。重新打开会话时不自动重放结果未知的上一条输入。
- **图片**：粘贴或拖入的图片由客户端压缩后单独上传（见"接口与数据 · 附件"），宿主发消息时转成 base64 放进 pi `prompt` 的 `images` 字段。只有当前模型的 `input` 包含 `image` 时才允许添加图片，否则提示当前模型不支持。文件引用和粘贴内容在发送时展开进 `text`；历史消息里不保证还原成小胶囊。
- **工具卡片**：
  - `bash`：显示命令和输出，输出随 `tool_execution_update` 实时刷新
  - `read`：显示文件路径和行范围
  - `edit`：用结果里的 `details.diff` 显示 diff
  - `write`：显示文件路径和写入的内容（没有旧内容，不显示增删行）
  - 其他工具（包括 MCP 工具）：显示工具名、参数和结果文本
  - 同一批里的工具调用可能并行，每个调用各自显示状态
- **上下文分段**：总量用 `get_session_stats` 的 `contextUsage.tokens`，它可能为空，也可能是 pi 的估算值，为空时显示"—"。系统提示词和工具定义从会话记录还原：pi 在第一次请求时把提示词的各个分段（`sections`）和工具声明（`toolsAdded`）写成一条系统消息，之后的变化也写成系统消息（按名字修改分段、`toolsAdded` / `toolsRemoved`）；压缩条目里存有完整的检查点（`systemMessage`）。宿主沿当前分支回放这些条目，得到当前的提示词和工具集，再按字符数估算 token；对话消息 = 总量 − 系统提示词 − 工具定义。分段数字标"~"。新会话在第一次请求前、以及没有系统消息的旧会话，只显示总量。
- **对话框**：pi 发出 `extension_ui_request` 时，对话框类（`select` / `confirm` / `input` / `editor`）显示为卡片，回答后发 `extension_ui_response`；带超时的显示倒计时。对话框可能出现在一次运行之外，由宿主按会话保存（pi 不把它写进会话文件），所以"问题 → 回答"只在宿主存活期间保留。有未回答对话框的会话不回收进程；多个客户端同时回答，只接受第一个。单向通知类（`notify` 等）保留原文、暂时不显示。
- **在终端中继续**：pi 没有跨进程的写锁，两个进程同时写一个会话会悄悄分叉。所以这是一次交接：Atrium 停止接受该会话的写命令并回收进程，再给出 `pi --session <文件>`；用户回到 Atrium 时重新加载。会话文件被外部改动后怎么提示，等文件区设计时再定；宿主先预留检测（比较文件大小和修改时间）和 `session_changed_externally` 事件。交接之后回到 Atrium 要点"在 Atrium 里继续"，切到标签不会自动启动 pi（M1.9，见下文"并行、同步与关注"）。
- **同步与断线重连**（参照 Paseo）：
  - 项目、工作区、会话摘要三个列表各带 `generation`（宿主每次启动生成）和递增的 `seq`。客户端带游标请求，宿主返回快照或增量，之后推送 `upsert / remove`。
  - 会话的对话记录带 `epoch`（进程代次）和 `seq`。客户端只订阅打开着或可见的会话，宿主只给订阅者推增量；往上翻按游标拉更早的，`epoch` 变了或有缺口就重新拿一份快照（M1.9 定不做按序号补拉，见下文"并行、同步与关注"）。
  - 重连时先对齐三个列表，再对打开着的会话拿会话快照（最近 20 轮、流式中的消息、工具状态、排队、未回答的对话框、指标）；关注状态在列表里。
  - 刚发的消息先在本地显示，带 `clientMessageId`；宿主确认后用同一个 id 对上，不重复。
  - 断线不自动重发结果未知的命令。
  - 主窗口底部只在没连上时显示一行连接状态（正在连接、正在重连、已断开、被拒绝）；连上后不显示，连接和版本在"设置 · 关于"里看（2026-10-12 定）。

## 接口与数据

命令和事件的字段随里程碑补全，准绳是 `packages/protocol` 的 zod 定义。

所有会话命令都带 `sessionId` 和客户端生成的 `requestId`；连接上没有隐式的"当前会话"。所有会话事件都带 `sessionId`、`epoch`（进程代次）和 `seq`（会话内单调递增）；列表类事件带 `generation` 和 `seq`。命令落到哪个类，见 [领域模型 · 协议与类的对应](../architecture/domain-model.md#8-协议与类的对应)。

### 协议细节（2026-10-07 定）

zod 定义在 `packages/protocol`，是唯一的准绳；下面的表格是概览。

**信封**（`protocol/src/envelope.ts`）

- 客户端发的每条消息是一个可辨识联合 `ClientMessage`，按 `type` 区分：握手的 `hello`，以及各条命令。宿主发的是 `HostMessage`：`welcome`、`response` 和各种事件。
- 每条命令都带 `requestId`（客户端生成，同一连接内唯一）和 `traceparent`；会话命令再带 `sessionId`。参数和这三个字段平铺在同一层，不另套 `params`。

**应答**

- 每条命令恰好一条应答：`{ type: "response", requestId, ok: true, result? }` 或 `{ type: "response", requestId, ok: false, error: { code, params? } }`。宿主不产出给用户看的文字，界面按 `code` 和 `params` 显示。
- 错误码是 protocol 里的枚举，随里程碑增加。M1.3 用到：`invalid_message`（不是 JSON、不符合 schema）、`unknown_command`、`session_not_found`、`pi_unavailable`（`params.status` 说明原因：`missing` / `outdated` / `unusable` 是检查结果，`exited` 是 pi 已退出，`unresponsive` 是 pi 没有回应）、`session_busy`（pi 正在运行或压缩，不收新消息）、`transcript_changed`（`fetch_transcript`、`fetch_step` 带的 `epoch` 已经过时，M1.4）、`session_cwd_missing`（打开的会话记录的工作目录不存在，M1.4）、`pi_rejected`（pi 拒绝了这条命令，`params.detail` 是 pi 的原文，只供"展开看原始报错"）、`internal_error`（宿主自己的 bug）。pi 的拒绝不算宿主的 bug，不报 `internal_error`。
- `prompt` 不设期限：pi 要做完发送前的准备（可能包括自动压缩）才回应答，可能远超 30 秒；超时会让界面以为没发出，而 pi 照样执行。
- 未知或无效的消息也有应答：能读出 `requestId` 就带上，读不出时为 `null`。限流仍然直接断开（4429）；现在用日志"message ignored"计数的限流测试改成断言应答。
- 原来事件表里的 `error` 不再需要：命令的错误走应答；运行中的失败由 `run_settled` 带出，系统事件走 `notice`。

**握手与心跳**

- `welcome` 带 `protocolVersion`、`hostVersion`、`hostInstanceId`（宿主每次启动随机生成，就是列表同步的 `generation`）和 `heartbeatMs`（15000）。客户端重连后比较 `hostInstanceId`，判断宿主是否重启过。
- 客户端每 `heartbeatMs` 发一条 `ping` 命令，`heartbeatMs` 内没收到应答就当连接已死、断开重连（浏览器察觉不到休眠唤醒后断掉的 TCP）。宿主每 `heartbeatMs` 发一次 WebSocket 协议层的 ping，到下一次时还没收到 pong 就终止连接（浏览器会自动回 pong）。

**事件**

- 会话事件带 `sessionId`、`epoch`、`seq`，以及所属运行的 `traceId`（不在运行中为 `null`）。快照带 `exited`，pi 已退出的会话重连后也显示为已退出。
- 客户端每次连上都比较 `hostInstanceId`：变了说明宿主重启过，之前订阅的会话在新宿主里不存在（宿主重启后的恢复在 M1.4、M1.9）。M1.3 把这些会话的视图标为"已失效"，保留已显示的消息，清掉运行和流式状态，不再订阅；对话界面在已失效或已退出的会话里发消息时，新建一个对话。M1.9 起界面随即对已失效的当前会话重新 `open_session` 并订阅（见"并行、同步与关注"）。
- 列表事件带 `collection`（`projects`、`workspaces`、`sessions`）、`generation`、`seq`。

**追踪**：宿主为每条命令开一个 `command <type>` span，父 span 是命令自带的 `traceparent`，再用 span link 指向连接的 trace；不挂在连接那条长 trace 下面，否则一个连接上的所有操作会堆进同一条 trace。

**订阅**：哪个客户端订阅了哪些会话，记在宿主 `sync/` 下的 SubscriptionRegistry（[领域模型 §6、§7](../architecture/domain-model.md#6-宿主的组件)）；连接断开时清掉它的订阅。

**发送端背压**：宿主发消息前看这个连接的 `bufferedAmount`，超过 16 MiB 就以 4507 关闭这个连接，不再往里写。客户端重连后按游标重新对齐（[领域模型 §7](../architecture/domain-model.md#7-客户端与一致性)），所以不需要在宿主为它合并或丢弃增量；一个读得慢的客户端只影响它自己。

**附件**（实现在 M1.7）

- 客户端先压缩：长边缩到不超过 2048 像素（主流模型本来就会把更大的图缩小再看），编码成 WebP；base64 超过 100 万字符（约 730 KB，一条 WebSocket 消息要放得下）时按质量 0.9 → 0.5 逐级降低，还放不下就把边长缩到 3/4 再试，直到长边小于 256 像素仍放不下才提示图片太大（2026-10-10 定）。
- 粘贴或拖入时就用 `upload_attachment(mimeType, data)` 单独上传（`data` 是 base64），应答带 `attachmentId`；`prompt` 和 `steer` 只带 `attachmentIds`。每条 WebSocket 消息仍不超过 1 MiB，一次发好几张图也不受影响，发送时也不用再等上传。
- 宿主把上传的图片暂存在内存里，按连接计：最多 32 MiB、20 张，超出时应答 `attachment_limit`。消息带的图片全部在才发出，缺一张就应答 `attachment_missing`（带缺的那张的 id），一张也不用掉。只有图片的消息 `text` 可以为空，什么都没有的不行（`invalid_message`）；排队项带图片数（`images`），停止或崩溃退回排队的插话也带着它的图片。会话收下这条消息（发给了 pi 或进了宿主的排队）、连接断开、或 30 分钟没被用到时释放；会话拒绝这条消息时（例如 `session_stopping`）图片留着，界面可以再发一次（2026-10-10 定）。消息进了宿主的排队时，图片随排队项保存，不再算在客户端头上。宿主发给 pi 时按 pi 的 RPC 格式放进 `prompt` 的 `images`。

**界面问题上报**：`report_client_issue(kind, message, details?)` 把界面里的未捕获错误和性能问题（长任务、掉帧）写进宿主日志，带客户端 id 和当时的 trace id。`message` 和 `details` 截断到 4 KB，照常脱敏；界面不在里面放对话内容。界面在入口捕获未处理的错误和 Promise 拒绝，并观察超过 50 毫秒的长任务；同一类问题每 10 秒最多报一次，不会触发连接的限流。

**M1.3 先做的部分**

- 命令：`ping`、`create_chat`（最小形态：在 `~/.atrium/chats/` 下建目录，按领域模型"已决定 9"立刻启动 pi；写进索引留到 M1.5）、`subscribe_sessions`、`prompt`（只有文字）、`report_client_issue`。
- 运行中输入框不能发送：宿主的排队和"停止"在 M1.6，这之前运行中发消息只会被 pi 拒绝（`session_busy`）。
- 事件：`session_snapshot`（这次宿主运行中见过的消息；用 `get_entries` 重建历史在 M1.4）、`run_started`、`message_started`、`text_delta`、`reasoning_delta`、`message_finished`、`run_settled`、`session_exited`。
- 只显示文字和推理；工具调用的事件和显示在 M1.4。

### 对话记录（M1.4，2026-10-08 定）

对话区显示的是 TranscriptProjection（[领域模型 §2](../architecture/domain-model.md#2-会话历史条目分支与对话记录)）：宿主沿当前分支把 pi 的条目组织成"轮"和"提示条"，实时事件和分页拉取用同一套实体，M1.3 的消息级事件（`message_started`、`text_delta`、`reasoning_delta`、`message_finished`）由下面的轮级事件取代。

**实体**（`packages/protocol`）

- **轮** `Turn`：一条用户消息到下一条用户消息之间的全部内容。字段：`id`、`user`（文字、图片张数、`clientMessageId`、时间）、`steps`、`outcome`（`running` / `done` / `stopped` / `failed`）、`error`（失败时 pi 的原文）、`startedAt`、`durationMs`（运行中为空；宿主当场看到的轮按宿主计时，只在历史里出现的轮由消息时间戳推算）、`usage`（这一轮所有助手消息的输入、输出 token 之和，没有助手消息时为空）、`changes`（这一轮"已观测到的工具修改"：文件路径和增删行，`write` 没有行数）。
- **步骤** `Step`，按出现顺序：
  - `thinking`：推理文字；`durationMs` 只有当场计时才有，否则为空，界面显示"思考过程"而不是"思考了 N 秒"。
  - `text`：一段文字。只有一轮最后那段文字作为回复显示在过程下方，前面的收进过程（"一轮里的文字"）；哪段是最后一段由界面判断。
  - `tool`：`callId`、`tool`（工具名）、`args`、`status`（`running` / `done` / `failed` / `unfinished`：这一轮结束了还没有结果，比如被中断）、`output`（结果文字；运行中是到此刻为止的输出）、`details`、`partial`（见下面"大内容"）。`details` 按工具区分：`bash`（命令）、`read`（路径、起止行）、`edit`（路径、pi 给的 diff、增删行数）、`write`（路径和写入内容，内容来自调用参数，pi 的结果里没有；`write` 的 `args` 不再带 `content`，内容只发一份）、其他工具没有。
  - `steer`：插话。pi 的文件不记录一条用户消息是插话还是新的一轮（2026-10-08 按 pi 1.0.2 源码核实）。宿主当场看到的用户消息，记下它开启了新的一轮还是插话，运行结束后按顺序对应到新的用户消息条目，重建时以记录为准（M1.5 起存进 `~/.atrium`，宿主重启后仍在）。没有记录的（宿主之外跑的会话、宿主重启前的历史）用推断：紧跟在工具结果之后、下一次模型回复之前的用户消息是插话，属于当前这一轮。这条推断在"一次运行停在工具结果上"（工具要求结束本轮、pi 中途崩溃）时会把下一轮并进来，这种情况少见，接受。
  - `retry`：自动重试（第 N 次、pi 的报错原文），显示成一行灰色"正在重试"。重试发生在一轮中间，所以是步骤，不是提示条。失败的那次回复已经输出的部分（通常没有）照常是前面的步骤，重试步骤跟在后面，所以不会被当成回复；实时事件没有"删除步骤"，这样实时和重建才能一致。第 N 次按 pi 的计法：连续失败一次加一，有一次回复成功就归零；报错原文为空时和 pi 一样写 "Unknown error"。上下文溢出时 pi 屏蔽失败的回复、先压缩再重试，不发自动重试事件，所以也不算重试步骤：被屏蔽的出错回复后面紧跟压缩条目时，只显示压缩提示条。
- **提示条** `Notice`：`compacted`（压缩前 token 数、压缩摘要）。压缩发生在一轮中间时（上下文溢出），提示条放在这一轮之后，不把一轮拆开。

**id**：工具步骤带 pi 的调用 id；步骤的 `id` 是它在轮里的序号（从 `"0"` 起的十进制字符串）：一条助手消息的第 i 块是这条消息开始时已有步骤数 + i，实时和重建按同样的规则排出同样的序号。轮的 `id` 在实时时由宿主生成；运行结束后宿主重新读条目，按顺序把新的用户消息条目对应到实时的轮，沿用实时的 id。只在历史里出现的轮用"会话 id + 条目 id"。

**实时事件**（都带 `sessionId + epoch + seq + traceId`）：

- `turn_started(turn)`：pi 回显开启一轮的用户消息时，带整条轮（`outcome: running`，还没有步骤）。
- `step_added(turnId, step)`：推理、文字块开始时（文字为空）；工具调用在调用块写完时，带完整参数；插话、重试出现时。
- `step_delta(turnId, stepId, delta)`：推理、文字的增量。
- `step_updated(turnId, step)`：带整个步骤。助手消息结束时，与已发的不同的步骤各发一次；工具有了实时输出、结果时；一轮结束时还在运行的工具改为 `unfinished`。
- `turn_finished(turnId, outcome, error, durationMs, usage, changes)`：运行结束（`agent_settled`）时，在 `run_settled` 之前。pi 在运行中退出时，这一轮的结果是 `failed`（`error` 为空）；之后打开这个会话，文件里看不出崩溃，同一轮显示为 `stopped`。
- `notice_added(notice, before)`：见下面"快照与分页"的重建。`before` 是插在哪一条之前（轮或提示条的 id），为空表示放在最后。压缩发生在运行中，或在新消息开始前（pi 在 `prompt` 里先压缩），提示条在运行结束后才出现。
- `run_started`、`run_settled`、`session_exited` 不变。

**快照与分页**

- `session_snapshot` 带最近 20 轮（连同其间的提示条）、`hasOlder`、运行状态和 `exited`。打开会话订阅后一条消息就能画出首屏。快照和分页还受大小限制（4 MB）：装不下 20 轮时少带几轮（至少一轮），其余的留给翻页。
- `fetch_transcript(sessionId, before, limit)`：取某一条（轮或提示条）之前的 `limit` 条，返回条目和 `hasOlder`，带当前 `epoch`；`epoch` 已经变了就应答 `transcript_changed`，客户端改为重新订阅取快照。
- 运行结束、压缩结束、宿主自己发出改变状态的命令之后，宿主用 `get_entries(since)` 补齐条目并重建（运行中不重建，等这次运行结束）。重建结果和已推给客户端的完全一致就什么都不推；只是多了提示条（不论在哪里），就逐条推 `notice_added`，带插入位置；其余情况（例如当前分支变了、实时漏了什么），`epoch` 加一并给订阅者推新的快照。

**大内容**（2026-10-08 定）：内容不截断、不丢。工具步骤里的长文字（输出、`write` 的内容、`edit` 的 diff、参数里的长字符串）各自超过 16 KB 时，事件、快照和分页里只带一段预览（`bash` 的输出取结尾，其他取开头），步骤标 `partial: true`；界面展开这一步时用 `fetch_step(sessionId, epoch, turnId, stepId)` 取回完整的步骤。宿主内存里和重建比较用的都是完整内容。`epoch` 变了同样应答 `transcript_changed`。

**当场计时的数据**：轮的用时、推理用时由宿主在实时事件里测得，连同轮的实时 id、`clientMessageId` 和它开启新一轮还是插话，按轮另外存放，重建时合并回去，所以正常运行后重建结果和实时推过的一致；宿主重启后为空（"滚动与长会话"）。首 token 时间、输出速度只在状态栏显示，和状态栏一起做（2026-10-08 定；2026-10-09 状态栏单独成为 M1.8）。

**打开历史会话**（M1.4 的临时入口，M1.5 由侧栏和"历史"取代，见下一节）：没有打开会话时，对话区列出 pi 会话目录里最近的会话（第一条提问、时间）。`list_recent_sessions(limit)` 返回会话 id、文件里的第一条提问、修改时间；`open_session(sessionId)` 用 `pi --session <文件>` 在会话记录的工作目录里启动 pi 并返回，客户端随后订阅；工作目录不存在时应答 `session_cwd_missing`（`params.cwd`），界面显示"恢复失败：目录不存在"。扫描会话目录是 pi 包的 SessionFiles，只读，按 LF 分行，和读 pi 的 RPC 输出用同一个分帧（pi-internals §3）。

### 项目、工作区与会话（M1.5，2026-10-08 定）

侧栏、标签栏和"历史"显示的是宿主推来的一份完整列表（[领域模型 · 已决定 11](../architecture/domain-model.md#已决定)）。M1.5 只发快照：客户端订阅后先收到一份，之后索引、扫描结果或会话的运行状态一有变化，宿主合并一下再推一份完整的。M1.9 再加增量和游标。M1.4 的临时入口 `list_recent_sessions` 和"最近会话"列表随之删掉。

**实体**（`packages/protocol`）

- **项目** `Project`：`id`（`prj_…`）、`path`（解析过符号链接的真实路径）、`name`。
- **工作区** `Workspace`：`id`（`wks_…`）、`projectId`、`kind`（`local` / `worktree`）、`dir`、`alias`（自定义名称，没有为空）、`branch`（检出的分支；detached HEAD 或不是 git 仓库时为空）、`head`（detached 时的短 commit 号）、`external`（不是 Atrium 建的 worktree）、`createdAt`（worktree 的创建时间，本地工作区为空）、`merge`（合并状态，本地工作区和非 git 项目为空）。名称由界面按 `alias ?? branch ?? 目录名` 得出。
- **合并状态** `MergeState`：`dirty`、`ahead`、`verdict`（`noChange` / `pending` / `merged` / `removed` / `unknown`）、`reason`（`unknown` 的原因：`git_too_old`、`no_main_branch`、`git_failed`、`base_unknown`）。主干只认项目的覆盖值或 `origin/HEAD`，没有就是 `unknown`（`no_main_branch`），不猜本地分支（2026-10-08 定）。
- **对话** `Chat`（2026-10-12 加，ADR-0007）：`id`（`cht_<目录名>`）、`dir`、`alias`（自定义名称，没有为空）、`firstSessionId`（没归档的会话里最早建的，没有为空）。名称由界面按 `alias ?? 第一个会话的标题` 得出。宿主扫描 `~/.atrium/chats/` 的子目录得出对话列表，自定义名称存在 `chats.json`。
- **会话摘要** `SessionSummary`：`sessionId`、`containerId`（工作区或对话的 id；2026-10-12 前对话都是 `chats`）、`name`（pi 的会话名）、`prompt`（第一条用户消息的第一行，去掉 Markdown 符号和首尾空白，最多 200 个字符；没有文字为空）、`file`（会话文件路径，还没写出时为空）、`state`（`draft` / `persisted` / `missing`）、`updatedAt`、`archived`、`running`。标题由界面按 `name ?? prompt` 得出，都为空时草稿显示"新会话"，否则显示"图片"。
- **布局** `Layout`（只给这个客户端自己的）：`container`（当前所在的工作区或对话，没有为空）、`tabs`（每个容器打开着的会话和当前标签）。
- **偏好** `Preferences`：`appearance`（`system` / `light` / `dark`）、`displayMode`（摘要 / 思考 / 详细，从 M1.4 的 localStorage 挪到宿主，所有客户端一致）。

**事件**：`index_snapshot(generation, seq, projects, workspaces, chats, sessions, layout, preferences, resets)`（`chats` 2026-10-12 加，`index_changes` 同样多一组）。`generation` 是宿主实例 id，`seq` 每推一次加一。`resets` 列出这次宿主启动时因损坏被重置的索引文件（领域模型 §1"索引的存储"），界面提示一次。

**命令**

- `subscribe_index()`：订阅列表，宿主马上推一份快照，之后有变化就推。连接断开即退订。
- 订阅一个已写出文件、但 pi 还没启动的会话时，宿主先记下订阅，pi 启动（由 `open_session` 或第一次 `prompt` 触发）后再发快照，不拒绝；客户端拿到列表后，对当前标签先 `open_session` 再订阅（2026-10-08 审查后补）。
- `add_project(path)`：登记项目，返回 `projectId`。不是目录应答 `path_not_found`；已经是某个项目或其工作区时应答 `project_exists`（`params.projectId`）；名称和已有项目重复时自动加序号，如 `app (1)`。选的是某个仓库的 worktree（不是主工作树）时，登记的是主工作树所在的仓库，这个 worktree 作为它的一个工作区出现（2026-10-08 定）。同时添加的几个目录依次处理。
- `remove_project(projectId)` / `rename_project(projectId, name)`：移除只删索引，同时停掉其中会话的 pi、从各客户端的布局里去掉；改成已有项目的名字应答 `name_taken`。
- `rename_workspace(workspaceId, name | null)`：`null` 恢复为分支名。
- `rename_chat(chatId, name | null)`：`null` 恢复为第一个会话的标题；对话不存在应答 `chat_not_found`（2026-10-12 加）。
- `window_focused()`：窗口获得焦点，宿主重扫工作区、合并状态和会话文件。
- `create_session(containerId)` / `create_chat()`：`create_session` 在工作区或对话的目录里新建会话（2026-10-12 起也能在对话里，工作区不存在应答 `workspace_not_found`，对话的目录不在了应答 `chat_not_found`）；`create_chat` 新建一个对话目录和其中的第一个会话。新建草稿会话并立刻启动 pi（领域模型"已决定 9"，2026-10-08 定工作区里的新会话也一样），打开成这个客户端的标签并激活（这期间客户端换过位置时不切过去，见下文），返回 `sessionId`。不等 pi 启动（2026-10-11 改）：会话 id 由宿主生成，记下草稿、打开标签就应答，pi 在后台用 `--session-id <id>` 启动；第一次 `prompt`、`list_commands` 和 `open_session` 都等这次启动。pi 不可用或启动失败不让新建失败，只记日志；`open_session`、`prompt`、`list_commands` 再启动一次，失败应答给它们，显示在会话里。
- `open_session(sessionId)`：打开成标签并激活，切到它所在的容器；pi 没在运行就用 `--session <文件>` 启动。宿主重启后恢复的草稿不启动，第一次 `prompt` 时才用 `--session-id <id>` 启动（"已决定 7"）；宿主这次运行里新建的草稿照常启动，后台启动还没结束就等它，启动失败就应答失败。
- `close_tab(sessionId)`：只改这个客户端的布局。关掉的是还没发过消息的草稿时，丢弃它：停掉 pi、删掉索引里的记录（2026-10-08 定）；它是对话里唯一的会话时，对话的空目录一并删掉（只删空的），对话随之消失（2026-10-12 补）。
- 同一个客户端改标签和位置的命令（`open_session`、`close_tab`、`select_container`）按收到的顺序生效（2026-10-08 修）。索引里已有记录的会话立刻打开成标签，不等第一次扫描；还不认识的会话才等扫描结束再打开，扫描期间关掉的标签不会在扫描结束后又被打开。启动 pi 仍要等第一次扫描，因为要知道会话文件在哪。第一次扫描要先读出登录 shell 的环境（最坏约 30 秒），界面上的切换和关闭不跟着等，这和 VS Code、Zed 的做法一致。宿主开始关闭后，排着队的这类命令不再执行。
- 新建的会话记下草稿就打开成标签，不等 pi 启动（2026-10-11 改）：它成为所在容器的激活标签；客户端在发出新建之后换过位置就留在原处，没换过就切过去（2026-10-08 定）。
- 已知问题：关掉一个空草稿的标签后立刻再打开它，标签可能开着而草稿已被丢弃（记录删掉、pi 停掉）。需要两条命令落在丢弃的那几毫秒里，少见，暂不处理。
- `select_container(containerId | null)`：切换工作区或对话。
- `archive_session(sessionId)`：只改索引；停掉它的 pi，从各客户端的布局里去掉。pi 正在启动时等它启动完再停，不让归档后的会话留着一个 pi（2026-10-10 审查后补；移除工作区同样）。
- `rename_session(sessionId, name)`：用 pi 的 `set_session_name` 写回；pi 没在运行就先启动。草稿不能改名，应答 `session_is_draft`，界面上"重命名"置灰（2026-10-08 定）。
- `set_preferences(appearance?, displayMode?)`。

新增错误码：`project_not_found`、`workspace_not_found`、`chat_not_found`（2026-10-12 加）、`project_exists`、`name_taken`、`path_not_found`、`session_is_draft`。

**扫描**：工作区用 `git worktree list --porcelain`，同时最多跑 4 个 git 命令。会话只扫已登记的容器对应的 pi 会话目录（按 pi 的规则由工作目录得出目录名），再按文件头的 `cwd` 核对；按文件大小和修改时间缓存，文件只增长时只读新增的部分（会话名取最新一条 `session_info`）。同一个 id 出现在多个文件时取最新的，日志记一条冲突。

**收件箱**挪到 M1.9，和关注状态一起做（2026-10-08 定）：它收的"待回答、待授权、出错未看"要到 M1.6、M1.9 才有，为空时本来就整块不显示。

### 运行控制（M1.6，2026-10-09 定）

排队、插话、停止、对话框、失败重试和崩溃重启的协议与行为。产品层面的规则见上文"对话区"的"运行中输入""运行出错与停止"和"关键流程"，这里写宿主和协议怎么做。

**控制状态**：会话快照新增 `control`，变化时推 `control_updated`（整份，内容很小）：

- `queue`：宿主的排队，每项 `{ id, text, createdAt }`，按发出顺序；图片附件在 M1.7 加进来。
- `paused`：排队是否暂停，`reason` 为 `stopped`（你点了停止）或 `crashed`（pi 崩溃后还没恢复）；压缩期间出队也会等，但那不算暂停，不显示。
- `steers`：已经交给 pi、还没送达的插话，`{ id, text }`。pi 的 `queue_update` 每次带完整的内部队列，宿主按它确认哪些已送达，界面据此显示"N 条插话将在下一步前送达"。
- `stopping`：停止已发出、pi 还没确认停下。
- `restarting`：pi 崩溃后宿主正在重新启动它（2026-10-09 审查后补）；这期间界面不提供"重试"。
- `interactions`：未回答的对话框，见下文。
- `failure`：连续崩溃 3 次后为 `{ reason: "crashed", attempts }`，会话进入"出错"；下一次运行开始时清掉。

**一个会话只有一个 pi**（2026-10-09 审查后补）：自动重启、打开、发消息、"重试"、"继续发送"都经同一个启动入口；重启没结束前会话仍算在运行，期间收到的消息进排队，不另起 pi。换上新 pi 时旧的必须已经退出。归档、移除工作区、宿主关闭会打断进行中的重启：新起的 pi 停掉，不再续做。

**提交**

- `prompt(text)`：空闲（没有运行、没在压缩、没在停止）时直接发给 pi，应答 pi 的结果 `started` / `handled`；正在运行或压缩时加到排队末尾，应答 `queued` 和排队项的 `itemId`。排队暂停时（停止之后）空闲状态下发的新消息直接发出，排队保持暂停，由你点"继续发送"或清掉（2026-10-09 定）。
- 出队：运行结束（`agent_settled`）、上一条被 `handled`、压缩结束（`compaction_end`）、换上新 pi 或"继续发送"后，宿主把排队的第一条作为 `prompt` 发给 pi，一次一条。出队和停止由会话控制器串行处理。出队的那条被 pi 拒绝时：pi 忙就放回最前、等下一次机会；pi 退出就放回最前、交给重启（重启后由排队发出，不再当作被打断的那条另发一次）；其他原因放回最前并暂停排队（`stopped`），后面的不会先发出去（2026-10-09 审查后补）。
- `steer(text)`：有运行（已收到 `agent_start`）时调用 pi 的 `steer`，应答 `queued`（pi 已收下）或 `handled`；没有运行时（空闲、消息还在发送、单独的压缩中、重启中）等同 `prompt`，该排队就排队（2026-10-09 审查后补）。插话在发给 pi 之前就记进 `steers`，pi 的 `queue_update` 先到也能对上。同一会话的插话逐条发给 pi，上一条应答后才发下一条（轮到时已经在停止的，不再发出，应答 `session_stopping`，界面把它放回输入框）：pi 并发处理命令，extension 的输入处理是异步的，同时发出的插话进队顺序可能和发出顺序不同。pi 队列里列的是展开后的文字（skill、提示词模板展开之后），和宿主发出的不一定相同，所以宿主不按文字认插话：pi 的队列每多一项，就是它收下了最早一条还没被列出的插话；每少一项，就是从队头送达了最早一条已列出的；停止时 pi 退回几条，就是最后几条已列出的，按宿主发出时的文字和图片放回排队。只有图片、没有文字的插话发给 pi 时文字写成"（见图片）"：pi 只按文字把送达的消息移出队列，空文字的插话会一直留在它的队列里（pi 1.0.2、1.1.0 的缺陷，见 pi-internals.md）（2026-10-10 第二轮审查后定）。pi 的 `steer` 在空闲时不会启动运行，消息只会留在 pi 的队列里（按 pi 1.0.2 源码核实），所以宿主必须把空闲时的插话改成普通发送。插话不接受 extension 的 `/` 命令，pi 会拒绝，应答 `pi_rejected`。
- `prompt_handled(clientMessageId)` 事件：输入被 extension 直接处理、没有启动运行，界面去掉这条消息的待发副本。

**停止**：`stop()` 先暂停出队，再对 pi `clear_queue`、`abort`（两条同时发出，2 秒从发出 `stop` 算起）。`clear_queue` 退回的还没送达的插话放回排队最前面（和崩溃时一样，不丢）。`abort` 等 pi 真正停下才应答：2 秒内应答时 `stop` 应答 `{ confirmed: true }`；否则应答 `{ confirmed: false }`，会话保持 `stopping`，一直等到 pi 确认或退出（2026-10-09 定，不设上限）；`abort` 出错不算确认，照样等 pi 退出。pi 已回应 `started`、`agent_start` 还没到，或正在重启，也算有运行要停；只有确实什么都没在跑时才直接应答 `{ confirmed: true }`。停止之后 pi 若崩溃，重启后不续做被打断的那条，它放回排队最前、保持暂停，由你决定（2026-10-09 审查后补）。`stopping` 期间 `prompt`、`steer`、`steer_queued`、`resume_queue`、`retry_run` 应答 `session_stopping`；编辑、删除、清空排队照常。

**排队的编辑**：`update_queued(itemId, text)`、`remove_queued(itemId)`、`steer_queued(itemId)`（取出这一项作为插话发出，空闲时直接发出）、`resume_queue()`（解除暂停并立即开始出队；pi 不在时先启动它）、`clear_queue()`（清空宿主的排队）。不认识的 `itemId` 应答 `queue_item_not_found`。

**对话框**：pi 的 `extension_ui_request` 里的 `select`、`confirm`、`input`、`editor` 成为对话框 `{ id, kind, title, message?, options?, placeholder?, prefill?, deadline? }`，推 `control_updated`；`deadline` 由宿主收到时加上 pi 给的 `timeout` 算出。`answer_interaction(interactionId, answer)` 的 `answer` 是 `{ value }`、`{ confirmed }` 或 `{ cancelled: true }`，宿主转成 `extension_ui_response` 发给 pi。只接受第一个回答，之后的回答和已作废的应答 `interaction_closed`。到期时宿主把它标为超时（pi 自己会按默认值继续）；pi 退出时一律作废。对话框结束（回答、取消、超时、作废）后，对话记录里在当时的位置留一行"问题 → 结果"（`interaction` 提示，和重启提示一样只在宿主存活期间保留，2026-10-09 定）。`notify` 等单向通知不显示，截断到 4 KB、照常脱敏后写日志（2026-10-09 定，见 security.md"凭据与日志"）。对话框在宿主存活期间保留，不跨重启。

**失败与重启**

- 模型调用失败交给 pi 自带的重试：宿主启动 pi 时用 `set_auto_retry` 确保开启，次数沿用 pi 的设置（`retry.maxRetries`，默认 3），RPC 改不了（2026-10-09 定）。重试在对话记录里显示为 `retry` 步骤（M1.4 已有），当场看到的带上 pi 给的上限，显示为"正在重试（第 N / M 次）"；从文件重建的不知道上限，只显示"第 N 次"。用尽后这一轮以 `failed` 结束，带 pi 的报错原文，界面显示错误卡片。
- pi 崩溃：本轮以 `failed` 结束，排队暂停（`reason: crashed`），还没送达的插话退回排队最前面，对话框作废，发 `session_exited`。宿主随即用 `--session` 重新启动 pi，会话的 `epoch` 加一、推新的快照，对话记录里加一条宿主的提示"进程已自动重启（第 N / 3 次）"（`restarted` 提示，只在宿主存活期间保留）。重启后：崩溃时正在运行或正在提交（已发给 pi、还没回显，包括 `agent_start` 之前和重启后的续做）的那条输入还没写进会话，就重新提交它；已经写进会话，就补发一条"上一次运行意外中断了，请从中断的地方继续。"（2026-10-09 定），这条在界面上标为"系统自动发出"（`Turn.user.auto`，记在 `~/.atrium/turns/` 里，重建后仍在）。然后解除暂停、继续出队。
- 连续 3 次重启都失败（再次崩溃，或启动不起来）后不再重启：会话进入"出错"（`control.failure`），排队保持暂停，界面显示错误卡片。一次运行结束且这一轮没有失败（完成或被停止都算）后连续计数归零（2026-10-09 定）。
- `retry_run()`：错误卡片上的"重试"。pi 没在运行就先启动，启动期间算作重启中（消息排队、再点重试不起作用），启动时会话被关闭就停掉刚启动的 pi；然后按上面"重启后"同样的规则再来一轮：被打断的那条（重启用尽时记下的）没写进会话就重新提交，写进了就补发那句话；没有被打断的，就对最后一轮失败的补发那句话。正在运行、提交或重启时什么也不做。失败状态在新的 pi 换上之后才清掉。
- 出错状态在标签和侧栏一直显示到下一次运行开始：会话摘要 `SessionSummary` 多一个 `failed`（最后一次运行失败，或连续崩溃用尽），下一次运行开始时清掉；M1.9 换成写进索引的关注状态 `attention`，并加上收件箱（见"并行、同步与关注"）。

新增命令：`steer`、`stop`、`resume_queue`、`clear_queue`、`update_queued`、`remove_queued`、`steer_queued`、`answer_interaction`、`retry_run`。新增事件：`control_updated`、`prompt_handled`。新增错误码：`session_stopping`、`queue_item_not_found`、`interaction_closed`。`prompt` 的应答多了 `queued`（带 `itemId`）。

### 模型与输入框（M1.7，2026-10-10 定）

模型列表照 Paseo 的做法（`paseo-architecture.md` §3），`@` 候选和 pi 的终端界面一样用 `fd`。产品层面的规则见上文"对话区"的"输入框"，这里写宿主和协议怎么做。

**模型列表**

- 宿主的 PiCatalog 为一个目录短启一个 `pi --mode rpc`（不带 `--session`），调 `get_available_models` 和 `get_state`，然后停掉它。`get_state` 里的模型是 pi 按自己的设置选出的默认模型。不借正在运行的会话的 pi。工作区用工作区目录；对话用 Atrium 的目录 `~/.atrium`（Paseo 用家目录；对话各自的目录就在它下面，是空的，和它一样只有全局设置）。
- 结果按目录缓存在宿主内存里，没有期限，不落盘。项目自己的 `.pi/settings.json` 可能改变可用的模型，所以按目录分开。同一目录同时只查一次，后到的请求等同一次结果。宿主启动时不查，界面进入一个工作区或对话时预取一次。
- `list_models(workspaceId | null, refresh?)`：`null` 是不在工作区里的地方，所有对话和设置共用 Atrium 目录的列表（2026-10-12 改，原先按容器、对话是 `chats`）。有缓存就直接返回，没有就等查询完成（期限 120 秒，超时停掉那个 pi）。`refresh: true` 强制重查，是模型面板里"刷新"按钮用的；重查期间界面继续显示旧列表，重查失败时应答错误、宿主丢掉旧缓存（和 Paseo 一样）。打开模型面板时界面再请求一次（不强制），所以登录新服务商后点"刷新"就能看到。在 Atrium 里登录成功或退出登录成功后，宿主丢掉所有目录的模型列表缓存，下次请求时重查（2026-10-11 定）。
- 应答 `{ models, defaultModel }`。每个模型 `{ providerId, modelId, name, contextWindow, maxOutput, supportsImage, thinkingLevels }`。pi 只返回有凭据的服务商的模型。
- 推理档位按模型的元数据算出，不调 `get_available_thinking_levels`（它只回答当前模型）：不支持推理的只有 `off`；其余从 off / minimal / low / medium / high / xhigh / max 里去掉 `thinkingLevelMap` 标为 `null` 的，`xhigh`、`max` 只在 `thinkingLevelMap` 里明确给出时才有。规则照抄 pi-ai 的 `getSupportedThinkingLevels`，写在 `packages/pi` 里（运行时不依赖 pi 的包），pi 改了规则时契约测试会发现。
- 没有任何凭据时 pi 照常回答，列表为空；`get_state` 给的是占位模型（`unknown/unknown`），不算默认模型。默认模型必须在列表里。会话的模型是占位模型时也当作没有（`null`）。
- 查询失败（pi 退出、超时，或者启动不起来）应答 `models_unavailable`，`params.detail` 是 pi 的报错原文（stderr 的最后一段，截断到 4 KB），和 `pi_rejected` 一样只供"展开看原始报错"；宿主不把 `detail` 写进日志。探测用的 pi 的 stderr 和会话的 pi 一样按 observability.md 逐行、脱敏记录（2026-10-10 定）。

**会话的模型**

- 会话快照新增 `model`：`{ providerId, modelId, thinkingLevel } | null`，变化时推 `model_updated`。宿主在 pi 启动后、`set_model` 和 `set_thinking_level` 之后用 `get_state` 读取；pi 的 `thinking_level_changed` 事件自己带着新档位，直接用它。pi 退出后重新启动时，模型按新 pi 读到的为准。
- `set_model(providerId, modelId)` / `set_thinking_level(level)`：转给 pi，之后用 `get_state` 读回实际的模型和档位（换模型后 pi 会把档位截到新模型支持的范围），再取一次条目（`model_change` 等条目不发事件）。pi 已经接受、只是读回失败时，命令照样应答成功（pi 已经换了），模型留到下次取条目后再读（2026-10-10 第二轮审查后定）。运行中也可以换，从下一次请求开始生效；`stopping` 期间应答 `session_stopping`。pi 没在运行就先启动它。
- 记住上一次的选择：Preferences 新增 `lastModel`（`{ providerId, modelId } | null`）和 `thinkingByModel`（键是 `providerId/modelId`）。在任何会话里换模型或推理强度都会更新它们（Paseo 记在客户端，Atrium 的偏好在宿主索引里，所有客户端共用）。pi 的 `set_model` 不写 pi 自己的设置，所以由 Atrium 记。
- 新会话（工作区里新建、新对话、宿主重启后恢复的草稿第一次启动）启动 pi 后，宿主按 `lastModel` 调 `set_model`，再按 `thinkingByModel` 调 `set_thinking_level`，然后才处理第一条消息。**不照 Paseo 用 `--model` 启动**：pi 解析不出 `--model` 时直接退出，记住的模型后来没了凭据就会让会话起不来；`set_model` 找不到模型只是一条错误应答，宿主忽略它，会话用 pi 自己的默认模型。`lastModel` 为空时什么也不设。从文件打开的会话不设，pi 沿用会话里记录的模型。还没写出文件的会话重新启动时（崩溃后重启、退出后再打开），新的 pi 不知道它原来的模型，宿主按它原来的模型和档位设，不用 `lastModel`（2026-10-10 定）。
- 当前模型不支持图片时（模型列表里 `supportsImage` 为假）不允许添加图片，提示当前模型不支持；已经添加了图片再换到不支持的模型，发送按钮旁提示，发送时照样发出，由 pi 换成占位文字。

**Fast**（M1.11，2026-10-12 定，[ADR-0008](../adr/0008-atrium-own-pi-extension-for-fast.md)）

- 是什么：OpenAI 的 priority 服务档（对外叫 Fast），请求带 `service_tier: "priority"`，约 1.5 倍速度；额度消耗 GPT-5.4 约 2 倍，GPT-5.5、5.6 约 2.5 倍。服务端可能不按 priority 处理，请求的钩子看不到，所以 Atrium 不声称每一次都提速了。
- 哪些模型支持：只有 ChatGPT 订阅（`openai-codex`）里 id 匹配 `^gpt-5\.(4|5|6)(?:$|-)` 的模型，和社区插件 `pi-codex-fast-mode` 一致；用 API key 的 `openai` 暂不支持（2026-10-12 定）。规则写在 `packages/pi`，宿主和扩展共用。`list_models` 的每个模型新增 `fastCredits`：支持时是额度倍数（2 或 2.5），不支持时是 `null`。
- 怎么生效：pi 核心不传服务档（1.0.2、1.1.0），宿主启动会话的 pi 时用 `--extension` 加载 Atrium 自带的扩展。扩展开着、当前模型支持时，在 `before_provider_request` 里给请求加上 `service_tier: "priority"`，其他请求原样放过。宿主用 `prompt` 发内部命令 `/atrium-fast on` 或 `/atrium-fast off` 开关它：pi 立即执行（运行中也可以），应答 `handled`，不进对话记录。从下一次请求开始生效。
- 不误发：扩展默认关。pi 启动后宿主从 `get_commands` 里确认扩展的 `atrium-fast` 命令在，才会发这条命令；不在（扩展没加载上）时记一条警告，这个 pi 上 Fast 不可用，`set_fast` 应答 `fast_unavailable`，绝不把 `/atrium-fast on` 当普通消息发出去。`list_commands` 不列出这个命令。
- 每个会话一份：会话快照新增 `fast: boolean`，是你想不想开，和当前模型支不支持无关，变化时推 `fast_updated`。`set_fast(sessionId, enabled)` 转给 pi，处理和 `set_model` 一样：pi 没在运行就先启动它，`stopping` 期间应答 `session_stopping`。当前模型不支持时也接受：记下开关，换到支持的模型后生效。
- 记住：`set_fast` 把开关写进这个会话在 `sessions.json` 里的记录（`fast`），终端里开的会话也因此有了记录；同时更新偏好 `lastFast`。会话的开关取自它的记录，没有记录时（新会话、终端里开的会话）取 pi 第一次启动时的 `lastFast`，之后由会话自己记着。pi 每次启动（含崩溃重启、从终端接回）后，开关是开的就补发 `/atrium-fast on`。宿主重启后，没有记录的会话重新按 `lastFast` 取。
- 交给终端后，终端里的 pi 不加载 Atrium 的扩展，Fast 不跟过去。用户自己装的 `pi-codex-fast-mode` 也改 `service_tier`，两个都开时 Atrium 关不住它，暂不检测。
- 费用：状态栏的费用来自 pi，pi-ai 按回复里实际给的服务档计价。但 pi-ai 1.0.2 只对 `gpt-5.5` 按 2.5 倍算，其他按 2 倍，所以 GPT-5.6 会比 OpenAI 的说法少算。

**`/` 命令**

- `list_commands(sessionId)` 调会话自己的 pi 的 `get_commands`，每次弹出列表时请求一次，宿主不缓存。pi 没在运行（宿主重启后恢复的草稿、已退出的会话）就先启动它，和第一次发消息时一样；只输入了 `/` 没发消息的草稿，关掉时照样丢弃。空状态（还没有会话）下输入 `/` 时先新建会话，和在空状态下发送时新建的是同一个。
- 列表三类：extension 命令、提示词模板、skill（名字形如 `skill:<名字>`），带描述和参数提示。↑↓ 选择，回车或 Tab 选中后插入 `/名字 `；已经完整打出列表里高亮的那个命令时，回车直接发送（2026-10-10 定）。发送时由 pi 展开或交给 extension 处理（`handled`）。pi 终端界面的内置命令（`/model`、`/compact` 等）在 RPC 里不存在，不列出。插话不接受 extension 命令（pi 拒绝，见"运行控制"）。

**`@` 引用**

- `search_files(sessionId, query)`：在会话的工作目录里调 `fd`，参数和 pi 的终端界面一致：`--type f --type d --follow --hidden --exclude .git`，每次最多 100 个结果；先搜一层、再递归搜，合并后按匹配程度排序（完全匹配 > 前缀 > 文件名包含 > 路径包含，目录略优先，同分按深度、长度、名字），返回前 20 个。查询里带 `/` 时只在那个子目录里搜。`fd` 自己遵守 `.gitignore`、`.ignore`、`.fdignore`，所以 git 仓库和普通目录走同一条路，也包括还没 `git add` 的新文件。只在工作目录之内搜，不支持 `~/`、绝对路径和 `..`；工作目录里的符号链接和 pi 一样跟进去（`--follow`），它指向的内容算工作目录的一部分（2026-10-10 定）。
- `fd` 的位置和 pi 一样：先找 `~/.pi/agent/bin/fd`（`PI_CODING_AGENT_DIR` 可改），再找登录 shell 的 `PATH` 里的 `fd`、`fdfind`。都没有时应答 `fd_missing`，界面提示"没有找到 fd"；宿主不自己下载（pi 的终端界面第一次启动时会下载它）。首次启动的检查在 M1.10 加上 fd。
- 每次查询最多 5 秒，超时或同一会话来了新的查询时停掉上一次的 `fd`。查询词作为 `fd` 的参数传入（不经 shell），放在 `--` 之后，以 `-` 开头的查询词不会被当成 `fd` 的选项；`fd` 把以 `-` 开头的名字输出成 `./-名字`，宿主去掉 `./`。
- 发送时文件写成 `@相对路径`，目录写成 `@目录/`，路径里有空白时写成 `@"路径"`，和 pi 的终端界面插入的一样。
- 什么时候算在输入 `@`：`@` 前面不是字母、数字或 `._+-` 时（所以邮箱不算）；中文词之间没有空格，跟在汉字或中文标点后面也算。查询词是 `@` 到光标之间的字。列表里回车把它变成文件小胶囊，Tab 在目录上是进入这个目录继续找（名字带空白的目录写成 `@"目录/` 继续找，引号里的字是查询词）。列表显示的结果还是上一个查询词的时（新的还没回来），回车不选。查询词按字面匹配（pi 当正则用，名字里的 `+`、`(` 会出错）。

**↑ 历史与草稿**

- ↑ 历史是本会话当前分支上你发过的消息和插话（不含"系统自动发出"的），按发出顺序从新到旧，相邻重复的只算一条。输入框完全为空（没有文字、小胶囊和图片）时 ↑ 才调历史。取自界面已经加载的对话记录，翻过已加载的最早一轮时按游标取更早的。宿主重启后照样在，Atrium 不另存。

**工作区改动**（2026-10-10 定：照抄 Paseo，见 [paseo-architecture §6.1](../research/paseo-architecture.md)；取代"本会话改动"）

- 统计的是工作区目录的 git 改动，不是 agent 的工具调用：不分会话，用户自己改的也算，和对话记录加载了多少无关。每轮的"改动汇总"不变，仍是已观测到的工具修改。新对话的目录不是 git 仓库，没有这些。
- 胶囊条里的"+A −D"：`git merge-base HEAD <比较基准>` 之后 `git diff --shortstat <merge-base>`（工作树对 merge-base：已提交、暂存、未暂存都算），加上未跟踪文件的行数。比较基准（git 命令里用完整的 ref 名，如 `refs/remotes/origin/main`，免得被同名的 tag 抢走；界面显示短名）：当前分支不是主干时，主干（按领域模型"已决定 15"：项目设置或 `origin/HEAD`）有 `origin/<主干>` 就用它，否则用本地的 `<主干>`；当前分支就是主干、或者没有主干时，用 `origin/<当前分支>`，没有就不显示。HEAD 分离、空仓库也不显示。增删都是 0 时不显示。数字超过 999 时写成 `1.2k` 这样的紧凑格式；减号沿用对话里每轮改动汇总的 `−`。
- 未跟踪文件的行数：`git ls-files --others --exclude-standard` 的前 500 个，跳过大于 1 MB 的、二进制的（前 16 KB 里有 0 字节，或控制字符超过 30%）、符号链接和读不了的，数换行（结尾的换行不另算一行）。读文件时不跟随符号链接（打开时就拒绝链接），类型、大小和内容都从同一次打开里取，检查之后文件被换掉也读不到别处。
- 宿主只给有界面在看的工作区算：界面在显示某个工作区时用 `watch_changes` 告诉宿主（有没有打开的会话都算：空状态里也有这个胶囊，照 Paseo）。宿主递归监听工作区目录（`fs.watch`，macOS 下递归），忽略 `.git` 里除 `HEAD`、`index`、`refs/`、`packed-refs` 以外的文件、`*.lock`，以及被 git 忽略的目录（`git ls-files -o -i --directory --exclude-standard`，`.gitignore` 变了重算）；linked worktree 另外监听它在主仓库里的元数据目录。文件变化后 1 秒（尾随防抖）重算；后台 fetch 之后、窗口获得焦点、工作区里一次运行结束时也重算。结果和上次一样就不推送。监听建好之后再算一次，免得漏掉建好之前的改动。监听出错、或一开始就建不起来时改为轮询：5 秒起，结果没变就把间隔翻倍，最长 60 秒，一有变化回到 5 秒；同时 30 秒后重试监听，再失败就退避（最长 5 分钟）。没有界面在看的工作区停止监听。没有 git 时面板显示"读不到改动"。
- 改动面板：点胶囊从对话区右侧拉出一栏（约 560px，对话仍可见），焦点在面板里时按 Esc（菜单开着时只关菜单）、或点关闭按钮收起（输入框里的 Esc 仍是停止运行），换到别的容器时收起。
  - 两种模式："未提交"= HEAD 对工作树（含暂存）加未跟踪文件；"已提交"= `merge-base..HEAD`，只有提交。所以胶囊上的数字和面板的合计可能不同（Paseo 也是这样）。默认：工作区有未提交改动时看"未提交"，否则看"已提交"；手动切换只在"有没有未提交改动"不变时有效，变了就回到默认（照 Paseo）。
  - 头部：模式菜单（"已提交"带说明"<分支> → <主干>"，两者相同时不写）、面板里各文件增删的合计、刷新按钮（让宿主重算一次，结果回来前保留正在显示的文件）、关闭按钮。
  - 正文按顺序判断：加载中（"正在检查仓库…"）；不是 git 仓库；出错（说明原因）；改动太大（git 的 diff 输出超过 8 MB："改动太大，无法在这里预览"）；没有改动（"没有改动"；"已提交"模式下有未提交改动时附"看未提交的改动"，"未提交"模式下分支领先主干时附"看已提交的改动"）。
  - 有改动时：先是文件列表（路径、增删、新增 / 删除 / 修改 / 重命名标记），点文件滚到它的 diff；然后逐个文件的 diff：文件头写文件名和灰色的目录、增删、标记（重命名写"旧路径 → 新路径"），点文件头折叠或展开；diff 行带行号和增删竖条，和对话里工具的 diff 一样，hunk 头 `@@ … @@` 显示成灰色一行。二进制文件显示"二进制文件"；单个文件的 diff 超过 1 MB、或按面板顺序（路径）前面的文件累计超过 2 MB 之后的文件，显示"改动太大，不显示"（行数照常，大于 1 MB 的未跟踪文件不读内容、只数行）。宿主按每段 diff 文件头里的路径把它对应到文件（文件和符号链接互换时 git 输出两段，合成一个文件）。git 读改动出错时面板显示"读不到改动"，不显示成"没有改动"；读不了的单个未跟踪文件跳过。
  - 不做（Paseo 有的）：并排对比、隐藏空白、换行切换、语法高亮、行内评论、文件右键菜单、撤销改动。
- 协议：
  - `watch_changes(workspaceIds)`：设置这个连接在看的工作区（替换上一次的）。宿主马上推每个工作区的 `changes_updated { workspaceId, stat, dirty, ahead, branch, base }`，之后变化时再推。`stat` 是 `{ added, removed }`，不显示时为 `null`；`dirty` 是否有未提交改动；`ahead` 当前分支领先比较基准的提交数；`branch`、`base` 供面板写说明，没有时为 `null`。不是 git 仓库的工作区 `stat` 为 `null`、`dirty` 为假。未知的工作区应答 `workspace_not_found`。连接断开时一并停止；重连后界面重新发。
  - `watch_diff(target)`：`target` 为 `{ workspaceId, mode: "uncommitted" | "base" }` 或 `null`（关面板）。一个连接同时只看一个面板。宿主推 `diff_updated { workspaceId, mode, files, tooLarge, error }`，变化时再推（150 毫秒防抖）。`error` 为 `null` 或 `not_git` / `failed`。每个文件 `{ path, oldPath, status: added | deleted | modified | renamed, added, removed, content: text | binary | too_large, hunks }`，hunk `{ oldStart, oldCount, newStart, newCount, lines }`，行 `{ kind: add | del | context, oldNumber, newNumber, text }`。
  - 这两种推送不带序号：都是整份的最新状态，丢了一条下一条照样对。
- 宿主跑的 git 命令都是固定参数，不带用户给的路径；git 的输出、文件路径不进日志，失败只记命令和原因（security.md"子进程与文件"）。照抄时避开 Paseo 的三个已知问题：重命名文件的 diff 带上旧路径；未跟踪文件超过累计上限时也保留占位；"未提交"面板也随提交和 reset 刷新（监听元数据目录）。

### 状态栏（M1.8，2026-10-10 定）

产品层面的规则见上文"对话区"的"状态栏"和"关键流程"的"上下文分段"，这里写宿主和协议怎么做。数据对照 pi 1.1.0 源码（pi-internals.md §2"统计"）。

**会话的指标**

- 会话快照新增 `metrics`，变化时推整份 `metrics_updated { metrics }`。和 `model_updated` 一样是会话事件（带 `epoch + seq`，只发给订阅了这个会话的连接），快照之后的按序号接上。
- `metrics` 各项都允许未知（`null`），界面显示"—"：
  - `turns`、`steps`、`tokens`、`cost`：来自 `get_session_stats`，还没读到时为 `null`。`turns`、`steps` 是 `userMessages`、`toolCalls`；`tokens` 是 `{ input, output, cacheRead, cacheWrite }`（整个会话文件，含其他分支和压缩消耗），卡片标"本会话累计"；总量是四项之和，缓存命中 = `cacheRead` ÷（`input` + `cacheRead` + `cacheWrite`），分母为 0 时未知；`cost` 是美元，按 API 价格折算。
  - `reasoning`：会话文件里所有助手消息 `usage.reasoning` 之和（pi 的统计没有这一项；它已经算在输出里），没有一条消息报告时为 `null`，卡片不显示"其中推理"。
  - `branchTokens`：当前分支上助手消息 `usage` 四项之和，卡片另起一行"当前分支"。
  - `context`：`{ tokens, window, system, tools }`。`tokens`、`window` 是 `get_session_stats` 的 `contextUsage.tokens`、`contextWindow`；pi 没给 `contextUsage` 时（没有模型、模型没有上下文窗口）整项为 `null`；压缩后到下一次回复前 `tokens` 为 `null`。`system`、`tools` 见下文"上下文分段"，还原不出来时为 `null`，卡片只显示总量。
  - `timing`：`{ modelMs, ttftMs, tps }`，宿主存活期间这个会话一次请求都没测到时整项为 `null`（宿主重启后、刚打开的会话）。
- **什么时候读**：会话的 pi 启动后、每条助手消息的 `message_end`、`compaction_end`、`agent_settled`、换模型或推理强度之后，宿主调一次 `get_session_stats`。同一会话同时只读一次，读的期间又要读时，读完再读一次。读失败只记日志（命令和原因；pi 退出或被停掉造成的不记，它的退出另有记录），保留上一次的值；pi 退出后指标保留最后的值。`reasoning`、`branch` 和上下文分段在取条目之后重算，不问 pi。算出的 `metrics` 和上一次推的一样时不推。

**宿主计时**

- pi 没有"请求已发出"的事件：`message_start` 要等服务商的响应头回来才发。所以一次请求从 pi 的 `turn_start` 算起（pi 发出它之后接着准备并发出请求），其中的上下文压缩（`compaction_start` 到 `compaction_end`）不算。
- TTFT：请求开始到这条助手消息的第一个增量（文字、推理或工具调用的参数）；卡片显示宿主存活期间这个会话所有请求的平均。没有增量就结束的请求（出错、被停止）不算进平均。
- 模型用时：每次请求从开始到助手消息的 `message_end`，累加，出错和被停止的请求也算。
- TPS：最近一次有输出的回复的 `usage.output` ÷（`message_end` − 第一个增量）；时长为 0 时不更新。
- 计时只在宿主内存里，按会话存，宿主重启后为空。

**上下文分段**

- 宿主沿当前分支回放：从最近一条压缩条目的 `systemMessage`（完整的检查点）开始，没有压缩就从头；之后每条 `role: "system"` 的消息里，`content` 接在提示词后面，`sections` 按名字替换（值为 `null` 的删掉），`toolsAdded` / `toolsRemoved` 按工具名增删。和 pi-ai 的 `getCurrentSystemMessage` 一致，写在 `packages/pi` 里（运行时不依赖 pi 的包）。
- 估算和 pi 的 `estimateTokens` 一致：系统提示词 = （`content` 加各个 `sections` 的字符数）÷ 4，工具定义 = 工具声明 JSON 的字符数 ÷ 4，向上取整。对话消息 = `tokens` − 系统提示词 − 工具定义，小于 0 时按 0。
- 分支上没有系统消息（新会话第一次请求之前、pi 写系统消息之前的旧会话）时 `system`、`tools` 为 `null`。

**显示哪些分组**

- Preferences 新增 `statusBar`：`{ [分组 id]: boolean }`，只记你改过的；没记的按注册表里的默认。这样以后新加的分组照它自己的默认显示。`set_preferences` 多了 `statusBar`，整份替换；"恢复默认"发 `{}`。不认识的 id 原样保留（降级再升级不丢）。
- 注册表在界面包里：每组 `{ id, name, description, defaultVisible, summary, detail }`，按注册顺序显示。摘要和卡片的写法照原型（`prototype/ui` 分支的 `app-prototype.html`）。

新增事件：`metrics_updated`。`set_preferences` 多了 `statusBar`。会话快照多了 `metrics`。

### 并行、同步与关注（M1.9，2026-10-10 定）

产品层面的规则见上文"侧栏"的"收件箱""会话状态""命名"和"关键流程"的"在终端中继续""同步与断线重连"，这里写宿主和协议怎么做。

**列表的增量**（取代 M1.5 每次推整份快照，界面不用改）

- `subscribe_index({ cursor? })`：`cursor` 是客户端上次收到的 `{ generation, seq }`。宿主按情况回一份快照 `index_snapshot`（带 `reason`：`no_cursor` 没有游标、`generation_changed` 宿主重启过、`cursor_expired` 游标比宿主记得的还早、`too_many_changes` 变化超过 200 项）或一份增量 `index_changes`。
- 之后有变化就推 `index_changes`：`projects`、`workspaces`、`sessions` 各是 `{ upsert, remove }`（整项替换、按 id 删除），`layout` 是这个客户端自己的布局、`preferences` 是偏好，没变时为 `null`。和快照一样，30 毫秒内的变化合成一批。
- 宿主不让各个模块报告"改了什么"：IndexFeed 每批重新算出整份列表，和上一批逐项比较（按 id，比较整项内容），得出新增、修改、删除。每批有变化就 `seq` 加一，所有订阅者共用这个序号；一批里没有一个订阅者相关的内容（比如只改了别的客户端的布局），就不发给它，它的序号随之跳过，不算缺口。
- 宿主记住每一项最后一次改动时的 `seq`，以及最近 1000 次删除；重连时"游标之后的变化"就是改动序号大于游标的项加上之后的删除。更早的删除已经忘掉时回快照（`cursor_expired`）。在线推送也一样：订阅者上次收到的序号早于已经忘掉的删除时，推给它一份快照（`cursor_expired`），不推增量（2026-10-10 审查后补：一批里删除超过 1000 项，比如移除一个有上千会话的工作区，增量会漏掉前面那些删除）。补发的增量总是带上这个客户端当前的布局和偏好。
- WebSocket 在一条连接里不丢不乱，所以序号只用作重连时的游标，客户端不按它找缺口。客户端收到的增量 `generation` 和自己的不同时丢掉（不会发生，宿主重启必然换连接）。
- 列表的顺序：项目按登记顺序，新增的项接在末尾；工作区、会话由界面自己排。`resets` 只在快照里。
- 先读到自己的写（2026-10-10 定，三个会话并行的端到端测试发现：快速切标签时，界面先乐观地切过去，随后到来的、宿主在处理这条命令之前就算好的布局把它切回去，对话区"显示出来就 `open_session`"又把旧标签写回宿主，用户的点击就丢了）：
  - 宿主在应答任何命令之前，如果有还没推出去的列表变化，先把这个连接的那一批立即推给它（不等 30 毫秒），所以客户端收到应答时，列表和布局已经反映了这条命令。别的连接照旧等这一批。
  - 客户端在自己的布局命令（`open_session`、`close_tab`、`select_container`）还没应答时，增量和快照里的布局只记下、不采用，界面保持乐观的样子；最后一条应答到了（成功、失败或断线），换成记下的宿主布局。命令失败时乐观的改动也就随之撤回。只记宿主真正发来的布局：增量的 `layout` 为 `null` 时记下的不变（2026-10-10 审查后补：否则会把界面上乐观的布局当成宿主的记下，失败时撤不回去）。

**会话状态**

- `SessionSummary` 去掉 M1.6 的 `failed`，换成：
  - `attention`：关注状态 `{ reason: "error" | "auth", at, cleared }`，没有为 `null`。
  - `asking`：最早一个还没回答的对话框是什么时候出现的，没有为 `null`（只在宿主内存）。
  - `handedOff`：已交给终端（见下文）。
- 关注状态写进 `sessions.json` 的会话记录（新增可选字段，不升版本；没有记录的会话补一条，和归档一样）。按边沿设上：一次运行以失败结束（pi 的重试用尽）、连续崩溃 3 次用尽时设上，`at` 是设上的时间；下一次运行开始时去掉。失败的原文像认证问题时 `reason` 是 `auth`，否则是 `error`：不分大小写含 `No API key`、`OAuth`、`401`、`unauthorized`、`authentication`、`invalid api key` / `invalid_api_key`、`/login` 之一（pi-internals §3"一次性调用"）（尽量识别，认错了也只是图标不同）。
- `clear_attention(sessionId)`：把 `error` 标为已清除（`cleared: true`），出错图标留到下一次运行开始；`auth` 不因为看了一眼就清，要等下一次运行开始（问题解决了才能跑起来）。客户端在会话显示出来时发：它是当前容器的激活标签、窗口有焦点、`attention` 是没清除的 `error`；窗口重新获得焦点时再看一次。
- 状态的优先级（界面从摘要派生）：待回答（`asking`）> 待授权（`attention.reason` 为 `auth`）> 出错（`attention.reason` 为 `error`，不论是否已清除）> 运行中 > 空闲。图标：问号圆圈（橙）、钥匙（橙）、感叹号圆圈（红）、转动的圆弧（强调色）。
- 工作区和项目（收起时）的状态由界面从会话摘要算出：取其中没归档的会话的最高优先级（2026-10-10 改，原先打算由宿主计算：客户端本来就有全部摘要，算法只有一处）。

**收件箱**

- 收没归档的、待回答、待授权、或出错且没清除的会话；按优先级，再按时间（新的在前）排。时间取 `asking` 或 `attention.at`，显示成"12 分钟前"。
- 布局、点击、展开收起照上文"侧栏 · 收件箱"。点击发 `open_session`（打开标签、激活、切到它的容器）。
- 收件箱行选中：它是当前容器的激活标签。收起的项目里有选中的工作区时，项目行带选中底色。

**后台运行**：会话的运行不依赖订阅和标签：切换标签、切换容器、关闭标签都只改布局，运行和 pi 照常（M1.5 起就是这样，本里程碑补上同时运行三个会话的端到端测试）。

**对话记录的同步**

- 客户端只订阅当前容器的激活标签（打开着、看得见的那个）。快照之后按 `seq` 接事件；`epoch` 变了或 `seq` 不连续时，重新订阅这个会话，拿一份新的快照（M1.3 起就是这样）。
- 不做按 `seq` 往后补拉（原先打算的 `fetch_transcript` 的 `after`，2026-10-10 定不做）：宿主不留事件历史，一个会话的快照本来就只有最近 20 轮，补拉和重拿快照代价相当。往上翻仍用 `before`。
- 断线重连（宿主没重启）：重新订阅列表（带游标）和当前会话（拿快照）；乐观显示的消息按 `clientMessageId` 和快照里的轮对上，没对上的保留为待发（M1.3 起就是这样）。断线时结果未知的命令不重发。
- 宿主重启后（`hostInstanceId` 变了）：列表拿新的快照；当前会话的视图先标为已失效，界面随即对它重新 `open_session` 并订阅（取代 M1.3 只标"已失效"、等下一次发消息再开）。重启前正在跑的运行已经随旧宿主结束（宿主退出时停掉了 pi），重建出来那一轮是"已停止"；宿主内存里的排队、对话框、当场计时都没了（"数据归属"）。

**交给终端**

- `hand_off(sessionId)`：把会话交给终端里的 pi。草稿应答 `session_is_draft`；正在运行、提交（消息发出到运行开始之间，包括 pi 已应答 `started` 而运行还没开始）、停止、重启，或宿主排队里还有消息时应答 `session_busy`（先停止或清空）。菜单项在同样的情况下置灰：界面按会话的运行、发送、停止、重启和排队判断（2026-10-10 审查后补）。其余情况：会话记录写上 `handedOff: true`，停掉 pi（没回答的对话框作废），应答 `{ file }`。界面把 `pi --session '<文件>'`（单引号转义）复制到剪贴板。
- 交接之后：标签照常可以打开，`open_session` 只改布局、不启动 pi；对话区不显示对话记录和输入框，只显示"已在终端中继续"、命令（可再复制）和"在 Atrium 里继续"。会启动 pi 或写会话的命令（`prompt`、`steer`、`resume_queue`、`retry_run`、`rename_session`、`set_model`、`set_thinking_level`、`list_commands`）应答 `session_handed_off`。标记写在索引里，宿主重启后仍在（2026-10-10 定：两个 pi 同时写一个会话会悄悄分叉，不能因为切到标签就自动开起来）。
- 同一会话的 `hand_off` 和 `take_back` 依次处理，后一条等前一条做完（2026-10-10 审查后补：交接停 pi 的途中拿回来，会拿到正在关闭的旧 pi、不另起，之后再发消息就在 Atrium 里起新 pi，和终端里的 pi 同时写）。
- `take_back(sessionId)`：去掉标记，重扫会话文件，用 `--session` 启动 pi（`epoch` 加一，订阅者拿到新的快照）。失败的原因和 `open_session` 一样（例如目录不存在）。终端里的 pi 还开着时两边会同时写，界面在按钮旁提示先退出终端里的 pi。

**自动生成标题**

- TitleGenerator（宿主 `sessions/`）：会话一次运行结束（`run_settled`，任何结果）时，会话没有名字、已经写出文件、没交给终端、第一轮有文字，且这个会话没在生成，就生成一次。失败（模型出错、超时、pi 退出）只记日志，下一次运行结束再试。只在 Atrium 里跑过的会话才会触发，历史会话不补。
- 输入：第一轮的用户消息文字和回复（这一轮最后一段文字），总长截到 2000 个字符，用户消息最多占 1200。
- 调用 OneShotPi（`packages/pi` 的 `oneshot/`）：在会话的工作目录、用和会话的 pi 相同的环境运行 `pi --mode json -p --no-session --no-tools --thinking off --model <服务商>/<模型> --system-prompt <标题要求>`，对话内容从标准输入给（不放进参数，`ps` 看得到参数）。模型用偏好里的 `titleModel`，为空或它的服务商已退出登录时用会话当前的模型（见"设置"）。"已退出登录"按 pi 的模型列表判断：`titleModel` 不在会话目录的模型列表里（对话用对话目录的列表，和模型面板同一份缓存），或查不到列表时，就用会话的模型（2026-10-11 定）。取最后一条助手消息的文字；`stopReason` 为 `error` / `aborted`、退出码不为 0、60 秒没结束（停掉整棵进程树）都算失败。
- 标题要求：和用户消息同一种语言、中文不超过 16 个字、不带标点和引号、只输出标题。宿主再整理一遍：取第一行，去掉首尾空白、成对的引号和末尾的标点，超过 50 个字符截断；整理后为空算失败。
- 写回：用会话自己的 pi 发 `set_session_name`，然后重扫会话文件，列表随之更新。写之前再看一次：已经有名字（生成期间手动改过名）、pi 已退出、已交给终端时丢弃结果。手动改名从 `rename_session` 收到就算有名字，不等重扫会话文件（2026-10-10 审查后补：改名应答之后、重扫之前标题刚好生成好，会盖掉手改的名字）。
- 测试用的 faux 模型：脚本多一个可选的 `title`，`-p` 模式下的 pi 用它回答；没写 `title` 时回一个错误，标题保持兜底，不影响别的测试。

新增命令：`clear_attention`、`hand_off`、`take_back`；`subscribe_index` 多了 `cursor`。新增事件：`index_changes`；`index_snapshot` 多了 `reason`。`SessionSummary` 去掉 `failed`，多了 `attention`、`asking`、`handedOff`。新增错误码：`session_handed_off`。

| `model_updated` | 会话当前的模型和推理强度变化（M1.7，见上文"模型与输入框"） |
| `metrics_updated` | 状态栏各分组的最新取值（区分本会话累计与当前分支，允许未知；M1.8，见上文"状态栏"） |
| `notice` | 系统事件：上下文压缩（带压缩前 token 数）、自动重试（第 N / 3 次）、进程自动重启；extension 通知原文 |
| `session_exited` | pi 进程退出，带原因 |
| `response` | 每条命令的应答，带 `requestId`；成功带 `result`，失败带错误码（见上文"应答"） |

## 备选方案

| 方案 | 为什么不用 |
|---|---|
| SDK 嵌入 pi | 见 ADR-0002，放弃进程隔离 |
| Atrium 自己保存对话记录 | 和 pi 的会话文件重复，两份数据会不一致；对话历史归 pi（见 [架构总览](../architecture/overview.md)） |

## 风险与待定问题

- [ ] **没有审批的风险**：agent 可能误删文件或执行危险命令。缓解：MVP 1 只在 git 仓库里使用，出问题用 git 回滚。
- [x] **pi 适配器用 pi 自带的 `RpcClient`，还是自己实现 JSONL 客户端**：自己实现（2026-10-04 定，对照 pi 1.0.1 的 `rpc-client.ts`）。`RpcClient` 没有发送 `extension_ui_response` 的方法（`send()` 是私有的），做不了需求 10；它还写死了 `node <cli.js>` 的启动方式、每条命令 30 秒超时（`compact` 会超）、无限增长的 stderr，并要依赖整个 `pi-coding-agent` 包。自己实现约 300 行：直接启动 `pi --mode rpc`，按命令设超时，stderr 只留最近一段、其余写日志，退出时先关 stdin、再 SIGTERM，最后连同所有后代的进程组一起 SIGKILL（2026-10-04 实测后细化，见 pi-internals §3"退出"）；分帧照搬 pi 的 `jsonl.ts`（MIT，只按 LF 切行）；类型用 `import type` 从固定版本的 pi 包取，只在开发时安装。Paseo 也是自己实现。
- [x] **包管理器**：pnpm workspaces。
- [x] **UI 组件库和状态管理**：组件用 shadcn；`client` 用 Zustand 的 `zustand/vanilla`（2026-10-04 定）：约 1KB、不依赖 React 和 DOM，UI 用 `useStore(store, selector)` 订阅。按领域拆 store：列表（项目、工作区、会话摘要）、每个会话一个（订阅时创建、退订时释放）、布局；流式增量只复制当前那条消息，其他轮次引用不变；选择器返回对象时用 `useShallow`；不引入 Immer。备选里自己写 store 要重做选择器和 devtools，MobX / Valtio 的可变代理不利于按序号整段替换，Jotai 围绕 React 设计，Signals 接 React 不顺。
- [ ] **pi 版本兼容**：会话文件格式和 RPC 都可能变化。宿主启动时检查 pi 版本，低于最低版本就提示升级。
