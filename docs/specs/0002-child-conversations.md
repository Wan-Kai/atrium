## 背景与目标

Atrium 里一个会话一个 pi 进程，多开几个会话并行做事已经可以，但会话之间没有关系：另开一个会话查东西、让别的模型审查，结论要手动复制回来；几个会话的状态散在标签和收件箱里，看不出哪些是为同一件事开的。自用时这些事在 Paseo 里做（子代理审查、交接、委员会），见 [multi-agent.md](../research/multi-agent.md)。

目标分两步：

1. **用户开子对话**：在一个会话里开子对话，子对话的状态汇总到主对话，结论一键带回主对话。只用到宿主到扩展的隐藏命令（已有），不用来回的通道。
2. **agent 开子对话**：主对话的 agent 自己开子对话、发消息、拿结果，过程轨道上看得到它分出去、合回来。需要 Atrium 自带扩展里的工具和一条扩展与宿主之间有来有回的通道（ADR-0012）。

第二步不等插件系统（2026-10-16 定）：子对话的主体是宿主的会话、索引、关注和排队，工具放在 Atrium 自带的扩展里（ADR-0008、ADR-0010 的做法），不走第三方插件的打包接口；第二步依赖的扩展通道是 MVP 2 本来要定的，这个里程碑先定（ADR-0012），MVP 2 的上下文检查器沿用。两步都在 M1.15 里做（2026-10-16 定）。

## 非目标

- 子对话之间平级通信、共享任务列表（Claude Code 的 agent teams）。
- 不相干的两个会话之间通信（`@会话` 授权、来源标注、接收方的接受 / 先问我 / 拒绝）：以后单独设计。
- 父 agent 替用户回答子对话的审批或提问：**不做**。
- 审批本身（MVP 2）；用户自定义角色文件；定时唤醒（heartbeat）。

## 需求

1. 当我在一个会话里想并行查另一件事，我希望从这里开一个子对话（可以带上到某一轮为止的对话），主对话不受影响。
2. 当子对话在跑、在等我、或出错了，我希望在主对话里一眼看到，不用逐个切标签。
3. 当子对话做完了，我希望一键把它的结论带回主对话，由我决定发不发。
4. 我希望打开子对话直接和它说话，也能一步回到主对话。
5. 当我归档主对话，我希望它的子对话一起收好。
6. （第二步）当我让 agent 并行调研、或交给另一个模型审查，我希望它自己开子对话、等结果、汇总，过程轨道上看得到。
7. （第二步）当子对话需要回答或批准时，我希望问的是我，而不是让主 agent 代答。

## 方案设计

### 概念

- **子对话就是一个普通会话**，多一个"父会话"。它有自己的 pi 进程和会话文件，打开、发消息、停止、交给终端、导出全都照旧。和分叉的区别：分叉出的会话和原会话平级、没有关系；子对话可以选择带上下文（你手动开的用分叉同一套做法，agent 开的见"带上下文的子对话（agent 开的）"），但始终挂在父会话下面。
- **谁开的**：子对话的记录里 `by: "user" | "agent"`，只在创建时写。
- **名字**：建子对话时就定下（用户开的由你填，界面给建议名；agent 开的由 `agent_spawn` 必填的 `name` 参数定下句柄，记在记录的 `handle` 里、之后不变，显示名一开始等于句柄，见"第二步 · 工具"），显示名先记进 Atrium 的会话记录（`name`）；pi 第一次起时用 `--name` 写进会话（只在第一次，之后每次都加会多写一条），会话文件写出之前摘要用记录里的名字。子对话一开始常是草稿（只有自定义消息时 pi 还不建文件），SPEC-0001 的"草稿不能改名"对子对话例外：名字存在记录里。不等自动标题：agent 开的子对话做完一轮就停 pi，标题写不回去。
- **层数**：agent 开的最多 2 层，主对话 → 子对话 → 孙对话，孙对话的 agent 不能再开（2026-10-16 定）。用户手动开的不限层数（2026-10-16 定）。合起来按"agent 层数"算：
  - 没有父会话，或 `by` 是 `user`：0；`by` 是 `agent`：父会话的 agent 层数加 1。
  - agent 层数小于 2 的会话才有开子对话的工具。例：主对话 0、agent 开的子对话 1、agent 开的孙对话 2（没有工具）；你在孙对话下手动开的 0，它的 agent 又能往下开两层；脱离后的会话没有父会话，是 0。
  - 层数在起 pi 之前算好，决定启动参数（见"第二步 · 角色与限制"）；之后关系变了（脱离）在 pi 下次启动时生效，工具调用到了宿主照样按当前关系再查一遍。
  - 父会话链成了环（索引被手改）时按断开处理：走到见过的会话就停，当作没有父会话。索引损坏被重置后父子关系全丢，都算普通会话。
- **数量**：agent 开的，**每个父会话同时没结束的最多 6 个**；用户手动开的不算（2026-10-16 定）。"没结束"是：创建中、提交中、在跑（含挂着 `ask_parent` 等主 agent 回答）、排队里有待处理的（排队没暂停时）、在等你回答、在停止、pi 在重启。一轮做完空闲、被停下（排队暂停，哪怕里面还有消息）、崩溃用尽、交给终端、归档的不占名额。agent 让子对话干活（`agent_spawn`、`agent_send`、给被回收的子对话送通知而起 pi）时在受理那一刻占名额（见"角色与限制 · 名额"）；你自己在 agent 开的子对话里发消息、恢复排队、重试不受这个上限挡（上限管的是 agent 自己开的量），但它在跑时照样占名额。
- **位置和归属分开**（参照 Paseo）：子对话可以在父会话的容器里，也可以在同一项目新建的 worktree 工作区里；放在哪不改变它属于谁。父会话在对话（chat）里、或项目不是 git 仓库时，只能放在同一个容器。
- **新 worktree 的起点**（2026-10-16 定）：父会话所在工作区当前的提交。宿主在父会话的目录里取 `HEAD` 的完整提交号（`detached HEAD` 也行），作为只在宿主内部用的起点交给新建 worktree 的那一套，并记成工作区的 `baseCommit`（合并状态照它判断）；不经 `create_workspace` 的 `base`，那里的 `HEAD` 是项目主目录的。父会话没提交的改动不会带过去。分支名按 SPEC-0001 AI 起的分支名那样整理（去空格、转成合法的 ref），重名时同时避开已有的分支和目录（目录只取分支名的最后一段，也要避开已归档工作区占着的目录），加序号；整理后不到 2 个字符（比如名字全是中文）时，用 SPEC-0001 的随机名。

### 第一步：用户开子对话

**入口**（样式待原型）

- 回复下方那一行，分叉旁边加"开子对话"：带上到这一轮为止的对话。这一轮后面紧接着的是由通知开头的一轮时不能从这里开（pi 的 `fork` 只认用户消息），按钮变淡；SPEC-0001 的"从这里分叉"同样变淡。
- 标签栏"+"旁的菜单，或输入框的 `/` 菜单里的"子对话"：开一个空的子对话，挂在当前会话下面。
- 新建时可选位置：当前容器（默认）或新建 worktree（分支名由你填，界面给建议名）。只能放同一容器时（见"概念 · 位置"）没有"新建 worktree"。
- 带上下文的只在父会话空闲时能开（同分叉：在跑、在停止、在压缩、pi 在重启应答 `session_busy`，交给终端应答 `session_handed_off`）。空的子对话随时能开。父会话是草稿时两种都不行（`session_is_draft`）。
- 子对话打开成标签并切过去；在别的工作区时切到那个工作区。子对话里还能再开子对话，层数不限。

**带上下文的子对话怎么做出来**（2026-10-16 按 pi 源码和现有分叉核实，三方审查后定）

- 同容器：沿用 SPEC-0001 的分叉（`forkWithPi`）：另起一个临时 pi 做 `fork`，最后一轮用 `clone`，原会话的 pi 不动（pi 的 `fork` 会把执行它的进程换到新文件上，所以不能在父会话自己的 pi 里做）；从检查通过到临时 pi 停掉父会话算忙；轮的起点照分叉复制。不同的只是宿主同时写下子对话的会话记录（`parent`、`by: "user"`、名字），分叉现在不写记录。
- 新建 worktree：
  1. 临时 pi 加 `--session-dir <宿主在系统临时目录下新建的目录>`，`fork` / `clone` 出的中间文件写在那里，扫描看不到、终端里的 pi 也不会去打开。临时目录名带宿主的固定前缀，并写一个标记文件；启动时只清带这个标记的。
  2. 宿主建好 worktree 工作区（起点见"概念"），生成子对话的会话 id，写下记录。
  3. 在新 worktree 里以 `pi --mode rpc --fork <中间文件> --session-id <id>` 起子对话的 pi。pi 以它启动的目录为新会话的 `cwd`，复制中间文件的全部条目（条目 id 不变），在进入 RPC 之前就写出会话文件。轮的起点复制到这个 id 上。
  4. `get_state` 成功后删掉临时目录。
  - 子对话会话头的 `parentSession` 指向已经删掉的中间文件；Atrium 的父子关系以索引为准，不读它（写进 pi-internals）。
  - 历史里的绝对路径（工具参数、输出）还是原目录的。可写的模型可能照着改回原目录，工具限制管不了这个。所以宿主在子对话里先送一条说明（经隐藏命令交给扩展，作为自定义消息给模型看，界面显示成一行提示，见"对话记录里的自定义消息"）：历史里的路径属于原来的目录，这个对话在新目录里工作。系统提示词的 `cwd` 分段 pi 在下一次请求前自动补成新目录。新 worktree 的项目设置要等 pi 信任这个目录才生效，同 SPEC-0001 新建的 worktree。
  - 失败时：先停掉这次起的子对话 pi，删掉临时目录。会话文件还没写出的，删掉会话记录；已经写出的（pi 在应答 `get_state` 之前就写了），记录留着，子对话照样挂在父会话下、可以打开，问题行说明"子对话没有开好"；不拿同一个 id 再起一次 `--fork`（pi 会报会话已存在）。worktree 已建好的留着（同 SPEC-0001 新建工作区失败时）。应答 `fork_failed`；建 worktree 本身的失败照 SPEC-0001 原样应答（`branch_exists`、`branch_invalid`、`worktree_create_failed`）。

**显示**

- **子对话的标签**：标题前一个"↳"标记。对话区顶部一行面包屑"主对话名 › 子对话名"，点前面的名字切回去；超过三层时中间收成"…"："根对话 › … › 父对话 › 当前"，点"…"列出中间各层。
- **子对话条**：主对话的输入框上方（排队面板之上），没有子对话时不出现。收起时一行：计数加各状态的图标，例如"子对话 3 · ◌ 1 · ? 1"，图标和侧栏的会话状态一致（形状区分，不只靠颜色）。展开后每个子对话一行：状态图标、名字、位置（在别的工作区时写工作区名）、更新时间、"带回"按钮，行末菜单是打开、脱离、归档。点行打开子对话。只列直接的子对话；有孙对话的行末尾写"+N"，行的状态图标汇总它整棵子树。按创建时间排序，归档的不列。
- **主对话标签的状态图标**：取主对话自己的状态，和所有子孙对话里"待回答 / 待授权 / 出错"的最高优先级；子对话"运行中"不抬高主对话（运行中只在子对话条里看）。由界面从摘要算，同工作区的汇总（SPEC-0001"并行、同步与关注"）。
- **收件箱**：子对话的待回答、待授权、出错照常进收件箱，行里写"工作区 · 主对话名 › 子对话名"。以后加的"已完成未读"（`finished`）不进收件箱，只在子对话条里标一个点：主对话会处理它（参照 Paseo 不让子代理打扰用户）。
- **"历史"和搜索**：子对话照常列出，名字前加"↳"，悬停说明属于哪个主对话。

**用量合计**

- 主对话状态栏的 Token 用量和费用卡片里多一行"含子对话"：主对话自己加上所有子孙对话**新产生的** token 和费用（2026-10-16 定）。摘要（状态栏上那一行字）不变，仍是这个会话自己的。没有子对话时这一行不显示。
- 带上下文的子对话复制了父会话到分叉点为止的条目，pi 的统计把文件里所有用量都算进去，直接加会重复。所以子对话的记录里存一个基线 `usageAfter`：分叉出的文件（新建 worktree 时是中间文件）里最后一条条目的 id，包括 pi 分叉时新加的 label 条目；只算这条之后的。空的子对话和 agent 开的不带上下文的子对话没有复制历史，`usageAfter` 是 `null`，从头全算；agent 开的带上下文的同样记基线（见"第二步 · 带上下文的子对话"）。
- 算法和 pi 的统计一样：助手消息、压缩、分支摘要、`usage` 条目、带用量的工具结果都算，token 和费用都取条目里记的原值（pi 包读条目时要多读出费用，现在只读 token）。
- 数字由宿主读会话文件自己加（同对话记录的增量读取），不靠子对话的 pi 在跑：没起过 pi 的、交给终端后接着用的都算得准。不往 `sessions.json` 里写高频数字。脱离的子树不再算进原来的祖先。

**带回主对话**

- 子对话条的"带回"和子对话面包屑旁的"带回主对话"：把子对话最后一轮回复的 Markdown 原文填进主对话的输入框，切到主对话。回复由宿主从子对话的会话文件读出（新命令 `read_last_reply`，子对话的 pi 不用在跑）；文字由界面拼：第一行"子对话「名字」的结论："，下面是回复；超过长粘贴的阈值（8 行或 800 字）时收成长粘贴胶囊（SPEC-0001"模型与输入框"）。宿主不产出文字。
- 只填进输入框、不直接发：你可以删改、补一句再发。主对话在跑时按平常排队或插话。
- 子对话还没有回复（还没跑完一轮、最后一轮失败且没有文字）时，点了在问题行说明"子对话还没有结论"，输入框不动。

**归档、脱离、交接**

- 规则从被归档的那个会话往下算，不管它自己是不是子对话：它的子孙里和它在同一个容器的（含草稿）一起停掉并归档；在别的容器的那一支改为脱离（脱离的那个会话变成普通会话，它下面的关系不变），不归档（参照 Paseo：那边可能还要接着用）。在跑的先停再归档，同 `archive_session`。
- 三个入口都走这一套：`archive_session`、归档对话（`archive_chat`）、归档工作区。开始时先把整棵要处理的子树记成"归档中"，期间这棵树里不能开新的子对话、不往这棵树里的会话送通知（同 2026-10-14 给工作区归档补的规则）；收件人被归档的待送达通知删掉。被归档的子对话的父会话不在这次归档里时，照常收到 `ended`（第二步）。
- 归档工作区时，别的容器那一支的脱离在 `git worktree remove` 成功之后才做；删失败时 SPEC-0001 会撤掉归档标记，脱离也就没做。
- 恢复对话或工作区时只恢复那次归档记下的会话（SPEC-0001 已有），被脱离的不挂回去。
- 脱离：去掉父会话，变成普通会话。只由用户在子对话条的行菜单里做，不给 agent 工具。脱离后 agent 层数从 0 算，下次起 pi 时生效。
- 交给终端只影响它自己；子对话条里它的行显示"已在终端中继续"。复制给终端的命令带上它的工具参数（见"角色与限制"）；这在终端里只是建议，你可以删掉。

### 对话记录里的自定义消息（第一步就要）

- 现在一轮是"一条用户消息到下一条用户消息"（domain-model §2），pi 的自定义消息在 pi 包里落成"其他"条目、实时事件也不翻译。Atrium 自己的自定义消息统一用 `customType: "atrium-agent"`，`details.kind` 分三种：
  - `note`：宿主给模型的说明（新 worktree 子对话的路径说明）。界面画成一行提示，不开新的一轮。
  - `task`：主对话的 agent 交代给子对话的事（第二步）。
  - `report`：子对话发回给父会话的通知（第二步）。
- pi 包的会话条目和实时 `message_end` 保留这些自定义消息（`details` 里的结构化数据，不含给模型的外壳文字）。
- 由 `task` 或 `report` 开头的运行算一轮，轮的开头不是用户消息而是"来自主对话的 agent"或"来自子对话「名字」"；运行中 steer 进来的是这一轮里的一个步骤，画法同插话。协议里 `Turn` 的开头和步骤各加一种，协议版本加一。
- 重建对话记录、实时显示、重试、导出都认这几种；pi 的 `fork` 不认这种轮的开头，"从这里分叉""开子对话"在它前一轮变淡（见"入口"）。

### 第二步：agent 开子对话

**工具**（Atrium 自带扩展注册，只在 Atrium 宿主下加载：扩展只经宿主的 `--extension` 加载，终端里的 pi 本来就没有。2026-10-16 对照 pi 官方示例、pi 社区四个热门子代理包、Paseo、Codex、Claude Code 定，见 [multi-agent.md](../research/multi-agent.md) §7；2026-10-17 按三方审查修订）

设计原则：一个动作一个工具、参数少、必填清楚（官方示例和 `pi-subagents` 一个工具扛多种模式，模型常传错）；用不变的句柄寻址，调用方是谁由宿主按 pi 进程认定，不从参数里读；默认后台跑、做完通知、不轮询，另给一个等待工具用于"派出几个、等齐再汇总"；子对话有自己往回说话的工具，最终回复就是交付；结果截断、按页读全文。后续要用的信息（句柄、会话 id、任务 id、实际的模型和档位、状态）都写进给模型的文字里：pi 只把工具结果的文字发给模型，`details` 只给界面和重建用。

**句柄与显示名**

- agent 开的子对话有两个名字。句柄存在记录的 `handle` 里，由主 agent 在 `agent_spawn` 时起，之后永远不改，只用来寻址，分支名 `agent/<handle>` 也用它。显示名就是会话名，一开始等于句柄，你可以随时重命名，只影响界面和通知里的称呼。
- 句柄在同一父会话下永不重复：父会话的记录里存一份用过的句柄（`usedHandles`，只增不减），脱离、归档、记录没了都还占着。重名应答 `agent_name_taken`。
- `to` 只认两种写法：句柄，或 `id:<会话 id>`（`agent_spawn` 返回，也不变）。句柄的格式和会话 id 撞不上前缀 `id:`，所以没有歧义。`agent_list` 和每条通知同时给句柄、显示名和会话 id。改了显示名，主 agent 照样用句柄找得到。

**推理档位**：用 pi 的档位名 `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`（2026-10-16 定，和 pi、Claude Code、Codex 及社区插件一致）。每个模型支持的档位不同（pi 的 `getSupportedThinkingLevels`：不支持推理的只有 `off`，`xhigh`、`max` 要模型声明），`agent_models` 列出来。pi 对不支持的档位会悄悄往上（再往下）换一档，模型不知道；Atrium 不这样：指定了不支持的档位应答 `agent_thinking_invalid`，参数带这个模型支持的档位。不指定时沿用主对话当前的档位，按 pi 的规则换成新模型支持的档位，结果里写明实际用的是哪一档。

**任务**：每次 `agent_spawn`、`agent_send` 交代一件事，宿主给它一个任务 id（`taskId`）。事件、等待、通知都按任务算，不按会话算：同一个子对话先后交代了几件事，各算各的。

**主 agent 用的工具**（agent 层数小于 2 的会话才能用）

1. `agent_spawn`：开一个子对话。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `name` | string，`^[a-z][a-z0-9-]{0,39}$` | 是 | — | 句柄，见上 |
| `task` | string，1–32000 字 | 是 | — | 交代给它的第一件事，作为"来自主对话的 agent"的消息送进去，不走 `prompt` |
| `role` | `"explore"` \| `"work"` \| `"advise"` | 否 | `"explore"` | 见"角色与限制"（2026-10-16 定默认只读） |
| `context` | `"none"` \| `"fork"` | 否 | `"none"` | `fork` 带上本会话到这次调用为止的全部对话（2026-10-17 定，`pi-subagents` 的做法），见"带上下文的子对话（agent 开的）" |
| `place` | `"same"` \| `"worktree"` | 否 | 跟着角色 | 只读角色只能 `same`；对话里或项目不是 git 时也只能 `same` |
| `model` | string，`provider/modelId` | 否 | 本会话当前的模型 | 拿不准时先调 `agent_models` |
| `thinking` | 档位名 | 否 | 见"推理档位" | |
| `wait` | boolean | 否 | `false` | `true` 时等这件事出结果再返回 |
| `waitSeconds` | integer，30–3600 | 否 | 600 | 只在 `wait: true` 时有效；到时间只是不再等，子对话照跑，结果照常通知 |

返回（文字里都有，`details` 同样的字段）：

- `wait: false`：`{ name, sessionId, taskId, role, place, workspace?, branch?, model, thinking, status }`，文字末尾"已开始，做完会通知你；不要轮询、不要编造结果"。
- `wait: true` 出了结果：上面这些，加 `{ event, reply?, questionId?, question?, options?, progress? }`；回复截断到 4000 字，附 `agent_read` 的用法。
- `wait: true` 到时间：上面这些，加 `{ timedOut: true }`，文字"还在跑，结果会通知你"。
- 提前返回（见"等待的规则"）：加 `{ interrupted: "user_message" }`。

2. `agent_send`：给自己的子对话交代下一件事。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `to` | string | 是 | — | 句柄或 `id:<会话 id>` |
| `message` | string，1–32000 字 | 是 | — | |
| `wait`、`waitSeconds` | 同 `agent_spawn` | 否 | `false`、600 | `wait: true` 只等这条交代自己那件事，之前那件事的事件照常按通知送，不算这次的结果 |

对方在跑时排在它这次运行之后，不打断（Paseo 会打断并丢掉对方正在做的事）；对方做完了、被停下了，在同一个会话里带着完整上下文接着干（`pi-subagent-manager`、Claude Code 的做法）。返回：`{ to, sessionId, taskId, queued }`；`wait: true` 时形状同 `agent_spawn` 的 `wait: true`。

3. `agent_wait`：等子对话出结果（2026-10-16 定要这个工具）。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `tasks` | string[] | 否 | 自己所有还没出终态结果的任务 | 任务 id；同一批里刚开的子对话，最好把 `agent_spawn` 返回的任务 id 传进来 |
| `until` | `"any"` \| `"all"` | 否 | `"any"` | `all` 等每个任务都到终态（`finished`、`failed`、`stopped`、`ended`） |
| `waitSeconds` | integer，30–3600 | 否 | 600 | |

返回 `{ events: [{ name, sessionId, taskId, event, reply?, questionId?, question?, options?, progress? }], timedOut, pending: [taskId] }`（`question` 事件带问题的全文和可选答案）。名单为空立刻返回 `{ events: [], timedOut: false, pending: [] }`；不是自己的任务应答 `agent_not_allowed`。工具说明写明只在"派出几个、要等齐再汇总"时用，平时等通知。

4. `agent_reply`：回答子对话用 `ask_parent` 问的问题。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `to` | string | 是 | 句柄或 `id:<会话 id>` |
| `questionId` | string | 是 | `question` 事件里带的 |
| `answer` | string，1–8000 字 | 是 | |

- 回答经通道交给子对话 pi 里挂着的那个工具调用，不进排队。答了、超时、取消由子对话那边的扩展说了算：它收下回答（第一个有效的回答算数）后回报宿主，`agent_reply` 才返回 `{ delivered: true }`；问题已经超时、取消、答过，或者子对话的 pi 已经换了一个进程（宿主按进程代次判断），应答 `agent_question_closed`，提示"要补充就用 `agent_send`"。等确认最多 10 秒；等不到，宿主让子对话那边的扩展关掉这个问题，免得子对话还挂着、`agent_send` 又排在它后面：扩展回"已经收下"就返回 `{ delivered: true }`（回答进去了，只是回报慢了）；回"已关掉"就应答 `agent_question_closed`，子对话的 `ask_parent` 得到 `reason: "reply_failed"`，提示"主 agent 的回答没送到，按你的判断继续"。再等 10 秒扩展还不回（pi 卡住了），返回 `{ delivered: "unknown" }`，提示"可以用同样的 questionId 和回答再调一次"：同一个问题再收到同样的回答，扩展按已收下处理并再确认一次（幂等），收到不同的回答应答 `agent_question_closed`。
- 子对话问**你**的（pi 原有的对话框）不在这里，父 agent 拿不到，见事件 `needs_you`。

5. `agent_list`：列出自己的子对话。参数 `includeEnded?: boolean`（默认 `false`；`true` 时把已归档、交给终端、记录没了的也列出，脱离的不列，它们已经不是你的）。返回 `[{ name, title, sessionId, role, status, place, branch?, model, thinking, updatedAt, openTasks: [taskId], lastProgress? }]`；`status` 是 `creating`、`running`、`queued`、`waiting_for_you`、`waiting_for_parent`、`idle`、`stopped`、`failed`、`handed_off`、`ended` 之一。

6. `agent_read`：读子对话的回复或过程。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `to` | string | 是 | — | |
| `taskId` | string | 否 | 最近一件 | 读哪件事的回复 |
| `what` | `"reply"` \| `"steps"` | 否 | `"reply"` | 回复，或最近几步的标题 |
| `offset` | integer，≥ 0 | 否 | 0 | 只对 `reply`，按字符分页（`pi-subagent-manager` 的 `agent_output`） |
| `limit` | integer | 否 | `reply` 8000（1–16000）；`steps` 10（1–50） | |

返回 `{ text, totalChars, nextOffset }`（还没有回复时 `{ text: null, reason: "no_reply_yet" }`）或 `{ steps: [{ title, status }] }`。由宿主从子对话的会话文件读，子对话的 pi 不用在跑；交给终端后也能读。

7. `agent_stop`：停下一个子对话这次运行。参数 `to`（必填）。连带停下它下面由 agent 开的、在跑的子孙，碰到你手动开的或已脱离的就不再往下（停止父会话时连带停 `wait: true` 在等的子对话，也按这条）。会话保留，之后能用 `agent_send` 接着干。返回 `{ to, sessionId, previousStatus, stopped: [句柄] }`。

8. `agent_models`：没有参数。返回 `[{ id: "provider/modelId", name, thinking: ["off", "low", …], current?: true }]`，取自宿主的模型列表（Paseo 也要求先查再填）。

**子对话往回说话的工具**（只在 agent 开的子对话里能用）

1. `report_progress`：汇报进度，不打断主 agent。参数 `message`（string，1–2000 字，必填）。立即返回"已记下"。宿主在内存里记每个子对话最近一条，显示在主对话的子对话条里，`agent_list` 的 `lastProgress` 也看得到；不唤醒主 agent，随下一条通知或等待的结果一起带过去，带过一次就不再带。进度不进待送达、不算排队、不挡回收；宿主重启后从子对话会话文件里最后一次 `report_progress` 调用读回（`pi-subagent-manager` 的 `agent_update`、`pi-subagents` 的 `progress_update`）。

2. `ask_parent`：向主 agent 提问，挂着等回答，超时就继续（2026-10-16 定，同 `pi-subagents` 的 `contact_supervisor`）。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `question` | string，1–4000 字 | 是 | — | |
| `options` | string[]，最多 6 个 | 否 | — | 可选答案 |
| `timeoutSeconds` | integer，60–3600 | 否 | 600 | |

- 只在主 agent 交代的那件事里能问；你直接在子对话里说话开的那一轮里调用，马上返回 `{ answered: false, reason: "user_turn" }`，提示"这一轮是用户开的，有问题直接问用户"。
- 子对话的这个工具调用一直挂着，子对话算"在跑"（`waiting_for_parent`），占名额，不回收。扩展经通道告诉宿主有了一个问题（`questionId`、问题、可选答案、这次工具调用的 id），宿主给主 agent 发 `question` 事件。
- 返回给子对话：答了是 `{ answered: true, answer }`；超时是 `{ answered: false, reason: "timeout" }`，提示"主 agent 没有回答，按你的判断继续，并在最终回复里说明你做了什么假设"；被停下是 `"aborted"`；被脱离、归档、交给终端时宿主主动关掉，分别是 `"detached"`、`"archived"`、`"handed_off"`。主 agent 的回答没确认送到、宿主关掉问题时是 `"reply_failed"`（见 `agent_reply`）。
- 超时由扩展自己计时（pi 不给工具设超时）；工具听 `signal`，停止时马上返回，不让 RPC `abort` 卡住。同时可以有几个问题，各有 `questionId`。
- 问题一关（答了、超时、取消、pi 退出、宿主重启），扩展回报宿主，宿主把还没送到主 agent 的这条 `question` 删掉，不再唤醒主 agent；已经送到的不追回，之后的 `agent_reply` 应答 `agent_question_closed`。宿主重启或子对话的 pi 退出时，那一轮按 `stopped` 通知主 agent。

交付：子对话最后一轮的最终回复就是交付，没有专门的"完成"工具（Codex v2、`pi-subagent-manager` 的做法）。`work` 的交付由宿主自动附上分支、目录和改动统计。

**错误码**（扩展写进工具结果给模型，宿主只发错误码和参数）

| 情况 | 错误码 | 哪些工具 |
|---|---|---|
| 不是自己开的、已脱离 | `agent_not_allowed` | 所有带 `to` 或 `tasks` 的 |
| 已归档 | `agent_gone` | `agent_send`、`agent_reply`、`agent_stop`（`agent_read`、`agent_list` 照样能读） |
| 记录没了 | `agent_gone` | 所有带 `to` 的 |
| 交给终端了 | `agent_handed_off` | `agent_send`、`agent_reply`、`agent_stop`（`agent_read`、`agent_list` 照样能读） |
| 正在归档 | `agent_busy` | `agent_spawn`、`agent_send`、`agent_stop` |
| 超过 6 个 | `agent_limit`（参数里带现有子对话） | `agent_spawn`、让空闲的子对话再干活的 `agent_send` |
| 层数到了 | `agent_depth_limit` | 主 agent 的工具 |
| 句柄重了、格式不对 | `agent_name_taken`、`agent_name_invalid` | `agent_spawn` |
| 角色比调用方高（见下） | `agent_role_not_allowed` | `agent_spawn` |
| 只读的调用方或只读角色要新 worktree；父会话在对话里、项目不是 git 时明说要 worktree | `agent_place_invalid` | `agent_spawn` |
| 建 worktree 失败 | `agent_place_failed`（参数带 SPEC-0001 的原因码） | `agent_spawn` |
| 模型不在列表里 | `agent_model_unknown` | `agent_spawn` |
| 档位这个模型不支持 | `agent_thinking_invalid`（参数带支持的档位） | `agent_spawn` |
| 带不了上下文（见下） | `agent_context_unavailable` | `agent_spawn` |
| 问题已经关了 | `agent_question_closed` | `agent_reply` |

- 工具说明写明：不要轮询、不要编造还没回来的结果、子对话的回复用户看不到要自己转述（三家一致，见调研 §3）；同一个目录同一时间只让一个子对话写（`pi-subagents` 每次都提醒）。
- **交代给子对话的话不当用户的话发**：`task` 和 `message` 由宿主经隐藏命令交给子对话 pi 里的扩展，扩展发成 `task` 自定义消息，不走 `prompt`，所以开头是 `/` 的文字不会被 pi 当成命令执行，界面上也显示成"来自主对话的 agent"，不是"你说的"。宿主发给扩展的隐藏命令，参数一律是 base64url 编码的 JSON，模型的文字只在 JSON 里，碰不到命令解析。
- **子对话的角色说明放在第一件事的消息里**（2026-10-17 审查后改，原先打算用 `--append-system-prompt`）：给了这个参数，pi 就不再读你自己的 `APPEND_SYSTEM.md`，等于顶掉了你的设置。所以扩展生成第一条 `task` 消息时，开头放一段 `<atrium-subagent>`：谁开的、什么角色、能用哪些工具；最终回复交给主 agent、用户看不到；拿不准用 `ask_parent`，不要猜；`work` 只在自己的 worktree 里改。之后每条交代只带一句简短提醒。子对话的系统提示词和你自己的会话一样，不改。
- 子对话不自动开标签、不切过去：出现在子对话条里，需要你时照常进收件箱。
- **什么时候开**：由 agent 判断（2026-10-16 定）。工具说明写明适合的情况：彼此独立、能并行的调研，交给别的模型审查，改动范围互不相交的执行；简单的查找自己做。层数和数量的上限兜底。

**带上下文的子对话（agent 开的）**（2026-10-17 定，`pi-subagents` 的做法，见调研 §7）

- 切在父会话**当前的叶子**：这一轮也带上，一直到发出这次 `agent_spawn` 的那条助手消息（pi 在执行工具之前已经把它写盘）。子对话看得到"为什么开它"，而且请求的开头和父会话一样，能命中父会话的提示缓存。
- 分支由父会话 pi 里的 Atrium 扩展自己做：`SessionManager.open(本会话的文件, 宿主给的临时目录).createBranchedSession(当前叶子)`。扩展和写这个文件的 pi 在同一个进程里，读到的不会是写了一半的行；用的是 pi 自己的接口，宿主不写 pi 的会话文件格式；分支可以切在任何条目上，不受 RPC `fork` 只认用户消息的限制；父会话照常在跑，不用等它空闲（和你手动开的不同）。
- 之后同"带上下文的子对话怎么做出来"的新建 worktree 那条：宿主在目标目录（同一容器就是父会话的目录，新 worktree 就是新目录）以 `pi --mode rpc --fork <分支文件> --session-id <id>` 起子对话的 pi，`get_state` 成功后删掉临时目录。用量基线 `usageAfter` 是分支文件里最后一条条目的 id。
- 分支停在一个还没有结果的工具调用上（就是这次 `agent_spawn`，同一批里别的调用也是）；第一条 `task` 消息之前，pi 发请求时会给没配对的工具调用补一条"No result provided"的结果（`pi-ai` 的 `transform-messages.ts`，契约测试核实）。
- 这些"失败"的调用是父会话的，子对话不能当成自己失败了去重做（一批开三个时每个都会看到三个失败的 `agent_spawn`；`work` 可能把父会话那批写操作再做一遍）。所以带上下文的子对话，`<atrium-subagent>` 开头写明："历史最后一条助手消息里没有结果的工具调用（包括开你的这次 `agent_spawn`）属于主对话，主对话会自己处理，不要重做；你只做下面交代的事"。扩展另外兜底：子对话第一件事里，和分叉点那批调用名字、参数都相同的调用直接拦下，返回同样的说明。
- 子对话的系统提示词和工具声明要和父会话一样才命中缓存，所以带上下文的子对话不另加只读和层数的限制参数：启动参数里的工具参数 = 父会话的工具参数，去掉其中对 `report_progress`、`ask_parent` 的排除（父会话不是 agent 开的时候带着这条排除）。工具限制改由扩展在 pi 的 `tool_call` 钩子里按**白名单**放行：只读角色只放 `read`、`grep`、`find`、`ls`、`report_progress`、`ask_parent`，层数允许时再加八个 `agent_*`；`work` 放全部，层数到了拦 `agent_*`。白名单外的一律拦下（MCP、`codemode`、其他扩展注册的工具都算），带 `parentToolCallId` 的嵌套调用一样查，返回"这个子对话是只读的"之类（2026-10-17 定接受：带上下文的只读子对话，只读由扩展保证，不是 pi 注册表层面的硬限制）。子对话独有的 `report_progress`、`ask_parent` 在分叉点声明：支持中途改工具的模型照样命中缓存，其他模型丢掉缓存（同 `pi-subagents`；能不能命中列进契约测试，待确认）。父会话本身是带启动参数限制的子对话时，子对话照样继承它的参数，再由扩展按自己的角色拦。
- 限制在哪一层记在子对话的记录里（`toolGuard: "flags" | "extension"`）：宿主拼参数的那一处按它决定加不加 `--tools` / `--exclude-tools`，回收后再起、自动重启、接回都一样。
- 交给终端时扩展不在，所以 `toolGuard: "extension"` 的子对话，复制给终端的命令改带和不带上下文时一样的硬限制参数（只读白名单、层数排除）；这在终端里只是建议，同"交给终端"那条。
- 换了模型的子对话，父会话里签过名的 thinking 由 pi 处理（只回放给原来的模型，别的模型变成文字）。父会话的上下文接近子对话模型的窗口时，子对话照 pi 的规则压缩，这个里程碑不做 `pi-subagents` 那种"超长时先用模型摘要"。
- 带不了时（父会话还没有会话文件、读不到当前叶子、分支没写出来）应答 `agent_context_unavailable`，不悄悄退回不带上下文。

**角色与限制**

- **角色**：`explore` 只读、同一容器；`work` 可写、默认新建 worktree（只能放同一容器时默认同一容器）；`advise` 只读、同一容器、可以换模型。角色记在子对话的记录里（`role`），pi 重启、重新打开、交给终端时照样带上。
- **只读用白名单**（2026-10-16 定，不带上下文时）：宿主启动只读子对话的 pi 时加 `--tools read,grep,find,ls,report_progress,ask_parent`（agent 层数允许时再加八个 `agent_*`）。pi 在注册表这一层就只留这些名字，MCP、`codemode`、其他扩展的工具一概没有，扩展的 `setActiveTools`、`executeTool` 也拿不到。代价：只读子对话用不了 MCP（浏览器、搜索之类）。保证只到名字：你自己装的扩展若注册了同名工具覆盖内置的 `read` 等，不在保证之内。`read` 能读绝对路径，和主对话一样，只读不等于看不到工作区外的文件。带上下文的见上一节。
- **角色不能比调用方高**：只读的子对话只能开只读的（`explore`、`advise`），且只能放同一容器，否则应答 `agent_role_not_allowed` / `agent_place_invalid`；`work` 和你自己的会话不限。宿主在 `agent_spawn` 上按调用方的记录查，不只靠启动参数。
- **哪些会话有哪些工具**：主 agent 的八个工具只在 agent 层数小于 2 的会话里能用；`report_progress`、`ask_parent` 只在 agent 开的子对话（`by: "agent"`）里能用。不带上下文的用启动参数做硬限制：agent 层数到 2 的去掉八个 `agent_*`，不是 agent 开的去掉那两个（`--exclude-tools`，只读的白名单里本来就按需加）。不用 `setActiveTools`：它只管声明给模型的工具，进程重启后也不恢复。带上下文的由扩展拦，宿主收到工具请求时照样再按记录查一遍。
- 所有启动参数统一在宿主拼 pi 参数的一处算（打开、自动重启、重试、接回、草稿第一次发送都经过它）；分叉用的临时 pi 不带扩展，不受影响。
- **名额**：同一父会话的 `agent_spawn`、"让一个空闲的子对话再干活"的 `agent_send`、给被回收的子对话送通知而起 pi，都由宿主按父会话依次受理，查名额和占名额在一起：受理时先占一个"创建中"，建 worktree、起 pi 失败就释放。受理很快，受理完就应答扩展，等子对话的部分在扩展里各自等，所以同一批里几个 `wait: true` 照样并行。工具不标成依次执行（pi 同一批里只要有一个依次执行的，整批都变成依次执行）。
- **进程**（2026-10-16 定）：agent 开的子对话一轮做完、没有标签开着（你后来关掉它的标签也算）、排队为空（含待送达的交代）、没有挂着的对话框时，宿主停掉它的 pi（`requested`，界面不当成出错，记成"已回收"）；下次 `agent_send`、有通知要送给它、或你打开它时再起。停 pi 和再起由宿主按这个子对话依次处理，不会一边停一边送。只对 agent 开的子对话，别的会话照旧不回收。
- **新建 worktree**：起点和分支名见"概念"，agent 开的分支名是 `agent/<句柄>`（2026-10-16 定）。做完的通知里带上分支和目录，由父 agent 或你来合。子对话在别的工作区，归档主对话时它被脱离、不归档，worktree 由你像别的工作区一样归档。

**通知父会话的事件**

只有 `by: "agent"` 的子对话、而且不是你开头的那一轮才通知父会话：`agent_spawn` / `agent_send` 交代的那件事，以及它收到孙对话的通知（`report`）后开的那一轮（这样主 → 子 → 孙的结果能一路送上去）。孙对话的每件任务记下它的来源任务（`originTask`：子对话开它或交代它时，子对话自己正在做的那件事）；由孙对话的通知开头的那一轮归到这件来源任务上；来源任务已经到了终态，就新记一件"后续"任务（`originTask` 指回它），通知里写明是哪件事的后续。不按"最近一件没结束的"去猜，也不挂到还没开始的任务上。你在子对话里直接说话的那一轮不通知（同 Claude Code），用户开的子对话靠"带回"。每个事件都带任务 id。

| 事件 | 什么时候 | 终态 |
|---|---|---|
| `finished` | 交代的那件事成功结束（带最终回复） | 是 |
| `failed` | 那件事失败（含崩溃用尽） | 是 |
| `question` | 子对话用 `ask_parent` 问主 agent（带 `questionId`、问题、可选答案） | 否 |
| `needs_you` | 子对话在等你回答或批准（父 agent 只知道在等你，拿不到对话框，也不能代答） | 否 |
| `stopped` | 被你停下、被 `agent_stop` 停下、宿主退出时被停（参数写原因） | 是 |
| `ended` | 被归档、被脱离、交给终端、记录没了（参数写是哪一种） | 是 |

进度（`report_progress`）不是事件，见上。

**等待的规则**（`wait: true` 和 `agent_wait` 一样）

- 等待开始时先按当前状态算：要等的任务里已经有了还没交给主 agent 的事件，马上算进结果。
- 有等待接住某个任务时，这个任务的事件照样写进待送达，但状态记成 `claimed`（带接住它的那次工具调用的 id），不发；已经交给 pi（`sending`）的不再放进等待的结果。等待返回的结果写进父会话的会话文件后（宿主在文件里看到这次工具结果），这些记录才删掉；等待被中止、pi 退出而工具结果没写出，就放回 `waiting` 走普通送达。宿主重启后，`claimed` 的先去文件里找那次工具结果，找到就删，找不到放回 `waiting`。用等待取到的事件不再另发通知（`@tintinweb/pi-subagents` 的做法）。
- 提前返回：你在主对话里发了新消息（宿主一收下就算，不等 pi），或要等的子对话问了问题（`question`），无论 `any` 还是 `all` 都提前返回；`needs_you` 只在 `any` 时让它返回。你的消息照常作为插话进这一轮。
- `any`：任一任务有了事件就返回；`all`：都到终态才返回，期间只有 `question` 提前返回（`needs_you` 不打断 `all`，见上一条）。
- 停止父会话时（工具的 `signal` 被中止），等待马上结束，宿主一起停掉 `wait: true` 在等的子对话（连带范围同 `agent_stop`），不靠扩展跑完清理。
- `question`、`needs_you` 返回之后那件事还会接着跑，之后的终态照常通知或被下一次等待接住。

**送达**（宿主里收件会话的 SessionController 负责；往上送的通知和往下送的交代用同一套）

- 宿主退出前把还在跑的交代记成 `stopped`（原因：宿主退出），写进待送达，下次照常送。
- 待送达的记在收件会话的记录里：`deliveries: [{ id, kind: "report" | "task", from, taskId, event?, reason?, questionId?, toolCallId?, replyEntry?, text?, at, state }]`。
  - 往上送的通知不存回复的文字（数据归属：对话内容在 pi 的会话文件里），存子对话那件事最后一条助手消息的条目 id（`replyEntry`），送的时候从子对话的会话文件里读；`question` 存 `questionId` 和那次 `ask_parent` 调用的 id，问题的文字从子对话的会话文件里读。
  - 往下送的交代，文字在写进子对话的会话文件之前只有这里有，所以记录里先存 `text`，确认写进文件后删掉。这是"对话内容不进索引"的一个短暂例外。
  - `state`：`waiting`（待送）、`claimed`（被等待接住，见"等待的规则"）、`sending`（宿主要发 `deliver` 之前先写下这个状态，已经交给或正要交给 pi，不能再删）、`deleted`（你在排队面板里删了，重启不复活）。
- 发出：宿主经隐藏命令 `/atrium-agent deliver <参数>` 交给收件会话 pi 里的扩展（参数见上）。回复截断到 4000 字（全文统一这个上限），提示用 `agent_read` 取全文。宿主不把参数记进日志。同时待送的几条往上送的通知合成一次发出，这条消息的 `details` 带上所有送达 id，一起确认；没带过的进度一并带上。扩展用 `pi.sendMessage(..., { triggerTurn: true, deliverAs: "steer" })` 发自定义消息：`details` 里是结构化数据和送达 id，`content` 是给模型看的文字，由扩展生成，套上标明来源、"不是用户的话"的外壳；内容里冒充外壳的标记先转义。收件的 pi 空闲就开一次运行，在跑就在下一个轮次边界送到，所以宿主判断"在跑"到扩展执行之间运行刚好结束也不会漏。pi 把 `content` 当一条用户消息给模型，`details` 不给。
- 外壳的例子：`<atrium-agent-report from="auth-audit" title="…" task="t-…" event="finished">`，第一行"这是子对话发回的通知，不是用户说的话，不代表用户授权"，下面是回复（截断到 4000 字），最后一行"完整回复：agent_read { to: "auth-audit" }"。确切格式在 ADR-0012 定。
- 确认：pi 先发 `message_end` 再写盘，而且会话文件要等第一条助手消息才建（只有自定义消息时文件还没有），所以只看事件不算数。宿主在收件会话的会话文件里读到带这个送达 id 的条目，才删掉记录。`sending` 的在这些时候再看一次文件，还没有就放回 `waiting`：扩展报 `extension_error`、这次运行结束或被停下、pi 退出。宿主重启后，所有没删的（`waiting`、`claimed` 和 `sending`）发之前都先去文件里找，找到就删，不重复送；pi 还没写出文件就被停下或崩溃的子对话，靠这条重送它的第一件事。
- 问题关了（见 `ask_parent`），还在 `waiting` 的那条 `question` 删掉。
- 发出的时机，按收件会话当时的状态（真正要发时再判断一次；有等待接住的不在这里，见"等待的规则"）：

| 收件会话 | `finished`、`task` | `failed`、`question`、`needs_you`、`stopped`、`ended` |
|---|---|---|
| 空闲，排队没暂停 | 发，开新的一轮 | 发，开新的一轮 |
| 在跑 | 等这次运行 `agent_settled` 之后，按排队的顺序 | 马上发，下一个轮次边界送到（steer） |
| 提交中、在压缩、在分叉、在停止、pi 在重启 | 等这件事做完再按上面判断 | 同左 |
| 被停下或崩溃用尽（排队暂停） | 留着，你恢复排队或发消息时一起走 | 同左 |
| agent 开的、pi 被回收了 | 过名额（满了就留着，等有空位）、起 pi，再按上面判断 | 同左 |
| 交给终端 | 留着，接回后再送；不因为送达接回 | 同左 |
| 宿主重启后 | 都暂停，排队面板里写"宿主重启后暂停"，你点继续才送；不为送达起 pi。主对话的子对话条里有"全部继续"，一次恢复整棵子树里暂停的（中间那层多半没开标签） | 同左 |
| 归档中、已归档 | 删掉 | 删掉 |

- 宿主发出 `deliver` 后到看见 `agent_start`（或 steer 时的 `message_end`）之间算"提交中"：排队里的下一条不发，压缩、分叉、交给终端应答 `session_busy`，免得和刚开始的运行抢。
- `triggerTurn` 开的运行不经 pi 的 `prompt()`，所以不做 pi 发送前的压缩检查，也不触发 `before_agent_start`（Atrium 的扩展不靠它）。上下文快满时 pi 在这一轮里溢出、先压缩再重试（SPEC-0001 已有的溢出处理）。
- 停止收件会话时 pi 的 `clear_queue` 会清掉还没送到的 steer 自定义消息，且不在返回里带回：宿主没在文件里见到它，所以它还在待送达里，随排队暂停。
- 排队面板里，待送达的是另一种项："来自子对话「名字」：完成 / 出错 / 在问你的 agent / 在等你 / 已停下 / 已结束"，子对话里是"来自主对话的 agent"。`waiting` 的能删（父 agent 不另外得知），`sending` 的已经交给 pi、删不掉了；都不能编辑、不能改成插话。待送达的不挡交给终端（不算排队里的消息）。
- 你在输入框里打的以 `/atrium-` 开头的消息，宿主在发消息、插话、改排队里的消息、新建工作区的第一条消息上都应答 `command_reserved`，不发给 pi（现有的 `/atrium-fast`、`/atrium-plan` 也一样）；宿主自己发的隐藏命令不受这个检查。

### 扩展与宿主的通道（第二步，写 ADR-0012）

两种做法都能用，ADR-0012 选一种（2026-10-16 按 pi 源码核实的事实）：

- **甲：借用对话框**。`ctx.ui.input` 发出 `extension_ui_request`、等宿主的 `extension_ui_response`，标题带固定标记，内容是 JSON；宿主在 PendingInteraction 之前认出标记、自己处理。挂着的对话框不挡 pi 的其他命令和事件流。但要小心：不给 `timeout` 或 `signal` 时 pi 永远等；`editor` 不收这两个参数；超时了 pi 不告诉宿主；工具里的对话框没绑 `signal` 时，RPC `abort` 一直等它，不应答。
- **乙：状态加隐藏命令**（M1.13 的 `/atrium-plan` 就是这样）。扩展用 `ctx.ui.setStatus("atrium-agent:<请求 id>", JSON)` 发请求（单向、不等、没有大小限制、不写会话文件），宿主处理完用隐藏命令 `/atrium-agent reply <参数>` 回答，扩展在进程里兑现那个请求的 Promise。宿主要在原始的 `extension_ui_request` 上认这个键，和 `atrium-fast`、`atrium-plan` 分开（翻译成会话事件时 `setStatus` 被丢掉）。
- 草稿倾向乙：少一套拦截，也不会和真的对话框混在一起。
- 不管选哪种，ADR 都要定：请求 id、按请求 id 幂等（扩展重启后用同一个 id 问，不再开一个）、进程代次（旧 pi 的迟到应答丢掉）、超时与取消、重复或迟到的应答、JSON 的 schema 和大小上限、正文不进日志、各工具和命令的参数形状。同一个 pi 里的其他扩展也能发这个键，宿主分不出来；这算 ADR 的代价（扩展本来就和 pi 同进程、同权限）。
- **宿主 → 扩展**：隐藏命令，同 `/atrium-fast`、`/atrium-plan`，参数是 base64url 编码的 JSON。只有宿主会给 pi 发 `prompt`，你打的 `/atrium-` 被挡在宿主（见"送达"末尾）。
- **调用方是谁**：请求从哪个 pi 进程的管道来，就是哪个会话，宿主不信参数里写的身份。不要 socket、端口和 token，环境变量照旧去掉 `ATRIUM_*`（security.md）。
- 工具在 `wait: true` 时一直等是可以的：pi 不给工具设超时；RPC `abort` 会中止传给 `execute` 的 `signal`，工具要听它、马上结束，否则 `abort` 不应答。
- 契约测试要实测的（源码读的是仓库依赖的 pi 1.0.2，本机跑的是 1.1.0）：选定的通道来回一次、运行中途送达、`triggerTurn` 加 `deliverAs: "steer"` 在空闲和在跑时的行为、只有自定义消息时会话文件什么时候写出、`clear_queue` 清掉自定义 steer、`--tools` / `--exclude-tools` 去掉的工具模型看不到也调不到、`fork` 和 `--fork` 保留条目 id、`--fork` 在应答 `get_state` 之前就写出文件、扩展在运行中用 `createBranchedSession` 切在当前叶子、没配对的工具调用在自定义消息之前补上"No result provided"、`tool_call` 钩子拦下的工具调用模型看到的结果。2026-10-17 在本机 pi 1.1.0 上实测，除了缓存都成立（结果见 pi-internals "SPEC-0002 契约测试实测"）；通道乙走得通。上下文检查器要的"扩展给宿主发数据"也用这条通道，ADR 一起定。

## 备选方案

- **子对话放在会话内部，不是独立会话**（Claude Code 的 sidechain 对话记录）：打不开、接不上、不能交给终端，不采用。
- **MCP 注入**（Paseo）：宿主起一个本机 HTTP MCP 服务写进 pi 的配置。要把 token 交给 pi，身份靠 URL 参数（Paseo 的越权就出在这），而 pi 的 MCP 本身也是扩展，不采用。
- **命令行**（`atrium agent spawn …`，模型用 bash 调）：要把连宿主的凭据放进环境变量，违反 security.md，不采用。
- **送达一律用 steer**（Paseo）：结果打断父 agent 正在做的事；完成的等这次运行结束再送，只有出错、等你、停下、结束才马上送。
- **对方在跑时打断再发**（Paseo 的 `send_agent_prompt`）：会丢掉对方正在做的事，改为排队。
- **父 agent 代答审批**（Paseo 的 `respond_to_permission`）：其他 agent 的话不是用户授权，不采用。
- **送达用普通 `prompt`**：简单，但通知会显示成"你说的话"，模型也当成用户的话，开头是 `/` 的文字还会被当成命令；改用自定义消息。
- **角色说明用 `--append-system-prompt`**：会让 pi 不再读你的 `APPEND_SYSTEM.md`；改放进第一条 `task` 消息（2026-10-17）。
- **agent 开的带上下文切在这一轮之前**（`pi-interactive-subagents` 的做法）：工具能照常用白名单限制，但子对话不知道为什么开它、也命不中提示缓存；改切在当前叶子（2026-10-17 定）。
- **按会话等待、按会话通知**：同一个子对话先后交代几件事时，会把上一件的结果当成这一件的；改按任务 id（2026-10-17）。
- **以 `message_end` 为送到**：pi 先发事件再写盘，文件还可能没建；改为在文件里见到才算。
- **在父会话自己的 pi 里 `fork`**：pi 会把这个进程换到新文件上，父会话就丢了它的 pi；沿用 SPEC-0001 的临时 pi。
- **改写会话头的 `cwd`**：要宿主改 pi 的会话文件，而 `--fork` 本来就能在新目录复制一份；不改写。
- **只读用黑名单**（去掉 `bash`、`edit`、`write`、`powershell`）：MCP 和其他扩展的写工具照样能用，不是真的只读（2026-10-16 定用白名单）。
- **`agent_spawn` 标成依次执行**：pi 会把整批工具调用都变成依次执行，几个 `wait: true` 就并行不了；改由宿主按父会话依次受理。
- **等插件系统做完再做**：插件系统在阶段 3，v0.1 不做；子对话不依赖插件接口，先写死反而给抽接口多一个样本（2026-10-16 定）。
