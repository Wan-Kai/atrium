## 每天做什么

1. 用 Atrium 做当天的编码任务，每个会话记一行到"会话"。拉了新代码或改了代码后重新 `pnpm package`，再拷一次。
2. 收工前跑 `pnpm usage`，看最近几次运行：
   - 带 `↑` 的行说明最后一个小时的最低值比第一个小时高（资源计数变高，或内存涨到 1.5 倍以上），可能有泄漏；
   - 运行不到两小时的不比较，只看每小时的数值有没有一路往上走。
   发现持续上涨就记到"问题"，补一个能复现的泄漏测试再修（[testing.md · 运行时监控](../architecture/testing.md#运行时监控)）。
3. 碰到 pi 不如 Codex 的地方，记到"pi 和 Codex 的差距"；碰到 Atrium 自己的问题，记到"问题"。出错时用界面上报的 trace id 跑 `pnpm trace <trace id>` 看链路。

## pi 和 Codex 的差距

H1 的结论从这里来：pi 比 Codex 明显不够用的地方，决定是否继续这条路线（[ADR-0001](../adr/0001-use-pi-as-core.md)）。每条写清场景、Codex 怎么做、pi 怎么做、能不能靠 extension 或宿主补上。下面是自用中碰到、已在 ADR 和调研笔记里记下的。

| 场景 | Codex | pi | 能否补上 |
|---|---|---|---|
| Fast（优先档） | 模型列表标了 `service_tiers`，桌面版有 Fast 开关 | 没有 | 能：Atrium 自带扩展给请求加 `service_tier: "priority"`，问 Codex 的模型列表决定显示（[ADR-0008](../adr/0008-atrium-own-pi-extension-for-fast.md)）；回复里看不出有没有生效 |
| 订阅余量（5 小时、每周窗口） | 界面直接显示 | 没有 | 能：扩展借 pi 的登录查 `wham/usage` 等，Claude 也从回复头读（[ADR-0010](../adr/0010-plan-usage-through-atrium-extension.md)、[ADR-0011](../adr/0011-plan-overview-all-subscriptions.md)、[ADR-0012](../adr/0012-claude-usage-from-replies-and-openai-mapping.md)） |
| 子代理 | `spawn_agent`、`send_input`、`wait_agent`，子线程完成时往父线程追加通知（[multi-agent.md](multi-agent.md) §1–3） | 没有 | 能，量大：扩展加七个 `agent_*` 工具，宿主管关系、名额、送达（M1.15、[SPEC-0002](../specs/0002-child-conversations.md)、[ADR-0013](../adr/0013-agent-channel-status-and-hidden-command.md)） |
| 带上下文的子代理命中提示缓存 | 同一线程的分支沿用缓存 | `openai-codex` 的 `prompt_cache_key` 是会话 id，分叉出的子对话第一次请求命不中 | 不能靠扩展补：Codex 按请求头的 `session-id` 分缓存（[pi-internals](pi-internals.md)、SPEC-0002） |
| 联网搜索 | 服务端工具 | 没有 | 能：扩展加 `web_search`、`web_fetch`，走 DeepSeek 的接口，另付费（[ADR-0014](../adr/0014-web-search-and-fetch-through-deepseek.md)） |
| 审批与沙箱 | 写入和执行要确认，有沙箱 | 没有审批，工具直接执行 | 审批能用 `tool_call` 钩子补（MVP 2）；沙箱以后再评估 |

H1：用户 2026-10-22 定继续走 pi 路线。上面缺的都能由 Atrium 的扩展和宿主补上，唯一补不上的是带上下文的子对话在 Codex 上第一次请求命不中缓存，影响的是成本和首字延迟，不是功能。

## 新账户首次启动

M1.10 完成标准第一条：在一个没装 pi 的 macOS 账户上，从首次启动走到第一次对话。

**没做**：用户 2026-10-22 定不跑。自动化测试用的都是装好 pi 的环境，所以"没装 Node 和 pi 时的安装"这条路径没有在真实账户上验证过；开源发布前再做。

1. 系统设置里新建一个标准用户，登录进去；确认 `which pi`、`which node` 都找不到，`~/.pi` 不存在。

5. 退出再打开，确认不再显示首次启动。

## 结论

- **H1**：成立，继续走 pi 路线（用户 2026-10-22 定）。12 天里 Atrium 做了 Atrium 自己的全部开发，184 个会话，没有一次会话 pi 崩溃；比 Codex 缺的都靠 Atrium 自带的扩展和宿主补上了，见"pi 和 Codex 的差距"。
- **没做到的**：新账户首次启动没验证（用户定不跑）；自用的项目只有 Atrium 自己，没在别的仓库上用过；会话和资源是事后从数据整理的，不是每天记的。
- **进入 MVP 2 前要先修的**：
  1. 界面的 React #185（见"问题"），打包版也有。
  2. 模型目录为不存在的目录起一次性 pi。
  3. 空闲回收在真实使用里的效果：下一段自用时看 `pnpm usage`，pi 和控制器计数应在空闲后回落。
  4. 已知不稳的测试：`pi-config.test.ts` 的队列用例、右栏 changes-pane "0.24 s"、`app.spec.ts` 的失焦用例；pi 契约测试有 33 项缺 pi 1.3.0 的夹具。
