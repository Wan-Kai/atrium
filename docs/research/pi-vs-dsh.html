pi 与 DeepSeek Harness：设计思路和插件开发的差异

长图

答

结论

两者分歧在于谁是核心。pi 本身就是固定的 agent loop，扩展只在节点上介入；DSH 没有特权核心，loop、会话日志和界面都能换成别的插件。

  1. pi 一个进程跑一个会话，界面在进程外；DSH 一个常驻进程装下所有会话和宿主逻辑。12
  2. pi 会话文件是条目树，扩展只能追加；DSH 会话日志是类型化事件流，插件能声明新事件。34
  3. pi 的扩展没有界面通道，宿主要自己接；DSH 的插件一个包两半，界面插槽和远程方法都现成。5
  4. 所以在 pi 上做插件，是"往别人的引擎上装配件"；在 DSH 上做插件，是"拼装整台引擎"。

适用于pi 1.3.0（本机）· DSH 687f282（0.2.1-rc.2）· 2026-10-23读源码和文档整理，未实测 DSH

两者的设计思路差在哪？

方面piDeepSeek Harness
核心理念极简内核，扩展在节点上介入可替换没有特权核心，一切皆插件
谁拥有 agent loop固定pi 自己，结构改不了loop 本身是一个插件
扩展点的形态事件钩子：拿到数据、返回改写服务注入加事件；拦截类事件要调 next() 交给下一个
产品形态一个 CLI，多种运行模式按配置拼装：Web、无界面、SDK、ACP
界面只有终端界面能扩展浏览器客户端，100 个插槽
成熟度1.x，迭代快不稳定开发者预览 0.2，会有破坏性变更

pi 把"agent 怎么跑"定死，换来的是简单、好嵌入；DSH 把"agent 怎么跑"也交给插件，换来的是整机可换，代价是组装和调试成本。2

pi 加 Atrium 是什么形状？

图的结构
  • Atrium 界面 ui
  • Atrium 宿主 host
  • pi 进程（每会话一个） pi
  • 扩展（钩子） ext
  • 会话 JSONL 条目树 file
  • ui → host · WebSocket 协议
  • host → pi · RPC：stdin/stdout
  • pi → ext · 节点上的钩子
  • pi → file · 追加条目
  • ext → host · setStatus 借道

pi 的 RPC 只转发对话框和单向通知，扩展没有自定义消息可用。Atrium 和扩展来回通信，靠 setStatus 加隐藏命令搭成。1 每个会话一个进程，一个会话出问题不波及别的会话。6

DeepSeek Harness 是什么形状？

图的结构
  • 客户端插件树（插槽） client
  • 远程网关 gateway
  • 宿主插件树（Cordis） host
  • agent-loop 插件 loop
  • 会话事件日志 log
  • client → gateway · Remote 方法和流
  • gateway → host · 调服务
  • host → loop · 驱动所有会话
  • loop → log · 提交事件
  • log → client · follow 流和投影

宿主和浏览器跑同一套 Cordis：插件提供服务、事件和可回滚的副作用，卸载时一并撤销。2 浏览器侧有自己的插件树和插槽，界面经网关调宿主的服务。7

做插件时各自卡在哪？

维度pi 体系DSH 体系
上手难度简单低：一个文件、几个钩子陡高：先学 Cordis、服务注入、插槽、生成契约
能做多深只能在 loop 节点上介入，不能改结构深loop、会话日志、界面都能换
界面要宿主另做一整套现成插槽，但启动全有或全无
数据通道窄：条目、setStatus、对话框宽：事件、投影、远程方法和流
出错影响局限在一个会话进程可能拖垮整个宿主
被内置界面限制只能放进宿主留的挂载点易误盖任何插件都能盖掉内置界面
版本风险pi 升级可能改钩子行为开发者预览，接口会变

pi 的问题是"够不着"：通道窄、界面靠宿主、跨会话做不到。DSH 的问题是"管不住"：什么都能换，隔离和稳定靠约定。

对 Atrium 意味着什么？

Atrium 站在 pi 这一边，补的是 pi 缺的那一半

Atrium 的插件系统，本质上是在 pi 外面补上 DSH 原生就有的界面插槽、状态投影和回传通道。 补的方式受 pi 的边界约束：插件逻辑仍在 pi 进程里，宿主只转发，所以跨会话和高吞吐这两块补不全。 从 DSH 能借的是形状，不是机制：插槽的基数和降级、投影"客户端拿成品"、按数据语义恢复连接。
