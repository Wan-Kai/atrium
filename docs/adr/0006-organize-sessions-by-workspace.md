# ADR-0006：以工作区组织会话，工作区与目录一一对应

- **状态**：已接受；第 4 条已取代（被 [ADR-0007](0007-each-chat-is-its-own-container.md) 取代）
- **日期**：2026-10-02
- **相关**：[ADR-0002](0002-connect-pi-via-rpc-subprocess.md)、[SPEC-0001](../specs/0001-mvp1-single-session-chat.md)、[架构总览](../architecture/overview.md)

## 背景

主场景是写代码：多个任务并行，每个任务常在独立的 git worktree 里跑。痛点是 worktree 建了不少，却常常忘了合并回主干，事后也说不清哪个会话改的是哪个 worktree。

约束和驱动因素：

- pi 按工作目录保存会话（`~/.pi/agent/sessions/--<路径>--/`），没有"项目"或"任务"的概念；Atrium 不复制对话内容，只能从目录推出归属。
- 侧栏要同时回答两个问题：哪些会话需要我（会话状态），哪些改动还没收尾（worktree 的合并状态）。
- 也有和项目无关的提问，不应该被迫挑一个项目。

原型讨论中先试过"会话平铺 + 彩色 git 图标对应 worktree 折叠区"，靠颜色把会话和 worktree 对上，信息分散、颜色不够用。Paseo 的工作区模型把这层关系变成结构上的包含。

## 决策

**1. 三层结构：项目 → 工作区 → 会话。** 项目是一个 git 仓库或目录；每个项目自动有一个本地工作区（项目目录本身），每个 worktree 是一个工作区；会话属于工作区，在对话区顶部以标签页打开，全部会话在"历史"里。

**2. 工作区与目录一一对应。** 宿主按会话的工作目录把它归到工作区，不需要额外的映射，终端里 pi 开的会话也能自动归位。pi 子进程以工作区目录为工作目录。

**3. 合并状态挂在工作区上。** 未提交、`↑N`、无改动、已合并、已移除是工作区的属性，和会话状态（等你处理、出错、运行中……）分开显示。已合并的判断兼容 squash 和 rebase（`git merge-tree` 模拟合并）。

**4. 另设不绑定工作区的"对话"。** ⌘N 新建；每个对话一个独立的空目录 `~/.atrium/chats/<id>/` 作为工作目录，满足 pi 必须有工作目录的要求，彼此不干扰。

**5. Atrium 只存索引。** 项目、工作区（含自定义名称、创建时的起点提交）、打开着的标签页、归档状态等元数据；对话内容始终在 pi 的会话文件里。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 会话平铺，用彩色 git 图标对应 worktree | 结构扁平，一眼看到所有会话 | 会话和 worktree 的关系靠颜色对应，颜色多了分不清；合并状态没有自然的位置 |
| 按会话组织，worktree 只是会话的一个属性 | 以对话为中心，简单 | 一个 worktree 上的多个会话分散；"这批改动收尾了没有"无处可看 |
| 工作区可以是任意的会话分组，多个工作区共用一个目录 | 能按任务分组 | 会话归属需要额外记录，终端里开的会话无法自动归位。以后确有需要再放开 |
| 项目 → 工作区 → 会话，工作区与目录一一对应（采用） | 归属由目录决定，没有歧义；合并状态有固定位置；和 pi 的存储方式一致 | 多一层层级；和项目无关的提问需要单独的"对话"来承接 |

## 后果

- 正面：会话属于哪个 worktree 不再需要记忆；待合并的 worktree 在侧栏上一目了然，直接对应"忘了合并"的痛点；不复制 pi 的数据，终端和 Atrium 看到的是同一份会话。
- 负面 / 代价：
  - 宿主要维护 worktree 列表和合并状态，定期跑 git 命令（`git status` 在大仓库上偏慢，需要控制计算时机）。
  - "对话"的目录由 Atrium 创建和管理，`~/.atrium/chats/` 会随使用增长，以后需要清理策略。
  - 新建、合并、清理 worktree 的入口要由 Atrium 提供（阶段 1 第 3 步），否则工作区只能被动反映外部操作。
- 什么情况下应重新评估：需要多个工作区共用一个目录（按任务分组）时；pi 原生提供项目或任务的概念时；合并状态的计算成本在大仓库上成为实际问题时。
