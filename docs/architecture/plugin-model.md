# 插件模型

> **状态：暂缓（2026-10-23 用户定）。** 对比 DeepSeek Harness 后（[pi-vs-dsh.html](../research/pi-vs-dsh.html)），认为基于 pi 做整体插件化的上限太低：扩展只活在一个会话的 pi 进程里，做不了跨会话和常驻的事；数据只能走会话条目和 `setStatus` 这条窄通道；界面只能放进核心留好的挂载点。下文是暂缓前的设计，留作参考，不再维护；重新启动时先重新评估前提。

## 组成

一个 Atrium 插件分两半，打包在同一个 pi package 里（理由见 [ADR-0003](../adr/0003-plugin-as-pi-package.md)）：

- **逻辑**：一个 pi extension，负责注册工具、处理钩子、产出结构化数据（tool result 的 `details` 或自定义 entry）。
- **视图**：React DOM 组件，由 UI 加载，在清单里声明挂在哪个挂载点、用什么键，负责把数据画出来（见"能力 · 发现与加载"）。

```json
{
  "name": "@ktoon/atrium-todo",
  "keywords": ["pi-package"],
  "pi": { "extensions": ["./extension/index.ts"] },
  "atrium": {
    "api": 1,
    "views": [{ "mount": "tool", "key": "todo_write", "module": "./dist/todo-step.js" }]
  }
}
```

pi 忽略 `atrium` 字段，桌面端读取它来加载视图。安装和分享直接用 pi 的机制（`pi install`、package gallery）。

## 为什么现在做

Atrium 自带的扩展里已经有好几个写死的第一方"插件"：Fast、套餐用量、子代理、`ask_user`、联网搜索。它们的界面都要改核心代码：协议的 `ToolDetails`（`packages/protocol/src/transcript.ts`）按工具名封闭，不认识的工具的 `details` 会被丢掉；宿主按 `atrium-fast`、`atrium-plan`、`atrium-agent` 这几个前缀逐个识别。用户自己装的扩展（如 pi-fff）在界面上只能显示通用的工具行。插件系统要把这些写死的地方变成通用的。

## 能力

2026-10-22 定。第一版要有的，todo 和 HTML 设计稿都用得上。

### 发现与加载

- 宿主从 pi 的全局和项目设置里读已装的 package，看 `atrium` 字段，列出带视图的插件。
- 设置里看得到每个插件的名字、版本、来源（全局 / 项目），能启用、停用。
- 清单声明 `atrium.api`（视图 API 的版本）；不兼容时只关掉视图、按"降级"显示，不拒装（逻辑在 pi 里照常工作）。
- **挂载点在清单里声明，ESM 只导出组件**：每个视图写明挂在哪个挂载点、用什么键（工具名、消息类型、代码块语言、面板 id）、顺序和多语言标题。界面不加载插件代码就知道它占哪些位置，第一次用到时才 import。低代码引擎和 DSH 都是在代码里调 `register`，要先跑插件才知道，不采用。
- 形如（字段名实现时定）：

  ```json
  "atrium": {
    "api": 1,
    "views": [
      { "mount": "tool", "key": "todo_write", "module": "./dist/todo-step.js" },
      { "mount": "panel", "key": "todo", "module": "./dist/todo-panel.js", "title": { "zh": "待办", "en": "Todo" }, "order": 30 }
    ]
  }
  ```

- 停用、升级、卸载插件时，按包名清掉它的全部挂载项和订阅；热替换前先清旧的。低代码引擎记了插件名却不回收，插件销毁后面板还在；DSH 用台账级联清理，照 DSH 做。

### 数据：逻辑到视图

- 协议的 `ToolDetails` 加一个不透明的插件分支（形如 `{ tool: "plugin", plugin, type, data }`，限大小）。宿主只转发、不解析，视图用插件自己的 schema 校验。
- 自定义条目（`appendEntry`）和自定义消息（`sendMessage`）也送到界面。
- 不要持久的实时数据（进度、生成中的状态）走 ADR-0013 的通道，键用 `atrium-plugin:<插件名>:` 前缀，限频；丢了不要紧。

### 状态跟着分支走

- 要持久的状态写在会话文件里（工具结果的 `details` 或自定义条目），**默认每条带完整状态，视图取当前分支上最后一条**（同 pi 官方 `examples/extensions/todo.ts`）。数据大的插件可以自己写增量合并，但条目里只放引用，不放大内容。
- 宿主按会话维护"当前分支上各插件的条目"，随会话快照和增量发给界面。对话记录是分页的，不能等用户翻到那一页才算。
- 这样做的理由（和"extension 每次推一份快照"比）：
  - 切分支、编辑重发后自动正确；推快照要靠 extension 在 `session_tree` 时重算，写漏了就错。
  - pi 没在跑时（空闲回收、没打开、已归档）照样能显示；推快照要先起 pi。
  - 旧的工具步骤能显示"当时"的状态；宿主重启、断线重连从文件重读，不丢。
  - 代价：宿主多一份按分支的索引；旧条目要一直读得懂，格式改动带版本。

### 挂载点

挂载点是界面上让插件视图画东西的位置，不是 pi 的钩子（那是逻辑侧的介入点，pi 已经提供）。

挂载点由核心定义，启动时就在；插件不能新增挂载点，只往里放内容（同低代码引擎的固定区域；DSH 只有根插槽是内建的，其余由插件声明，不采用）。外壳（边框、标题、错误边界、降级）由核心画。

每个挂载点有"基数"（参照 DSH 的插槽）：

- **按键**：核心按一个键分派到一个视图，找不到就用通用显示。只按键精确匹配，不用判断函数（判断函数要先加载插件代码）。
- **并列**：一排，按 `order` 排，可以同时显示几个。
- **互斥**：一排里同时只开一个（如右栏的标签）。
- **接管**：有待处理的事时接管一块区域，按"待处理的类型"这类键匹配；被接管的原组件隐藏不卸载（输入框的草稿不丢，同 DSH 的 `overlay`）。

| 挂载点 | 位置 | 基数（键） | 现在写死的例子 | 什么时候做 |
|---|---|---|---|---|
| 工具步骤 | 消息流或过程轨道里某个工具调用：折叠时一行、展开后的正文 | 按键（工具名） | bash、read、edit、write 的显示，`agent_*` 的车道、`ask_user` 的记录 | 迁移第 1 步 |
| 自定义消息 | extension `sendMessage` 的消息在对话里的显示 | 按键（`customType`） | 子对话通知的来源行 | 迁移第 1 步 |
| 代码块 | 回复里的围栏代码块 | 按键（语言） | Mermaid、PlantUML、JSON、CSV | 迁移第 2 步 |
| 面板 | 右栏的标签，跟着当前会话 | 互斥（面板 id） | "文件""更改" | 迁移第 3 步 |
| 查看标签 | 标签栏里和会话并列的标签 | 按键（查看对象的类型） | 文件、改动标签 | 迁移第 3 步 |
| 状态栏 | 底部状态栏 | 并列（项 id） | 上下文、套餐 | 迁移第 4 步 |
| 设置分区 | 设置页的一节 | 并列（分区 id） | 账户、pi 配置、代理、项目 | 迁移第 4 步 |
| 输入框附件 | 输入框工具条上的开关、按钮 | 并列（项 id） | Fast 开关 | 迁移第 4 步 |
| 输入框上方 | 输入框上方的卡片 | 接管（待处理的类型） | `ask_user` 提问卡片 | 以后，一般 pi 的对话框就够 |

- **同一个键有几个视图时默认用内置的**；要用第三方的，由用户在设置里选。DSH 靠优先级静默遮蔽，第三方天然盖过内置，不采用。
- **插件往另一个插件的视图里挂东西（"子插件"）第一版不做**。DSH 需要它，是因为整个界面都是插件、挂载点只能由插件声明；Atrium 的挂载点是核心的。等有了真实需求（如给 HTML 设计稿加标注工具）再做，做法：在清单里声明；名字带包名前缀；一个挂载点只有一个声明者；跟着声明它的视图一起撤；贡献者只拿声明者写明的参数。

### 视图到逻辑

- 视图里的操作（勾掉 todo、发出设计稿的标注）由宿主代发隐藏命令 `/atrium-plugin <插件名> <base64url JSON>`。宿主只让视图调用它自己那个插件的命令，保持"`/atrium-` 只有宿主能发"（security.md）。
- 另给视图一小组宿主能力：往输入框插文字、打开文件、发一条消息。

### 视图运行时

- 插件带构建好的 ESM。React 和 Atrium 的视图 API 是外部依赖，界面用 import map 指向自己那一份，只有一份 React。宿主用自己的路由提供插件文件，PWA 也能用。
- 视图 API 带版本，给一组核心组件和 hook：`Fold`、代码块、Markdown、沙箱框、`useSessionData`、`sendAction` 等。
- **props 按挂载点固定**，组件不拿整个上下文（同 DSH）：工具步骤给阶段、参数、结果和当前分支上本插件的条目；面板给会话 id 和条目。工具步骤的阶段分 `preparing`（参数生成中）、`start`、`result`；pi 的 RPC 不转发生成中的参数时，`preparing` 不出现（待核实）。
- 每个挂载项外面包错误边界；视图崩了按"降级"退位，只记错误码。
- 视图第一次用到时才加载；加载失败只影响它自己的挂载点，核心界面不等插件（DSH 一个包失败整个界面停在启动页，不采用）。
- 界面文字由视图自己出；宿主照旧只发错误码和参数。

### 沙箱视图

核心提供，要求见下文"HTML 设计稿 · 插件接口要提前留的"。

### 降级

- 不在 Atrium 里：逻辑照常，视图被忽略。
- 在 Atrium 里时是一条链：第三方视图 → 内置视图（如有）→ 通用显示（工具步骤是结果文字加折叠的 `details` JSON，代码块是普通代码块）。没有视图、视图出错、加载失败、`atrium.api` 不兼容都沿链往下退，不白屏。
- 核心可以强制走通用显示：宿主拒绝或中止的调用、`details` 校验不过的，不进专用视图（同 DSH）。
- 每一级退位都报错误码，测试覆盖每一级。

### 开发与构建

- 插件是一个独立的 pi package（单独的仓库或本机目录）。逻辑写 TypeScript，pi 直接加载，不用编译；视图在插件目录里编译成 ESM，产物放 `dist/`，发布时带上。
- Atrium 提供 `@atrium/plugin-kit`：构建预设（外部依赖、ESM 输出）、视图 API 的类型、测试工具（扩展用 testkit 的 faux 模型跑真实 pi，视图用夹具数据做浏览器测试，两边共用插件包里的同一份 zod schema），以及 `atrium-plugin dev` / `build`。
- 开发时：`atrium-plugin dev` 监听并持续编译；把本地目录装进 pi（pi 的本地路径安装，实现前核实）；Atrium 看到 `dist/` 变了就热替换视图。逻辑改了要重启这个会话的 pi（RPC 里没有 reload），等会话空闲时重启，不打断运行。
- 第一方插件（如 todo）放在 monorepo 的 `plugins/<名字>/`，作为 workspace 包，由仓库的构建一起编译。
- 以后 agent 自扩展时也要编译：可能让宿主带同一套工具，只给本地链接的开发中插件现场编译；从 npm 装的仍只加载编译好的产物。

### 内置插件：现有界面迁成插件

2026-10-23 用户提出：现有界面也由插件实现。评估后的做法（待用户确认范围）：**内容型界面走插件 API，骨架不拆**。两份调研都支持这个划分：低代码引擎的画布、属性面板是内置插件但骨架写死；DSH 连骨架都是插件，代价是启动全有或全无、激活顺序要兵底、自建加载器、任何人都能遮住内置界面，而实际没有第三方替换过布局。

- **留在核心**（定义挂载点本身，和协议同步绑得紧）：窗口框架、侧栏、标签栏、对话流的骨架（轮、流式揭示、过程轨道）、输入框的核心（排队、插话、停止）、连接与同步、首次启动、设置框架、插件加载和降级、通用显示。子对话与子代理（车道、胶囊、面包屑）和 `ask_user` 也留着：宿主的 AgentRelay 和运行控制太重，界面和停止、插话的竞态纠缠。
- **迁成内置插件**：工具步骤、代码块渲染、右栏面板、查看标签、状态栏各项、设置分区、Fast。它们的宿主部分（文件、更改、套餐、上下文分段）照旧留在核心，经协议发出数据；视图经视图 API 拿。所以"插件不在宿主里跑代码"不变。
- **和第三方同一套 API、同一张注册表、同一套降级**，只是随应用静态打包，不走 import map 动态加载。内置视图的目录只能 import `@atrium/plugin-kit`，用现有的依赖规则（oxlint）拦住后门。低代码引擎的两个内置插件直接拿内部对象、DSH 的内置有约定上的特权，都不采用。
- **核心专属的数据**（套餐、上下文分段等）在 kit 里单独导出、标为内部，第三方的类型里没有。是否提供给第三方以后再定。
- **允许只有视图的内置插件**：pi 自带的工具（bash、read、edit、write）没有自己的 pi package。
- **内置视图也走错误边界和降级**，并有测试覆盖。

#### 迁移顺序

逐步迁，每步单独验收，迁一个就验收一次视图 API。

1. 注册表、视图 API 的最小版、`ToolDetails` 的插件分支和降级链；工具步骤（bash、read、edit、write、web_search）和自定义消息迁成内置插件；然后做 todo，作为第一个新插件。
2. 代码块渲染（Mermaid、PlantUML、JSON、CSV），验证按语言分派和按需加载。
3. 右栏和查看标签（文件、更改、文件查看、diff 查看），验证面板、查看标签和调用宿主能力的接口；接着做 HTML 设计稿。
4. 状态栏、设置分区、Fast，验证并列挂载点和视图到逻辑的回传。

### 以后的阶段

- loop devtools、上下文检查器（路线图阶段 4）要高吞吐地把数据传出来，通道到时写 ADR 定。
- agent 自扩展（阶段 5）：把 `extension_error` 和视图的报错交回 agent，热加载。
- 分享（阶段 6）：第三方插件的视图一律进沙箱、权限声明、向 MCP Apps 靠拢。

### 不做

- **插件不在宿主里跑代码**（Paseo 有 daemon 侧 RPC，Atrium 不做）。宿主只转发，插件逻辑在终端 pi 里也能用。代价：子代理、`ask_user` 这类要宿主编排的功能做不成插件，留在 Atrium 自带的扩展里。
- 插件之间的通信（pi 进程内已有 `pi.events`）、主题、覆盖核心组件、签名和市场。

## 约束

- **UI 不能依赖 `ctx.ui.custom()`**：RPC 模式只转发对话框和通知，不转发自定义终端组件。extension 只产出数据，渲染交给桌面端。
- **状态跟随会话分支**：状态放在 tool result 的 `details` 里，在 `session_start` / `session_tree` 时沿 `ctx.sessionManager.getBranch()` 重建（参考 pi 官方 `examples/extensions/todo.ts`）。
- **生命周期**：工厂函数里不启动进程和定时器，在 `session_start` 启动、在 `session_shutdown` 幂等清理。
- **依赖**：`@earendil-works/pi-*` 和 `typebox` 放进 `peerDependencies`（`"*"`），不要打包。
- **手机端**：视图基于 React DOM，在 PWA 里直接可用。将来若做原生 App，视图通过 WebView 加载，或由插件声明不支持手机端（见 [ADR-0005](../adr/0005-split-host-and-ui-pwa-first.md)）。

## 安全

extension 跑在 pi 进程里，拥有和 pi 相同的系统权限。第三方插件安装前要看源码；开放分享前，需要重新评估沙箱和权限声明。

受信任的视图跑在应用的源里，能拿到宿主的 token，能做宿主能做的一切。只装自己写的插件时，这和 extension 本来就有的权限相当。项目级插件（项目 `.pi/settings.json` 里的 package）可能来自别人的仓库：**它的视图第一次加载前要用户确认**，否则克隆一个仓库就能在应用源里执行任意界面代码（2026-10-22 定）。

## 待做的插件：HTML 设计稿

> 状态：只记了需求，还没设计（2026-10-15 记）。等做阶段 3"抽出插件接口"时，拿它当第二个插件来检验接口。

### 需求

用途：在对话里让模型写 HTML 页面并直接渲染出来，主要拿来做设计稿，所以会来回改很多次。

1. **渲染**：模型写的 HTML 直接显示在对话里，可以交互。
2. **一个文件持续改**：设计稿是一个文件，不是一条消息。第一次生成时写成文件，之后模型用普通的编辑工具局部修改这个文件，不在下一轮重新生成整页。对话里显示这个文件的卡片，渲染的是最新内容。
3. **标注**：在渲染出来的页面上选中某个元素（像开发者工具的元素选取），写一句意见，连同元素的定位一起交给模型去改。
4. **分享**：把当前版本上传到自己的云端（自己的服务器或存储桶），拿到一个链接发给别人看。

### 插件接口要提前留的

- **沙箱视图由核心提供**：模型写的 HTML 是信任度最低的内容（运行时生成，可能受提示注入影响），不能跑在应用的源里，因为那里能连宿主。核心提供一个"在独立源的 iframe 里渲染一段 HTML"的组件：用自定义协议、`sandbox` 不加 `allow-same-origin`、CSP 从 `default-src 'none'` 起、拒绝弹窗、跳转和权限请求，高度通过 postMessage 回报，离开视口时卸载并换成快照。插件只用这个组件，不自己写 iframe。注意 `srcdoc` 会继承父页面的 CSP，不能用。
- **视图分两档信任**：受信任的 React 视图（内置插件和自己写的插件）；沙箱视图（模型生成的内容，以后也可能包括第三方插件的视图）。
- **两种挂载点**：除了面板，还要能接管某个工具结果在消息流里的显示（内联）。
- **流式**：渲染器最好能拿到工具参数生成到一半的状态，先显示骨架。pi 的 RPC 会不会转发生成中的工具参数，还要对照 pi 源码确认。
- **双向通信**：沙箱里的页面要发消息给宿主（标注、按钮触发）时，消息格式参照 MCP Apps（SEP-1865）的 postMessage + JSON-RPC，以后同一个渲染器也能显示 MCP 服务器带的界面。

### 设计时要考虑

- **标注**：元素选取层由核心注入沙箱，选中的结果经 postMessage 传出来。交给模型的内容：元素的选择器路径、截断后的 outerHTML 片段、用户的意见，截图可选。标注可以攒几条一起发。
- **文件放哪**：是临时文件，不放进工作区，免得弄脏仓库；候选位置有会话目录或 `~/.atrium/` 下。要能"另存到工作区"。
- **版本**：每次修改留一个版本，可以回退。旧消息里的卡片显示当时的版本还是最新版，待定。
- **和会话分支的关系**：插件状态要跟着分支走（见上文"约束"），但磁盘上的文件只有一份。分支切换时文件内容怎么对应，待定；可能要按版本记录每个分支指向哪一版。
- **实时刷新**：文件变了卡片就重新渲染，尽量保留滚动位置。
- **上下文**：完整 HTML 不必每轮都放进上下文，模型需要时再读文件。
- **分享**：是对外发布，每次都要用户确认；上传前提醒页面里可能带着对话里的敏感内容。外部资源（CDN 脚本、远程图片）是否打包成单个文件，待定。分享目标可以配置（例如 S3 兼容的存储），凭据处理遵守 [security.md](security.md)。分享出去的页面会在别人的浏览器里执行模型写的脚本，要放在单独的域名下。
