# 验收指南

> 2026-10-20 定，把 M1.11 到 M1.15 实际验收的做法写下来。开发的步骤见 [development.md · 标准开发流程](development.md#标准开发流程)，测试规范见 [testing.md](architecture/testing.md)。本文回答三件事：改了什么要跑哪些测试；一件事交给用户之前要自己查什么；用户和里程碑怎么验收。

## 改了什么，跑什么

每次都要的：改过的文件格式化后 `pnpm check` 通过；新行为的测试先见过失败，并用 `pnpm break-check` 确认抓得住；追踪表登记。在此之上按改动的地方加跑：

| 改了哪里 | 加跑 | 说明 |
|---|---|---|
| `packages/protocol` | 单元（protocol、client） | 改了线上的形状就把 `PROTOCOL_VERSION` 加一，在 SPEC 里写明；`envelope.test.ts` 的样例跟着改 |
| `packages/client` | 单元 | 客户端的状态同步改了时，宿主的 `sync/` 测试也跑 |
| `packages/pi` | 单元 + `pnpm test:pi` | 依赖了 pi 的新行为，先写契约场景、用 faux 模型录夹具（`pnpm fixtures:record`，审查 diff）；本机 pi 升级了，先为新版本录夹具，再做别的 |
| `packages/host` | 单元 + `pnpm test:host` | 动了进程、监听、定时器、订阅的，加跑 `pnpm test:leak` |
| `packages/ui` | 单元 + `pnpm test:ui` | 看得见的改动自己截图看（见下文"交给用户之前"）；动了对话、新建工作区、子对话、模型面板的，跑对应的 e2e |
| `apps/desktop`（主进程、预加载、打包） | `pnpm test:e2e` 里相关的 spec | 改了打包、找文件的路径、应用目录内容时加跑 `pnpm test:package` |
| `scripts/` | 单元（`scripts/**/*.test.ts`） | |
| 只改文档 | `pnpm check`（格式） | |

核心模块（testing.md"让每个测试都有效"列的那些，见 `mutation-groups.mjs`）改了时，只对改动的文件跑变异测试：`pnpm test:mutation <组> --mutate=<文件>`，分数 ≥ 80%，新代码的存活变异补测试或注明等价；跑完清掉残留进程和 `.stryker-tmp`（development.md 第 5 步）。

**合回 `main` 之前**：先把最新的 `main` 合进分支，`pnpm check`、单元、界面（`pnpm test:ui`）都过；动了宿主或桌面端时再跑 `pnpm test:e2e`。遇到"已知不稳的测试"（testing.md）里列的失败，单独重跑一次确认是它，在汇报里写明，不当作通过的理由去忽略别的失败。

## 交给用户之前

自己先查完这些，再说"做完了"：

- **测试和检查**：上表要跑的都跑过，结果照实说：几个通过、哪个失败、是不是已知不稳的、单独重跑的结果。没跑的写明没跑。
- **看得见的改动**：用原型或打包出来的应用截图，自己看过浅色和深色、长文字、空状态、出错时；动效要看过几帧（慢放或逐帧采位置），确认没有跳位置、闪烁、截断。截图里不能有真实的项目名、对话、路径、用户名。
- **文档**：设计变化写进了 SPEC / design-language / domain-model / security，写明日期和"原先怎样、为什么改"；追踪表登记了；里程碑完成时路线图"当前状态"更新了。
- **自己定的细节**：文档没写、实现时自己定的，逐条列给用户确认，确认后补进文档。
- **残留**：worktree 里没有 `.tmp/`、`.stryker-tmp/`，没有自己起的进程还在跑；用户的剪贴板、浏览器、`~/.atrium` 没碰（必须碰时先说，碰过照实说）。

## 用户验收

- **先通知验收**：实现、自查和审查完成后，按 [标准开发流程第 7 步](development.md#标准开发流程) 主动请用户验收，提供可操作的步骤与预期结果；等待明确的验收结论，期间保留分支和 worktree，不提前合并或删除。
- **装上试用**：用户要试时按 development.md 第 7 步打包、换掉"应用程序"里的 Atrium.app。重启会中断正在跑的 pi，先数清有几个、问过用户再重启；装完看一眼宿主日志有没有新的错误。
- **自用记录**：用户试用中发现的问题记进 [self-use.md](research/self-use.md)；验收未通过的在本任务 worktree 修复并重新请用户验收，交付后发现的新问题按"标准开发流程"另开 worktree 处理，修 bug 先写能复现它的测试。
- **验收后收尾**：用户明确确认验收通过后，按 [标准开发流程第 8 步](development.md#标准开发流程) 提交、合并回 `main` 并安全删除原 worktree；用户要求保留或尚不满足安全清理条件时保留。提交与推送仍按各自的明确授权执行。

## 里程碑验收

- 路线图里这个里程碑的"完成标准"逐条对上，追踪表里涉及的行都有测试并过了变异门槛（testing.md"让覆盖面全"）。
- **三方审查**：合并前两个外部模型加一个 Claude 子代理各自只读审查（用哪两个外部模型由用户定，不自己换）。提问用下面的模板；结果合并去重，需要拍板的设计问题交给用户，其余按测试先行修掉，修完再跑一遍相关测试和变异测试。
- 审查的问题修完、测试都过、用户确认后，在路线图"当前状态"写这次做了什么、审查找到并修了什么、各组变异分数、已知的限制，再合回 `main`。

把 `<…>` 换成这次的内容，发给每个审查者：

```text

仓库：<worktree 的绝对路径>（分支 <分支名>）。

先读这些文档，它们是标准：

- <这次对应的 SPEC 章节、ADR>
```
